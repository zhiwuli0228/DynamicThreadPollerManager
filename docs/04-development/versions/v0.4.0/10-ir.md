## Header

- Document type: IR requirement draft
- Version name: `v0.4.0`
- Status: `BASELINED`
- Current phase: `IR_CLOSED`
- Authoring date: `2026-06-04`
- Current conclusion: IR review disposition and closure verification completed; usable as SR design input

## 1. 需求来源

### 1.1 用户确认方向

用户提出需要在后续实现中引入管理变更标准，并询问当前阶段是否需要压测数据获取，以确认下一阶段发展。基于当前能力边界，下一阶段应先获取 baseline pressure 与 policy replay evidence，而不是直接进入 executor mutation。

### 1.2 项目现状

当前已交付能力：

- `metrics-snapshot-and-recording`：可采集和记录 pressure snapshots。
- `scenario-runner-and-baseline`：可运行 deterministic baseline scenario。
- `adaptive-policy-and-control-gate`：可基于 pressure snapshot 产生 policy decision，并通过 control gate 限制结果。

当前缺口：

- baseline evidence 与 policy evaluator 尚未形成统一 replay 流程；
- policy decision 没有针对 scenario evidence 的可审计输出；
- 阈值敏感性和抖动风险尚无数据支撑；
- executor mutation 的下一阶段设计缺少决策输入。

### 1.3 需求判断

当前阶段确实需要获取实验数据，但这里的“压测数据”不应直接升级为真实生产压测平台。更合适的第一步是使用现有 deterministic scenario runner 产生或复用 baseline pressure evidence，再用现有 policy evaluator 做 offline replay。

本 IR 的核心判断：

- 没有 pressure evidence 和 replay summary，不应进入 executor mutation；
- replay 数据只能作为下一阶段设计输入，不能直接证明 runtime mutation 有收益；
- `v0.4.0` 应优先解决 evidence 可用性、decision 可审计性和 readiness gate，而不是扩大到闭环控制。

## 2. 范围

### 2.1 范围内

- Baseline pressure evidence 需求。
- Offline policy replay 需求。
- Policy decision evidence 需求。
- Replay summary / experiment report 输入需求。
- Threshold sensitivity 最小分析需求。
- 进入 executor mutation 前的 readiness gate。

### 2.2 范围外

- Java 实现。
- OpenSpec change 创建。
- executor mutation。
- queue resizing。
- scenario runner 行为修改。
- 真实压测平台。
- 持久化存储。
- 外部 API、UI 或生产集成。

### 2.3 名词和状态

| 术语 | 定义 |
| --- | --- |
| Baseline pressure evidence | fixed baseline scenario 运行期间记录的 pressure snapshots 和 run/scenario metadata |
| Offline policy replay | 使用已记录 snapshots 调用 policy evaluator，生成 policy decision，但不修改 executor 或 scenario |
| Decision evidence | 每次 replay 产生的 policy decision 记录，包含 action、gate status、reason 和 source snapshot reference |
| Replay summary | 对一批 decision evidence 的统计摘要，用于判断策略行为和风险 |
| Readiness gate | 进入 executor mutation 设计前的需求级判断，不自动授权实现 |
| Real pressure test | 更接近生产的压力测试或外部压测平台；本版本不纳入 |

## 3. IR 条目草案

### IR-v0.4-001 Baseline pressure evidence

系统需要定义 baseline scenario evidence 在进入 policy replay 前应具备的最小信息。

候选验收语义：

- evidence 必须能关联 run id、scenario id、baseline policy id；
- evidence 必须包含按时间排序的 pressure snapshots；
- snapshot 至少包含 timestamp、activeThreads、poolSize、queueSize、completedTaskCount；
- 空 evidence、乱序 evidence、重复 timestamp 或缺失关键字段必须有明确失败或不可 replay 语义。

优先级：P0。

需求理由：如果 baseline evidence 不可靠，后续 replay 和 readiness gate 都会建立在错误输入上。

### IR-v0.4-002 Offline policy replay

系统需要定义一个离线 replay 需求，用已记录 pressure snapshots 调用现有 policy evaluator，不改变 executor 或 scenario runner。

候选验收语义：

- replay 不得修改 executor、queue 或 scenario；
- replay 必须使用 caller-supplied timestamp，保持 deterministic；
- replay 必须为每个可评估 snapshot 生成 policy decision；
- replay 必须记录跳过或无法评估 snapshot 的原因。

优先级：P0。

需求理由：policy replay 是连接 v0.2.0 scenario evidence 和 v0.3.0 policy decision 的最小下一步。

### IR-v0.4-003 Decision evidence

系统需要定义 policy decision evidence 的字段和状态语义。

候选验收语义：

- decision evidence 至少包含 run id、policy id、timestamp、action、gate status、current pool size、proposed pool size、reason；
- decision evidence 必须保留 source snapshot 的引用或顺序索引；
- hold、accepted、capped、rejected 必须可统计；
- decision evidence 不得被误写为实际 executor adjustment。

优先级：P0。

需求理由：下一阶段设计需要 audit trail，不能只看最终统计数。

### IR-v0.4-004 Replay summary

系统需要定义 replay summary，帮助判断 policy 是否适合进入 executor mutation 设计。

候选验收语义：

- summary 必须统计 SCALE_UP、SCALE_DOWN、HOLD 的数量和比例；
- summary 必须统计 ACCEPTED、CAPPED、HOLD、REJECTED gate status 的数量和比例；
- summary 必须至少暴露以下抖动风险信号：
  - 相邻非 `HOLD` decision 的方向翻转次数；
  - `SCALE_UP` / `SCALE_DOWN` 连续交替的最大 streak；
  - `HOLD` ratio 和 `CAPPED` ratio；
- summary 必须报告 evidence count、decision count、skipped count。

优先级：P0。

需求理由：summary 是判断是否进入 executor mutation 设计的主要输入。

### IR-v0.4-005 Threshold sensitivity

系统需要定义最小阈值敏感性分析需求，用于比较不同 policy config 在同一 evidence 上的 decision 分布。

候选验收语义：

- 同一 evidence 可用多组 threshold config replay；
- 最小比较集必须至少包括：当前默认 config、一组更保守 config、一组更激进 config；
- 结果必须能比较 decision distribution 和 capped/hold ratio；
- 不要求自动寻找最优参数；
- 不允许引入 learned policy 或外部优化器。

优先级：P1。

需求理由：阈值敏感性可以降低把错误阈值接入 executor mutation 的风险，但不应膨胀为自动调参。

### IR-v0.4-006 Executor mutation readiness gate

系统需要定义进入 executor mutation / queue resizing 设计前的 readiness gate。

候选验收语义：

- 若没有 baseline pressure evidence 和 replay summary，不得进入 executor mutation 设计；
- 若 replay 出现高频抖动或大量 capped decision，必须记录为阻塞或残余风险；
- readiness gate 必须输出 `ready`、`not_ready` 或 `ready_with_risk`；
- readiness gate 只提供设计决策输入，不自动授权实现。

优先级：P0。

需求理由：readiness gate 用于阻止没有 evidence 的 executor mutation 设计。

### IR-v0.4-007 Evidence hygiene and boundary isolation

系统需要定义 evidence 和 replay 的边界卫生，避免 replay 结果被误解为实际运行时调整结果。

候选验收语义：

- replay evidence 必须明确标识 `offline_replay` 或等价模式；
- replay evidence 不得生成 `AdjustmentEvent` 或实际 mutation 记录；
- replay evidence 不得声称 throughput 改善，除非后续 mutation 实验实际证明；
- replay 过程不得新增外部依赖、持久化存储、REST API 或 UI；
- evidence 文件若后续设计需要落盘，默认根路径应位于 `outputs/reports/v0.4.0/` 或等价受控输出目录；
- 运行时 evidence 默认可本地生成、可脱敏、可从版本控制中排除大型输出；只有显式批准的摘要样例才允许进入版本控制。

优先级：P1。

需求理由：防止后续 agent 把 replay 证据误报为闭环 adaptive control 成果。

### IR-v0.4-008 Reviewable experiment readiness criteria

系统需要定义下一阶段 SR 设计前必须回答的实验准备问题。

候选验收语义：

- IR/SR 必须明确最少需要哪些 scenario 类型：steady、ramp、burst；
- 每类 scenario 至少需要一个 completed baseline run，且每个 run 至少提供 3 个有序 snapshots；低于此门槛时不得判定为 `ready`；
- 必须说明哪些 replay 指标会阻塞 executor mutation：例如 skipped count 非零、decision 抖动、capped ratio 过高；
- 必须定义 readiness gate 的最低判断规则：
  - 任一必需 scenario 缺失 -> `not_ready`；
  - evidence 门槛不足或 skipped count 非零 -> `not_ready`；
  - 存在明显抖动、高 capped ratio 或高 hold ratio -> `ready_with_risk` 或 `not_ready`，并记录理由；
- 必须说明真实压测数据何时才成为必需输入；
- 必须说明当前 v0.4.0 输出是否足以支持 v0.5.0 executor adapter 设计。

优先级：P1。

需求理由：避免“先实现再补数据”的顺序再次发生。

## 6. 非功能需求草案

| 类别 | 需求 |
| --- | --- |
| Determinism | 同一 evidence 和同一 policy config 的 replay 结果必须可重复 |
| Auditability | 每条 decision evidence 必须能追溯到 source snapshot 或 snapshot index |
| Boundary isolation | replay 不得依赖 executor mutation、queue controller、scheduler 或 external API |
| Local execution | 后续实现应默认本地可运行，不依赖真实外部服务 |
| Evidence hygiene | 大型或运行时输出不得默认进入版本控制，文档只记录摘要和路径约定 |
| Weak-agent implementability | 后续 SR 必须给出明确 schema、状态枚举、失败语义和测试映射 |

## 7. 风险和延期项

| 风险 | 当前判断 | 后续触发条件 |
| --- | --- | --- |
| baseline executor 当前可能是简化模拟，不代表真实生产压力 | 作为需求阶段残余风险记录 | 若要进入生产级 adaptive control，必须补更真实 workload 或压测数据 |
| policy replay 只能证明 decision 分布，不能证明 mutation 后效果 | 非阻塞 | executor mutation 设计阶段必须单独验证 runtime adjustment behavior |
| threshold sensitivity 可能膨胀为自动调参 | 阻止在 v0.4.0 扩大范围 | 自动调参必须进入后续版本 |
| readiness gate 可能被误解为实现授权 | 阻塞性边界风险 | current-state 必须单独授权 OpenSpec/SR/implementation |
| evidence 输出可能变成未治理的大文件 | 需求阶段记录 | SR 必须定义输出位置、摘要字段和版本控制排除策略 |
