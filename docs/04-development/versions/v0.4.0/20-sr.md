## 1. 设计目标

`v0.4.0` 的 SR 目标不是实现 adaptive control，而是把现有 baseline scenario evidence 和 policy evaluator 串成一个可审计、可比较、可判定 readiness 的离线分析层。

本设计必须满足：

- 复用现有 `ObservedSnapshot`、`ScenarioRunOutcome`、`PolicyDecision`、`ThresholdPolicyEvaluator`。
- 不修改 executor、queue、scenario runner、metrics recorder 或 policy evaluator 的既有边界。
- 输出足够稳定，让后续弱实现 agent 能实现离线 replay、summary、sensitivity 和 readiness gate。

## 2. 输入基线

### 2.1 已有能力

- metrics 层：
  - `ObservedSnapshot`
  - `EvidenceRecorder`
  - `EvidenceSummary`
- scenario 层：
  - `ScenarioDefinition`
  - `ScenarioProfile`
  - `ScenarioRunOutcome`
  - `ScenarioExperimentRunner`
- policy 层：
  - `ThresholdPolicyConfig`
  - `PolicyEvaluationInput`
  - `PolicyDecision`
  - `ThresholdPolicyEvaluator`
  - `GateStatus`
  - `PolicyAction`

### 2.2 约束

- 不引入新依赖。
- 不修改现有 archived capability 的语义。
- 不创建 OpenSpec change。
- 不设计任何 executor mutation 或 queue resizing 接口。

## 3. 总体方案

`v0.4.0` 新增一个独立的离线分析子层，建议放在新包：

- `com.zhiwu.dynamicthreadpollermanager.experiment.analysis`

该层只允许依赖：

- `experiment.metrics`
- `experiment.scenario`
- `experiment.policy`
- `experiment.model`

禁止依赖：

- `ThreadPoolExecutor`
- `ScheduledExecutorService`
- `AdjustmentEvent`
- 未来 executor adapter / queue controller
- 外部 IO client、database、REST controller

总体流程：

1. 读取一个已完成 baseline run 的元信息和其 recorded snapshots。
2. 校验 evidence 最小可用性。
3. 用一组 `ThresholdPolicyConfig` 对 snapshots 做 offline replay。
4. 生成逐 snapshot 的 decision evidence。
5. 聚合单 run summary。
6. 聚合多 config sensitivity comparison。
7. 聚合跨 scenario 的 readiness assessment。
8. 可选地产出受控输出目录下的 JSON/Markdown 摘要。

## 4. 模块划分

### 4.1 Evidence validation

职责：

- 检查 run metadata 是否完整。
- 检查 snapshot 列表非空、有序、关键字段可用。
- 检查最低门槛：每个 run 至少 3 个有序 snapshots。

建议组件：

- `ReplayEvidenceValidator`
- `ReplayEvidenceValidationResult`

`ReplayEvidenceValidationResult` 最小契约必须包含：

- `status`: `VALID` / `INVALID`
- `failureCodes`: 失败代码列表
- `failureReasons`: 面向人审阅的原因列表
- `acceptedSnapshotCount`: 进入 replay 的 snapshot 数量
- `rejectedSnapshotCount`: 被拒绝的 snapshot 数量

### 4.2 Offline replay

职责：

- 把每个 `ObservedSnapshot` 转成 `PolicyEvaluationInput`。
- 调用 `PolicyEvaluator` 生成 `PolicyDecision`。
- 为每条 decision 附加 source snapshot index 和 scenario metadata。

建议组件：

- `OfflinePolicyReplayService`
- `ReplayRunInput`
- `ReplayDecisionEvidence`

### 4.3 Summary aggregation

职责：

- 统计 action 分布。
- 统计 gate status 分布。
- 统计 skipped count。
- 统计最小抖动指标。

建议组件：

- `ReplayRunSummary`
- `ReplaySummaryBuilder`

### 4.4 Threshold sensitivity

职责：

- 在同一 evidence 上比较默认、保守、激进三组 config。
- 比较 action/gate ratio 与抖动指标差异。

建议组件：

- `SensitivityConfigSet`
- `SensitivityComparison`
- `ThresholdSensitivityAnalyzer`

### 4.5 Readiness gate

职责：

- 检查 steady/ramp/burst 三类 scenario 是否具备最小证据。
- 读取 summary 和 sensitivity 结果。
- 输出 `READY`、`READY_WITH_RISK`、`NOT_READY`。

建议组件：

- `ReadinessStatus`
- `ReadinessAssessment`
- `ReadinessThresholds`
- `MutationReadinessGate`

### 4.6 Report artifact

职责：

- 生成本地 JSON/Markdown 摘要。
- 强制写入受控目录。
- 不默认把大型原始 evidence 纳入版本控制。

建议组件：

- `ReplayReportArtifact`
- `ReplayReportWriter`

## 5. 数据契约

### 5.1 ReplayRunInput

建议字段：

| 字段 | 说明 |
| --- | --- |
| `runId` | 实验 run id |
| `scenarioId` | scenario 标识 |
| `scenarioProfile` | `STEADY` / `RAMP` / `BURST` |
| `baselinePolicyId` | baseline preset policy id |
| `snapshots` | `List<ObservedSnapshot>` |
| `evidenceSummary` | 现有 `EvidenceSummary` |
| `completedStepCount` | 来自 `ScenarioRunOutcome` |
| `totalWorkUnits` | 来自 `ScenarioRunOutcome` |

规则：

- `runId` 必须与所有 `ObservedSnapshot.runId()` 一致。
- `scenarioProfile` 不得为空。
- `snapshots.size() < 3` 时不得判定为可直接 `READY`。

### 5.2 ReplayDecisionEvidence

建议字段：

| 字段 | 说明 |
| --- | --- |
| `runId` | run id |
| `scenarioId` | scenario id |
| `scenarioProfile` | scenario profile |
| `policyConfigLabel` | `default` / `conservative` / `aggressive` |
| `policyId` | 具体 config 的 policy id |
| `snapshotIndex` | 从 0 开始的 evidence 顺序索引 |
| `snapshotTimestamp` | source snapshot timestamp |
| `decisionTimestamp` | 必须等于 replay input timestamp |
| `action` | `PolicyAction` |
| `gateStatus` | `GateStatus` |
| `currentPoolSize` | 当前线程池大小 |
| `proposedPoolSize` | policy/gate 输出大小 |
| `reason` | 非空 reason |
| `replayMode` | 固定为 `offline_replay` |

规则：

- `decisionTimestamp` 必须等于 source snapshot timestamp。
- `replayMode` 必须显式存在，防止误报为 runtime adjustment。
- 不允许出现 `AdjustmentEvent` 引用。

### 5.3 ReplayRunSummary

建议字段：

| 字段 | 说明 |
| --- | --- |
| `runId` | run id |
| `scenarioId` | scenario id |
| `scenarioProfile` | scenario profile |
| `policyConfigLabel` | config label |
| `evidenceCount` | 输入 snapshots 数量 |
| `decisionCount` | 成功 replay 的 decision 数量 |
| `skippedCount` | 跳过数量 |
| `scaleUpCount` | `SCALE_UP` 次数 |
| `scaleDownCount` | `SCALE_DOWN` 次数 |
| `holdCount` | `HOLD` 次数 |
| `acceptedCount` | `ACCEPTED` 次数 |
| `cappedCount` | `CAPPED` 次数 |
| `gateHoldCount` | `GateStatus.HOLD` 次数 |
| `rejectedCount` | `REJECTED` 次数 |
| `directionFlipCount` | 相邻非 HOLD action 的方向翻转次数 |
| `alternatingStreakMax` | `SCALE_UP` / `SCALE_DOWN` 交替的最大连续长度 |
| `holdRatio` | `holdCount / decisionCount` |
| `cappedRatio` | `cappedCount / decisionCount` |

规则：

- `decisionCount + skippedCount` 必须等于 `evidenceCount`。
- `decisionCount == 0` 时 summary 不得判定为 `READY`。
- `directionFlipCount` 和 `alternatingStreakMax` 只基于非 `HOLD` decision 计算。

### 5.4 SensitivityConfigSet

最小集合必须包含：

| label | 含义 |
| --- | --- |
| `default` | 当前默认 `ThresholdPolicyConfig.defaultAdaptive()` 或其等价默认配置 |
| `conservative` | 比默认更不容易 scale-up、更保守 scale-down 的配置 |
| `aggressive` | 比默认更容易 scale-up、步长更积极的配置 |

本 SR 不锁死数值，但要求后续实现和测试使用明确、固定、可复现的三组参数。

### 5.5 ReadinessAssessment

建议字段：

| 字段 | 说明 |
| --- | --- |
| `status` | `READY` / `READY_WITH_RISK` / `NOT_READY` |
| `evaluatedScenarioProfiles` | 已评估的 scenario profile 集合 |
| `missingScenarioProfiles` | 缺失的 profile 集合 |
| `blockingReasons` | 导致 `NOT_READY` 的原因 |
| `riskReasons` | 导致 `READY_WITH_RISK` 的原因 |
| `selectedConfigLabel` | 当前用于 readiness 判断的 config label，默认应为 `default` |
| `inputRunIds` | 参与判断的 run ids |

最小规则：

- 缺失任一必需 profile：`NOT_READY`
- 任一 run evidenceCount < 3：`NOT_READY`
- 任一 summary 的 skippedCount > 0：`NOT_READY`
- 明显抖动或高 capped ratio：`READY_WITH_RISK` 或 `NOT_READY`
- 只有在必需 profile 都存在且无阻塞时，才可 `READY` 或 `READY_WITH_RISK`

### 5.6 ReplayScenarioSummary

建议字段：

| 字段 | 说明 |
| --- | --- |
| `scenarioProfile` | `STEADY` / `RAMP` / `BURST` |
| `policyConfigLabel` | config label |
| `runIds` | 被聚合的 run ids |
| `runSummaries` | `List<ReplayRunSummary>` |
| `totalEvidenceCount` | 聚合 evidence 总量 |
| `totalDecisionCount` | 聚合 decision 总量 |
| `totalSkippedCount` | 聚合 skipped 总量 |
| `aggregateDirectionFlipCount` | 聚合 flip count |
| `aggregateAlternatingStreakMax` | 聚合最大交替长度 |
| `aggregateHoldRatio` | 聚合 hold ratio |
| `aggregateCappedRatio` | 聚合 capped ratio |

### 5.7 ReadinessThresholds

建议字段：

| 字段 | 说明 |
| --- | --- |
| `maxCappedRatioForReady` | `READY` 的 capped ratio 上限 |
| `maxHoldRatioForReady` | `READY` 的 hold ratio 上限 |
| `maxDirectionFlipCountForReady` | `READY` 的 flip count 上限 |
| `maxAlternatingStreakForReady` | `READY` 的最大交替长度上限 |
| `maxCappedRatioForRisk` | 超过该值则直接 `NOT_READY` |
| `maxHoldRatioForRisk` | 超过该值则直接 `NOT_READY` |
| `maxDirectionFlipCountForRisk` | 超过该值则直接 `NOT_READY` |
| `maxAlternatingStreakForRisk` | 超过该值则直接 `NOT_READY` |

## 6. 算法设计

### 6.1 Evidence validation

验证顺序：

1. `runId` 非空。
2. `scenarioId` 非空。
3. `scenarioProfile` 非空。
4. `snapshots` 非空。
5. `snapshots.size() >= 3`。
6. 所有 `ObservedSnapshot.runId()` 与输入 `runId` 一致。
7. snapshot timestamp 非空且按非降序排列。
8. `PressureSnapshot` 的 `activeThreads`、`poolSize`、`queueSize`、`completedTaskCount` 可读取。

失败语义：

- 若 1-7 任一失败，该 run 不进入 replay，生成 validation failure。
- validation failure 必须可计入 readiness gate 的 `blockingReasons`。

### 6.2 Offline replay

每个 snapshot 的 replay 步骤：

1. 读取 `ObservedSnapshot.snapshot()`。
2. 用 `runId`、`PressureSnapshot`、`snapshot.timestamp()` 构造 `PolicyEvaluationInput`。
3. 调用 `PolicyEvaluator.evaluate(input, config)`。
4. 生成 `ReplayDecisionEvidence`，附加 `snapshotIndex`、`scenarioProfile`、`policyConfigLabel`。

约束：

- 不得调用 wall clock API 重新生成 replay 时间。
- 不得调用 executor mutation、queue mutation 或 scheduler。

### 6.3 Direction flip 计算

定义：

- 只看非 `HOLD` action 序列。
- 若前一个非 `HOLD` 为 `SCALE_UP`，下一个非 `HOLD` 为 `SCALE_DOWN`，计一次 flip。
- 反向同理。

`alternatingStreakMax`：

- 对非 `HOLD` action 序列求最长交替片段长度。
- 如 `UP, DOWN, UP, DOWN` 的 streak 为 4。

### 6.4 Readiness gate

建议默认规则：

- `NOT_READY`
  - 缺失 `STEADY`、`RAMP`、`BURST` 中任一 profile
  - 任一 run evidenceCount < 3
  - 任一 summary skippedCount > 0
- `READY_WITH_RISK`
  - `cappedRatio` 过高
  - `holdRatio` 过高
  - `directionFlipCount` 或 `alternatingStreakMax` 显示明显抖动
- `READY`
  - 必需 profile 齐全
  - 无 skipped
  - 无阻塞风险
  - 抖动和 cap/hold 风险在接受范围内

本 SR 只定义规则结构，不在本阶段锁死具体阈值常数；阈值必须在后续实现前通过 SR review 固化。

## 7. 目录与 artifact 设计

默认输出目录：

- `outputs/reports/v0.4.0/`

建议 artifact：

| 文件 | 内容 |
| --- | --- |
| `replay-run-summary-<runId>-<configLabel>.json` | 单 run summary |
| `replay-scenario-summary-<scenarioProfile>-<configLabel>.json` | scenario 级聚合 |
| `replay-sensitivity-report-<runId>.json` 或 `...-<scenarioProfile>.json` | 默认/保守/激进比较 |
| `readiness-assessment-<version>.json` | readiness gate 输出 |
| `replay-report-<version>.md` | 面向人审阅的摘要 |

规则：

- 原始大 evidence 不默认复制到报告目录。
- JSON/Markdown 只包含脱敏、最小必要字段。
- 文档只追踪 artifact 路径和摘要，不提交大输出。
