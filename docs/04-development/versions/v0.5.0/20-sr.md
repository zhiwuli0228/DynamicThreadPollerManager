## Header

- Document type: SR functional design

## 1. 设计目标

`v0.5.0` SR 将已闭环 IR 转成后续 OpenSpec change 可执行的功能设计。目标是定义 executor adapter、pool size adjustment、runtime safety gate、adjustment evidence 和 queue resizing 延期规则。

本设计只描述下一步能力边界，不授权 Java 实现。

## 2. 设计结论

- 第一批后续 change 候选应聚焦 `executor-adapter-and-adjustment-evidence`。
- 第一批候选只允许 pool size adjustment，不包含 queue capacity resizing。
- queue resizing 默认延期，除非后续 SR/ADR 证明存在安全、可测试、可回滚的 queue abstraction。
- runtime mutation 必须消费可执行 command，不能直接消费 offline replay evidence。
- `v0.4.0` readiness status 是进入设计或实现的门禁输入，不是实现授权本身。

## 3. 模块边界

| 模块 | 职责 | 禁止事项 |
| --- | --- | --- |
| `experiment.policy` | 继续负责 policy evaluation、control gate、`PolicyDecision.toScaleDecision()` | 不引用 executor adapter、queue controller、scenario runner 或 adjustment evidence |
| `experiment.analysis` | 继续负责 offline replay、summary、sensitivity、readiness assessment | 不执行 runtime mutation，不生成 adjustment event |
| `experiment.adjustment` | 后续候选新子层；负责把可执行 scale command 应用于受控 executor adapter，并输出 adjustment result/evidence | 不重新评估 policy，不读取 scenario runner，不做 queue resizing 第一批实现 |
| `experiment.scenario` | 继续负责 deterministic baseline scenario | 不接入 runtime mutation，不改变 fixed baseline executor 行为 |

## 4. 输入与输出模型

### 4.1 Readiness 输入

后续 SR/OpenSpec change 必须显式读取或接收 `ReadinessAssessment` 等价输入。

| `ReadinessStatus` | 设计门禁 | 实现门禁 |
| --- | --- | --- |
| `READY` | 可进入 executor adapter SR / OpenSpec decomposition | 不自动授权实现，仍需 `current-state.md` 单独授权 |
| `READY_WITH_RISK` | 可进入 SR，但必须记录风险接受条件和额外测试要求 | 不得实现，除非 SR 明确列出风险接受、阻断条件和测试映射 |
| `NOT_READY` | 不得进入 runtime mutation implementation 设计；只能设计补证据或修复 readiness 的前置任务 | 不得实现 executor mutation 或 queue resizing |

### 4.2 Decision 到 Command 映射

后续实现不应直接把 `PolicyDecision` 或 replay decision evidence 传给 executor adapter。应先转换成可执行 command。

候选模型：

| 模型 | 字段 | 来源 |
| --- | --- | --- |
| `ScaleAdjustmentCommand` | `commandId` | caller generated deterministic id or derived id |
| `ScaleAdjustmentCommand` | `runId` | `ScaleDecision.runId()` |
| `ScaleAdjustmentCommand` | `decisionTimestamp` | `ScaleDecision.timestamp()` |
| `ScaleAdjustmentCommand` | `currentPoolSize` | `ScaleDecision.currentPoolSize()` |
| `ScaleAdjustmentCommand` | `targetPoolSize` | `ScaleDecision.proposedPoolSize()` |
| `ScaleAdjustmentCommand` | `reason` | `ScaleDecision.reasoning()` |
| `ScaleAdjustmentCommand` | `sourceDecisionRef` | policy decision id, snapshot index, or deterministic source reference |

映射规则：

- `commandId` 必须 deterministic。默认格式建议为 `<runId>:<decisionTimestamp>:<currentPoolSize>-><targetPoolSize>`；若后续实现需要更短 id，也必须由这些字段稳定派生。
- `PolicyDecision.toScaleDecision()` 是从 policy layer 到 executor-applicable target 的唯一现有入口。
- 只有 `GateStatus.ACCEPTED` 或 `GateStatus.CAPPED` 且 `PolicyAction != HOLD` 的 decision 可以转换。
- `GateStatus.HOLD`、`GateStatus.REJECTED`、`PolicyAction.HOLD`、`currentPoolSize == proposedPoolSize` 必须被拒绝或转为 no-op result，不得执行 mutation。
- offline replay evidence 只能作为 source reference，不得直接驱动 runtime mutation。

## 5. Executor Adapter 设计

### 5.1 候选接口

后续实现候选：

```java
public interface ExecutorAdjustmentAdapter {
    ExecutorStateSnapshot currentState();
    AdjustmentResult apply(ScaleAdjustmentCommand command);
}
```

### 5.2 设计语义

| 行为 | 语义 |
| --- | --- |
| `currentState()` | 返回 adapter 观察到的 executor state，不执行 mutation |
| `apply(command)` | 尝试应用 pool size adjustment，并返回结构化 result |
| invalid command | 返回 `REJECTED`，不得抛出未分类异常 |
| boundary violation | 返回 `REJECTED` 或 `CAPPED_BY_SAFETY_GATE`，具体状态由 SR review 后确定 |
| no-op target | 返回 `NO_OP`，不得调用 executor mutation |
| runtime exception | 捕获并转换为 `FAILED` result，保留 failure reason |

### 5.3 禁止依赖

后续 `experiment.adjustment` 第一批实现不得引用：

- `ScenarioExperimentRunner`
- `BaselineWorkloadExecutor`
- `ReplayReportWriter`
- persistence / REST / UI 类型
- queue capacity controller
- scheduler 或 closed-loop controller

若必须使用 `ThreadPoolExecutor`，必须通过 adapter 边界隔离，且测试中要证明 policy/analysis/scenario 包未反向依赖 adjustment 包。

第一批 bounded change 默认不直接集成生产 `ThreadPoolExecutor`。推荐先实现可测试的受控 adapter contract、in-memory adjustable executor probe 和 evidence 模型；真实线程池集成需要后续单独授权。

## 6. Pool Size Adjustment 语义

### 6.1 Executor State Snapshot

候选模型：

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `observedAt` | yes | caller supplied timestamp，不在 adapter 内读 wall-clock |
| `corePoolSize` | yes | 当前 core pool size |
| `maximumPoolSize` | yes | 当前 maximum pool size |
| `activeCount` | no | 可选观测字段 |
| `queueSize` | no | 可选观测字段 |
| `queueCapacity` | no | 只读字段，不代表可 resize |

### 6.2 Adjustment Result

候选状态枚举：

| 状态 | 语义 |
| --- | --- |
| `APPLIED` | target 已应用，after state 与目标一致或满足 adapter contract |
| `REJECTED` | safety gate 或 input validation 阻止执行 |
| `NO_OP` | target 与当前状态一致，未执行 mutation |
| `FAILED` | 尝试执行但发生 runtime failure |
| `DEFERRED` | 当前 adapter 明确不支持该 adjustment 类型 |

候选结果字段：

- `commandId`
- `runId`
- `status`
- `beforeState`
- `requestedPoolSize`
- `appliedPoolSize`
- `afterState`
- `reason`
- `failureCode`
- `sourceDecisionRef`
- `decisionTimestamp`

## 7. Runtime Safety Gate

后续 SR/OpenSpec change 必须把 safety gate 设计为 adapter 之前的阻断层，而不是混在 adapter mutation 逻辑里。

候选模型：

```java
public interface RuntimeAdjustmentSafetyGate {
    SafetyGateDecision evaluate(ScaleAdjustmentCommand command, ExecutorStateSnapshot currentState);
}
```

最小阻断规则：

| 规则 | 默认语义 |
| --- | --- |
| target below minimum | reject |
| target above maximum | reject or cap，必须在 spec 中固定 |
| target equals current | no-op |
| cooldown not elapsed | reject |
| opposite direction immediately after previous adjustment | reject |
| per-run adjustment count exceeds limit | reject |
| readiness `NOT_READY` | reject |
| readiness `READY_WITH_RISK` without accepted risk profile | reject |

建议默认阈值由后续 OpenSpec 固定，不在本 SR 中硬编码实现值。

第一批 OpenSpec change 的最小建议默认值：

| 配置 | 建议默认值 | 说明 |
| --- | --- | --- |
| `cooldownDecisionIntervals` | `2` | 任一 accepted adjustment 后，至少跳过 2 个后续 decision index 才允许再次调整 |
| `maxAdjustmentsPerRun` | `5` | 单 run 内超过上限后拒绝 |
| `blockImmediateOppositeDirection` | `true` | 上一次 applied 为 scale up 时，下一次 scale down 必须被拒绝；反向同理 |
| `allowReadyWithRisk` | `false` | 未显式接受风险时，`READY_WITH_RISK` 阻止 mutation |

若 OpenSpec 后续改用不同默认值，必须在 design/spec/tasks 中说明理由并补测试。

## 8. Adjustment Evidence

后续实现必须生成 runtime adjustment evidence，且不能和 offline replay evidence 混淆。

候选字段：

| 字段 | 说明 |
| --- | --- |
| `evidenceType` | 固定为 `runtime_adjustment` |
| `commandId` | command identity |
| `runId` | run identity |
| `sourceDecisionRef` | policy decision / scale decision reference |
| `decisionTimestamp` | source decision timestamp |
| `recordedTimestamp` | caller supplied recording timestamp |
| `beforeState` | mutation 前 state |
| `requestedPoolSize` | command target |
| `appliedPoolSize` | 实际应用值，未应用时为空或等于 before |
| `afterState` | mutation 后 state |
| `status` | `APPLIED` / `REJECTED` / `NO_OP` / `FAILED` / `DEFERRED` |
| `reason` | 审计 reason |
| `failureCode` | 失败或拒绝原因码 |

Evidence hygiene：

- runtime adjustment evidence 不得写入 `outputs/reports/v0.4.0/`。
- 后续版本若落盘，应使用 `outputs/reports/v0.5.0/` 或后续 OpenSpec 固定路径。
- 大型 runtime evidence 默认不得进入版本控制。

## 9. Queue Resizing 判定

本 SR 明确：queue resizing 不进入 `v0.5.0` 第一批实现候选。

原因：

- 当前代码只有 `BaselineExecutorPreset.queueCapacity()` 和只读 `queueSize` 观测。
- 当前没有 runtime `QueueCapacityController` 或可回滚 queue abstraction。
- Java executor queue capacity 是否可安全调整取决于具体 queue 类型，不能被 pool size adjustment 语义覆盖。

若后续重新纳入，必须先产出单独 SR/ADR，至少回答：

- queue 类型是否支持 resize；
- resize 是否原子；
- resize 失败时如何恢复；
- 已排队任务如何处理；
- 与 pool size adjustment 的顺序关系；
- 测试如何证明并发安全。

## 10. OpenSpec Change 分解建议

SR review 闭环后，建议只创建一个 bounded change：

- change name: `executor-adapter-and-adjustment-evidence`
- capability: `executor-adapter-and-adjustment-evidence`
- scope:
  - scale adjustment command
  - executor state snapshot
  - runtime safety gate
  - executor adjustment adapter interface
  - in-memory adjustable executor probe for deterministic tests
  - adjustment result/evidence
  - boundary isolation tests
- non-scope:
  - queue resizing
  - closed-loop scheduler/controller
  - REST/API/UI
  - persistence
  - real production `ThreadPoolExecutor` integration
  - throughput improvement claims
