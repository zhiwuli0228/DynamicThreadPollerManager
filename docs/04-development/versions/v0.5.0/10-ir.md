# v0.5.0 IR 需求分析草案

## Header

- Document type: IR requirement draft
- Version name: `v0.5.0`
- Status: `DRAFT`
- Current phase: `IR_REQUIREMENT_DRAFT_AUTHORIZED`
- Authoring date: `2026-06-05`
- Current conclusion: draft requirements only; not usable as SR or implementation input until IR review closure

## 1. 需求来源

### 1.1 用户确认方向

用户要求按预定规划继续推进。根据 `v0.4.0` 的交付结论，下一阶段应使用 offline replay 和 readiness evidence 判断是否可以进入 executor adapter、queue resizing 或 runtime mutation 设计。

### 1.2 项目现状

当前已交付能力：

- `scenario-runner-and-baseline`：可生成 deterministic baseline runs。
- `metrics-snapshot-and-recording`：可记录 pressure snapshots。
- `adaptive-policy-and-control-gate`：可生成受 control gate 约束的 policy decision。
- `offline-replay-and-readiness-gate`：可离线 replay policy decision，生成 summary、threshold sensitivity 和 readiness assessment。

当前缺口：

- 尚未定义 runtime executor adapter 的最小控制接口；
- 尚未定义实际调整 executor 时的失败语义和审计记录；
- queue resizing 的安全性、可逆性和边界风险尚未被拆开评估；
- readiness gate 目前只提供设计输入，不自动授权 implementation；
- 尚未定义从 policy decision 到 runtime adjustment 的映射规则。

### 1.3 需求判断

`v0.5.0` 不应直接实现闭环 adaptive control。合理的下一步是先完成 executor adapter 和 queue resizing 的需求分析，明确哪些能力可以进入 SR 设计，哪些能力必须继续延期。

本 IR 的核心判断：

- executor mutation 是运行时状态突变，必须先有安全门限、失败语义和 audit trail；
- queue resizing 风险高于 pool size adjustment，应被单独判定；
- replay readiness 只能作为设计输入，不能替代运行时安全验证；
- 当前阶段不授权 Java 实现。

## 2. 范围

### 2.1 范围内

- Executor adapter 需求边界。
- Pool size adjustment 的最小需求。
- Queue resizing 的纳入/延期判断。
- Runtime adjustment safety gate。
- Adjustment evidence / audit trail。
- Policy decision 到 runtime adjustment 的映射需求。
- Implementation authorization 前的阻塞条件。

### 2.2 范围外

- Java 实现。
- SR 功能设计。
- OpenSpec change 创建。
- executor mutation 实现。
- queue resizing 实现。
- scheduler 或 closed-loop controller。
- persistence、REST API、UI、外部依赖。
- 自动调参或 learned policy。

### 2.3 名词和状态

| 术语 | 定义 |
| --- | --- |
| Executor adapter | 位于 policy decision 和实际 executor 之间的受控突变边界 |
| Pool size adjustment | 对 core/max pool size 或等价 executor capacity 的受控调整 |
| Queue resizing | 对 queue capacity 的调整；风险和实现策略需独立评估 |
| Runtime adjustment | 对正在运行的 executor 或队列容量产生实际影响的操作 |
| Adjustment evidence | 记录 adjustment request、accepted/rejected status、before/after state、reason 和 failure 的审计证据 |
| Safety gate | runtime adjustment 前的阻断规则，不等同于 `v0.4.0` offline readiness gate |

## 3. IR 条目草案

### IR-v0.5-001 Executor adapter boundary

系统需要定义 executor adapter 的最小职责和禁止职责。

候选验收语义：

- adapter 只能接收已通过 control gate 的 accepted/capped decision；
- adapter 必须显式拒绝 `HOLD`、`REJECTED` 或缺少 target pool size 的 decision；
- adapter 不得重新评估 policy；
- adapter 不得直接依赖 scenario runner；
- adapter 必须输出 adjustment result，而不是只抛异常或静默失败。

优先级：P0。

### IR-v0.5-002 Pool size adjustment semantics

系统需要定义 pool size adjustment 的最小行为语义。

候选验收语义：

- 必须记录 before pool size、requested pool size、applied pool size；
- 必须定义 min/max boundary；
- 必须定义 scale up 和 scale down 的不同风险；
- 必须定义无变化 adjustment 的结果语义；
- 必须定义 adjustment 失败时的状态和 reason。

优先级：P0。

### IR-v0.5-003 Queue resizing decision

系统需要判断 queue resizing 是否纳入 `v0.5.0` 后续 SR。

候选验收语义：

- 必须列出 queue resizing 的可行实现路径和风险；
- 若当前 queue 实现不支持安全 resize，应明确延期；
- 不允许把 queue resizing 混入 pool size adjustment；
- 若纳入后续 SR，必须单独定义 capability、failure 和 rollback semantics。

优先级：P0。

### IR-v0.5-004 Runtime safety gate

系统需要定义 runtime adjustment 前的 safety gate。

候选验收语义：

- 没有 `v0.4.0` readiness evidence 时不得进入 runtime mutation SR；
- readiness 为 `not_ready` 时不得进入 mutation implementation；
- readiness 为 `ready_with_risk` 时必须记录风险接受条件；
- 必须定义 adjustment frequency / oscillation 风险的阻断条件；
- 必须定义异常、invalid state、boundary cap 的处理语义。

优先级：P0。

### IR-v0.5-005 Adjustment evidence

系统需要定义 runtime adjustment 的审计证据。

候选验收语义：

- evidence 必须包含 request id、run id、decision reference、before state、target state、after state、status、reason、timestamp；
- evidence 必须区分 requested、applied、rejected、failed、no-op；
- evidence 不得和 offline replay decision evidence 混淆；
- evidence 必须支持后续 acceptance precheck 的追踪矩阵。

优先级：P0。

### IR-v0.5-006 Implementation authorization guard

系统需要定义从需求/设计进入实现前的强制阻塞项。

候选验收语义：

- IR/SR 未闭环不得创建 OpenSpec change；
- 没有明确 adapter contract 不得实现 Java mutation；
- 没有 adjustment evidence contract 不得实现 mutation；
- 没有测试映射不得授权实现；
- queue resizing 未单独判定前不得实现 queue capacity 修改。

优先级：P0。

## 6. 风险和延期项

| 风险 | 当前判断 | 后续触发条件 |
| --- | --- | --- |
| queue resizing 原地调整可能不安全 | 阻塞性设计风险 | SR 必须单独论证，否则延期 |
| runtime adjustment 可能导致抖动或频繁 resize | 阻塞性行为风险 | 必须定义 safety gate 和测试映射 |
| replay readiness 不能证明 mutation 后收益 | 残余风险 | 后续 runtime experiment 必须单独验证 |
| adapter contract 过宽会扩大实现风险 | 阻塞性边界风险 | SR 必须明确最小接口和禁止依赖 |

- runtime safety gate 是否有明确阻塞语义；
- adjustment evidence 是否足以审计实际突变；
- 是否存在 SR、OpenSpec 或 Java 实现越权内容。
