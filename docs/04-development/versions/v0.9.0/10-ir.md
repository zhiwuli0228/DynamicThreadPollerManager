## 1. 需求来源

### 1.1 项目现状

v0.8.0 完成了在真实 ThreadPoolExecutor 上的多场景数据获取。但 **queue capacity 仍是静态配置**：

| 能力 | 动态调整 | 实现版本 |
|---|---|---|
| corePoolSize | 可动态调整 | v0.7.0 (`ScaleAdjustmentCommand`) |
| maximumPoolSize | 可动态调整 | v0.7.0 (`ScaleAdjustmentCommand`) |
| **queueCapacity** | **不可动态调整** | **从未实现** |
| keepAliveTime | 可动态调整 | v0.7.0 (`RuntimeSetting`) |
| rejectionPolicy | 不可动态调整 | 未设计 |

### 1.2 结构性缺口

- **`ThreadPoolExecutor` 不支持运行时 queue 替换**：`workQueue` 是构造时传入的 final 字段，无公开 setter。任何 queue capacity 变更都需要 executor rebuild（decommission old → commission new）。
- **`RuntimeSetting` 排除 queue capacity**：当前 `RuntimeSetting` 只包含 corePoolSize/maxPoolSize/keepAliveTime，queueCapacity 不在其中。
- **`ScaleAdjustmentCommand` 只能调整线程数**：`targetPoolSize()` 对应 core pool size，没有 queue capacity 维度。
- **`ManagedExecutorAdjustmentAdapter` 只适配线程数调整**：`apply(ScaleAdjustmentCommand)` 调用 `setCorePoolSize()`/`setMaximumPoolSize()`，无法操作 queue。

### 1.3 为什么是现在

- v0.7.0/v0.8.0 已证明 executor 创建、注册、执行、关闭、证据记录全链路稳定（433 tests, 0 failures）
- `ExecutorRegistry` 的 `DeletionSafety` 为 executor 替换提供了天然的注册/注销框架
- `ExecutorStateSnapshot` 提供完整的 before/after state 对比能力
- `QueueResizeSafetyGate` 可复用 v0.4.0 的 `ControlGate` 接口模式
- 每个历史版本 scope 都写 "No queue resizing"——v0.9.0 是解决这个遗产的正确时机

## 2. 范围

### 2.1 范围内

- `QueueResizeCommand` record，封装目标 queue capacity 及 resize 参数
- `ExecutorRebuildStrategy`，实现 decommission → commission 周期
- `QueueResizeSafetyGate`，检查 resize 操作的安全性（queue 深度 vs 新容量等）
- 扩展现有 `ManagedExecutorAdjustmentAdapter` 或新增 adapter 接收 QueueResizeCommand
- `ResizeEvidence` 或扩展现有 evidence 类型记录 resize before/after
- 端到端集成测试：resize → re-run scenario → 验证新 queue capacity 生效
- 现有 433 测试零回归

### 2.2 范围外

- Rejection policy 运行时切换
- 自动触发 resize（closed-loop controller）
- 多执行器协调 resize
- 持久化 resize 历史
- CLI entry（DFR-01，可作为 v0.9.0 次要目标单独评估）
- 生产环境集成
- `ThreadPoolExecutor` 子类化或反射 hack

### 2.3 术语

| 术语 | 定义 |
|---|---|
| QueueResizeCommand | 不可变 record，封装目标 queue capacity，类似 ScaleAdjustmentCommand 但操作队列 |
| ExecutorRebuildStrategy | decommission（drain tasks → shutdown → awaitTermination）→ commission（create new TPE with resized queue → re-register）的策略 |
| Decommission | 排空在途任务、关闭旧 executor、等待终止的过程 |
| Commission | 用新 queue capacity 构建新 ThreadPoolExecutor、注册到 ExecutorRegistry 的过程 |
| Drain-and-replay | 排空旧 queue 中的等待任务，在新 executor 中重新提交 |
| QueueResizeSafetyGate | 在 resize 前评估安全性的门禁：queue 深度 vs 新容量、executor 状态等 |
| ResizeEvidence | resize 操作的完整证据：before/after ExecutorStateSnapshot, rebuildDuration, drainedTaskCount, resizeDirection |

## 3. IR 条目草案

### IR-v0.9-001 QueueResizeCommand

系统需要 `QueueResizeCommand` record 封装 queue capacity 调整请求。

候选验收语义：

- 必须包含字段：`targetQueueCapacity` (int, > 0)、`resizeReason` (String, 可选)、`timeoutMs` (long, >= 0, 默认值)。
- 构造时必须验证 `targetQueueCapacity > 0`，否则抛出 `IllegalArgumentException`。
- 必须提供 `fromCurrent(int currentCapacity, int newCapacity)` 工厂方法：若 `newCapacity == currentCapacity`，返回 `Optional.empty()`（无需 resize）。
- 必须提供 `resizeDirection()` 方法：返回 `EXPAND`（newCapacity > current 时）、`SHRINK`（newCapacity < current 时）、或 `NO_CHANGE`。
- 不可变（record）。
- 不强制要求与 `ScaleAdjustmentCommand` 共享基类或接口（两者操作不同维度）。

优先级：P0。

### IR-v0.9-002 ExecutorRebuildStrategy

系统需要 `ExecutorRebuildStrategy` 实现安全的 executor decommission → commission 周期，解决 `ThreadPoolExecutor` 不支持运行时 queue 替换的限制。

候选验收语义：

- 必须接受构造参数：旧 `ManagedExecutor`、目标 `QueueResizeCommand`、`ExecutorRegistry`、clock supplier。
- `rebuild()` 方法必须返回新的 `ManagedExecutor`（wrapping 以新 queue capacity 构建的 `ThreadPoolExecutor`）。
- Decommission 阶段：
  - 停止向旧 executor 提交新任务（通过 registry 标记或内部标志）
  - 排空旧 work queue 中等待的任务（drain）：`executor.getQueue().drainTo(pendingTasks)`
  - 调用旧 executor 的 `shutdown()` → `awaitTermination(timeoutMs, MILLISECONDS)`
  - 若 awaitTermination 超时，调用 `shutdownNow()` 强制终止
- Commission 阶段：
  - 用旧 executor 的 corePoolSize、maximumPoolSize、keepAliveTime、threadFactory 创建新的 `ThreadPoolExecutor`，但 **work queue 容量使用 `targetQueueCapacity`**
  - 将新 TPE 包装为 `ManagedExecutor`
  - 在 `ExecutorRegistry` 中替换注册（remove old → register new，保持同一 executorId，或分配新 ID 并在 evidence 中记录映射）
- 若 drain 出的 pendingTasks 非空且 resize 方向为 EXPAND：在新 executor 中重新提交这些任务（drain-and-replay）
- 若 resize 方向为 SHRINK 且 drain 出的任务数 > 0：这些任务可能无法放入新 queue（因为新 queue 容量更小）。replay 时必须检查新 queue 是否有空间；若空间不足，记录为 `rejectedTaskCount` 在 evidence 中。
- 整个 rebuild 过程必须可中断（通过 `Thread.interrupt()` 或 timeout）。
- 不得使用反射访问 `ThreadPoolExecutor.workQueue`。
- 不得修改旧 executor 的 `ThreadPoolExecutor` 配置。

优先级：P0。

### IR-v0.9-003 QueueResizeSafetyGate

系统需要在 resize 操作前评估安全性，防止危险操作（如 queue 深度超过新容量时缩小队列）。

候选验收语义：

- 必须实现 `ControlGate<QueueResizeCommand>` 或等效接口。
- `evaluate(QueueResizeCommand command, ManagedExecutor executor)` 方法必须返回 `SafetyGateResult`（PERMIT / DENY / REQUIRE_DRAIN）。
- 安全检查至少包括：
  - **容量合法性**：`targetQueueCapacity > 0`（已在 command 构造时验证，safety gate 二次确认）
  - **容量变更**：`targetQueueCapacity != currentQueueCapacity`（无变更则 DENY 并建议使用 NOOP）
  - **SHRINK 安全性**：若 `resizeDirection == SHRINK` 且 `executor.getQueue().size() > targetQueueCapacity`，必须 DENY（或 REQUIRE_DRAIN 要求先排空）
  - **Executor 状态**：executor 必须处于 RUNNING 状态（非 SHUTDOWN/TERMINATED）
  - **幂等保护**：若 executor 已在 resize 过程中（通过 registry 中的标记或状态检查），必须 DENY
- DENY 结果必须包含明确的拒绝原因字符串。
- 不得在 safety gate 中直接修改 executor 状态（只读检查）。

优先级：P0。

### IR-v0.9-004 Adapter 扩展（QueueResize）

系统需要扩展调整链路以支持 QueueResizeCommand。可直接扩展现有 `ManagedExecutorAdjustmentAdapter` 或新增 adapter。

候选验收语义：

- 现有 `ManagedExecutorAdjustmentAdapter.apply(ScaleAdjustmentCommand)` 不得修改签名或行为。
- 新增 `apply(QueueResizeCommand)` 方法（或在同一个 adapter 中，或在新 adapter 中）。
- `apply(QueueResizeCommand)` 流程：
  1. 通过 registry 查找目标 ManagedExecutor
  2. 调用 `QueueResizeSafetyGate.evaluate(command, executor)`
  3. 若 PERMIT：调用 `ExecutorRebuildStrategy.rebuild(command, executor)`
  4. 若 DENY：返回失败结果，包含拒绝原因
  5. 若 REQUIRE_DRAIN：先 drain queue 再 rebuild
- 返回 `AdjustmentResult`（复用现有类型或新增 resize-specific 结果类型）。
- 若使用现有 `AdjustmentResult`，其 `evidence()` 方法必须包含 `ResizeEvidence`。
- 不得移除现有的 `ScaleAdjustmentCommand` 支持。

优先级：P0。

### IR-v0.9-005 ResizeEvidence

系统需要为每次 resize 操作记录完整证据。

候选验收语义：

- `ResizeEvidence` record 必须包含：
  - `beforeState`: `ExecutorStateSnapshot`（pre-rebuild 的 executor 状态）
  - `afterState`: `ExecutorStateSnapshot`（post-rebuild 的新 executor 状态，刚创建尚未提交任务）
  - `rebuildDurationMs`: long
  - `drainedTaskCount`: int（从旧 queue 排空的等待任务数）
  - `rejectedTaskCount`: int（SHRINK 时因新 queue 空间不足未能 replay 的任务数）
  - `resizeDirection`: enum `EXPAND` / `SHRINK`
  - `success`: boolean
  - `oldQueueCapacity`: int
  - `newQueueCapacity`: int
- 必须可通过 `EvidenceRecorder` 或等效机制记录。
- `ResizeEvidence` 必须在 `AdjustmentResult.evidence()` 中可访问。

优先级：P1。

### IR-v0.9-006 端到端 Resize 验证

系统需要端到端集成测试验证完整的 resize 流程。

候选验收语义：

- 测试流程：
  1. 创建 ManagedExecutor（queue=10），注册到 registry
  2. 提交若干任务填满 queue（queue.size() ≈ 10）
  3. 等待任务完成（queue 排空）
  4. 发出 QueueResizeCommand（newCapacity=20，EXPAND）
  5. 验证 resize 成功：新 executor 的 queue capacity 为 20
  6. 使用 ManagedExecutorScenarioRunner（STEADY profile）在新 executor 上运行
  7. 验证 runner 正常完成，所有 snapshot 有效
  8. 验证 @AfterEach cleanup（先 latch countDown → shutdown → awaitTermination → registry.remove）
- 必须测试 SHRINK 路径：queue=20 → resize 到 queue=5，验证新旧容量正确
- 必须测试 safety gate DENY：queue 中有 8 个等待任务时尝试 shrink 到 5，验证 DENY
- 必须测试 executor 状态一致性：旧 executor 在 rebuild 后已 terminated，新 executor 已 registered 且 running
- 现有 433 测试零回归

优先级：P0。

## 6. 风险和延期项

| 风险 | 当前判断 | 后续触发条件 |
|---|---|---|
| drain-and-replay 中任务丢失或重复 | P0 风险 | SR 确认 drain/replay 原子性保证；若无法保证则降级为 drain-and-discard + 调用方感知 |
| SHRINK resize 时 drained 任务无法放入新 queue | P0 风险 | SR 确认策略：reject drained tasks + 记录 rejectedTaskCount，或拒绝 SHRINK 当 drained > 0 |
| awaitTermination 超时导致 rebuild 挂起 | P1 风险 | SR 确认 timeout 默认值和超时后 shutdownNow 策略 |
| 两个并发 resize 请求导致 executor 状态冲突 | P1 风险 | SR 确认幂等保护机制（registry 标记或锁） |
| registry 替换注册期间 executor 不可用 | P2 风险 | 窗口极小（微秒级引用切换）；SR 可评估是否需要双缓冲注册 |
| 线程配置（core/max/keepAlive）在 rebuild 期间被其他线程修改 | P2 风险 | 当前系统单线程执行 adjust；若未来引入并发需额外保护 |

## 9. 当前结论

v0.9.0 IR 草案已定义 queue capacity resizing 的需求方向：6 条 IR 覆盖 QueueResizeCommand（命令封装）、ExecutorRebuildStrategy（decommission → commission 安全周期）、QueueResizeSafetyGate（安全门禁）、Adapter 扩展（调整链路集成）、ResizeEvidence（证据记录）、端到端验证（EXPAND + SHRINK + DENY 全路径）。本文不授权实现或 OpenSpec change；下一步是 IR review。
