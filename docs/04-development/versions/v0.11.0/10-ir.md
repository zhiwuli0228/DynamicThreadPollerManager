# v0.11.0 IR 需求分析草案

## Header

- Document type: IR requirement draft
- Version name: `v0.11.0`
- Status: `DRAFT`
- Current phase: `PERSISTENT_METRICS_REQUIREMENT_DRAFT`
- Authoring date: `2026-06-13`
- Current conclusion: 本文只定义 persistent metrics recording and live sampling 需求，不授权 SR、OpenSpec change、Java 实现

## 1. 需求来源

### 1.1 项目现状

v0.1.0 交付了 metrics-snapshot-and-recording 的基础能力（RuntimeObservation → SnapshotAssembler → ObservedSnapshot → EvidenceRecorder → EvidenceSummary），但仅限于内存实现。三个动态配置维度（thread count、queue capacity、rejection policy）已全部完成（v0.7.0-v0.10.0），系统可以动态改变 executor 的完整运行时状态——但无法将调整前后的完整快照序列持久化。

### 1.2 结构性缺口

五个具体缺口：

1. **无持久化存储** — `InMemoryEvidenceRecorder` 使用 `ConcurrentHashMap` 存储。JVM 重启后所有证据丢失。无法支持跨会话实验对比或长期数据积累。

2. **无序列化格式** — `PressureSnapshot`、`RuntimeObservation`、`ObservedSnapshot` 均为纯内存对象，无 JSON 或二进制序列化。`AcquisitionJsonWriter` 仅处理聚合摘要类型（`RunManifest`、`PressureSummary`、`ReplaySummary`），不处理原始快照。

3. **无录制会话生命周期** — `EvidenceRecorder` 接口只有 `record()`、`snapshots()`、`runIds()` 三个方法。无 start/stop 概念、无会话元数据、无会话边界。

4. **无自主采样** — 只有 `ManualPressureSampler`，需要调用者提供 `RuntimeObservation`。`ManagedExecutorScenarioRunner` 在 step 执行循环中手动构建 observation 并调用 sampler。不存在按固定间隔自动从 live executor 读取的 `PressureSampler` 实现。

5. **CPU utilization 始终 absent** — `ManagedExecutorScenarioRunner.buildObservation()` 中 `cpuUtilization` 始终为 `MetricValue.absent()`。有字段定义但无数据来源——本版本不解决此问题（DFR-01），但 `LivePressureSampler` 设计预留扩展点。

### 1.3 为什么是现在

- 三个动态配置维度全部完成，持久化存储是离线分析的前提
- `AcquisitionJsonWriter` 和 `AcquisitionReportPaths` 已提供可复用的序列化基础设施（v0.6.0）
- `ManagedExecutorScenarioRunner` 已实现从 live executor 读取 7 个指标（v0.8.0）——`LivePressureSampler` 将此逻辑提取为独立组件
- 自主采样是长时间运行实验（超过单次 scenario 生命周期）的前提
- v0.10.0 retrospective 规则 #1 "JDK 原生支持优先检查"已固化——本版本不涉及新的 executor mutation，无 JDK API 评估需求

## 2. 范围

### 2.1 范围内

- `FileBackedEvidenceRecorder`：实现 `EvidenceRecorder` 接口，JSON Lines 文件持久化
- `PressureSnapshot` JSON 序列化/反序列化（通过 `AcquisitionJsonWriter` 扩展）
- `RuntimeObservation` JSON 序列化/反序列化（含 `MetricValue` 的 JSON 表示）
- `ObservedSnapshot` JSON 序列化/反序列化
- `RecordingSession`：录制会话生命周期管理
- `RecordingSessionMetadata` record：会话元数据
- `LivePressureSampler`：实现 `PressureSampler`，`ScheduledExecutorService` 定时采样
- `LivePressureSamplerConfig` record：采样配置
- `AcquisitionJsonWriter` 扩展（新增 3 个类型的序列化方法）
- `AcquisitionReportPaths` 扩展（新增 evidence/session 文件路径）
- `ManagedExecutorScenarioRunner` 扩展：支持注入 `LivePressureSampler` 作为替代采样路径
- `FileBackedEvidenceRecorder` 的并发安全
- 现有 535 测试零回归

### 2.2 范围外

- 跨 run 证据聚合
- 证据压缩/归档
- 保留策略强制执行（`RetentionRecord` 已有策略描述，执行延后）
- CPU utilization 真实数据源
- 数据库/远程存储
- 自定义序列化格式（仅 JSON）
- 新的 executor mutation 能力
- CLI entry

### 2.3 术语

| 术语 | 定义 |
|---|---|
| FileBackedEvidenceRecorder | 实现 EvidenceRecorder，将 ObservedSnapshot 追加写入 JSON Lines 文件（每行一个 JSON 对象），内存中保留 CopyOnWriteArrayList 缓冲以支持 snapshots() 查询 |
| RecordingSession | 录制会话：sessionId + runId + executorConfig 快照 + startTime + endTime + sampleCount + status |
| RecordingSessionMetadata | 不可变 record，携带会话的完整生命周期信息 |
| LivePressureSampler | 实现 PressureSampler，内部使用 ScheduledExecutorService 按固定间隔从 ManagedExecutor 读取状态并采样 |
| JSON Lines | 每行一个完整 JSON 对象的文本格式，支持流式追加，广泛应用于日志和 metrics 管道 |
| LivePressureSamplerConfig | 不可变 record：pollIntervalMs（默认 1000ms）、autoStart、sessionId |

## 3. IR 条目草案

### IR-v0.11-001 FileBackedEvidenceRecorder

系统需要 `FileBackedEvidenceRecorder` 将 `ObservedSnapshot` 持久化到磁盘。

候选验收语义：

- 实现 `EvidenceRecorder` 接口，保持与 `InMemoryEvidenceRecorder` 完全相同的接口契约
- 构造参数：`Path outputDir`、`AcquisitionJsonWriter jsonWriter`
- 每个 runId 对应一个 JSON Lines 文件：`outputs/reports/v0.11.0/evidence-<runId>.jsonl`
- `record(ObservedSnapshot)` 必须：
  - 将 snapshot 序列化为单行 JSON，追加写入对应 runId 的文件
  - 同时添加到内存缓冲（`ConcurrentHashMap<String, CopyOnWriteArrayList<ObservedSnapshot>>`）支持 `snapshots()` 查询
- `snapshots(String runId)` 必须返回该 run 的所有已录制快照（按插入顺序）
- `runIds()` 必须返回所有已录制的 runId 集合
- `flush(String runId)` 强制将缓冲刷入磁盘
- 线程安全：多线程并发 `record()` 同一 runId 时，文件追加和内存缓冲均安全
- 不得修改 `EvidenceRecorder` 接口签名

优先级：P0。

### IR-v0.11-002 Snapshot JSON 序列化

系统需要将 `PressureSnapshot`、`RuntimeObservation`、`ObservedSnapshot` 序列化为 JSON，并支持从 JSON 反序列化。

候选验收语义：

- 扩展 `AcquisitionJsonWriter`，新增方法：
  - `writePressureSnapshot(PressureSnapshot)` → JSON 字符串
  - `readPressureSnapshot(String json)` → `PressureSnapshot`
  - `writeRuntimeObservation(RuntimeObservation)` → JSON 字符串
  - `readRuntimeObservation(String json)` → `RuntimeObservation`
  - `writeObservedSnapshot(ObservedSnapshot)` → JSON 字符串
  - `readObservedSnapshot(String json)` → `ObservedSnapshot`
- `PressureSnapshot` JSON 格式：6 个字段（timestamp ISO-8601, activeThreads, poolSize, queueSize, completedTaskCount, cpuUtilization）
- `RuntimeObservation` JSON 格式：9 个字段，每个 `MetricValue` 表示为 `{"status": "PRESENT", "value": <json-value>}` 或 `{"status": "ABSENT"}`
- `ObservedSnapshot` JSON 格式：`{"runId": "...", "snapshot": {...}, "observation": {...}}`
- 往返序列化保证：`readXxx(writeXxx(obj)).equals(obj)` 对所有合法输入为 true
- 反序列化不完整/无效 JSON 时必须抛出明确异常（不返回 null 或部分对象）
- `MetricValue.Present<T>` 反序列化时需根据 value 的 JSON 类型推断泛型类型（整数 → Integer，浮点 → Double，字符串 → String）

优先级：P0。

### IR-v0.11-003 RecordingSession 与 RecordingSessionMetadata

系统需要录制会话生命周期管理，为每次持久化录制提供明确的开始/结束边界和元数据。

候选验收语义：

- `RecordingSession` 类必须包含：
  - `sessionId`: String（唯一标识，构造时生成）
  - `runId`: String（关联的 experiment run）
  - `executorConfig`: `ManagedExecutorConfig`（会话开始时的配置快照，不可变）
  - `startedAt`: `Instant`
  - `status`: `SessionStatus` enum（`ACTIVE` / `CLOSED`）
- `RecordingSession.incrementSnapshotCount()` 每次 record 时递增内部计数器
- `RecordingSession.close()` 必须：
  - 设置 `closedAt = Instant.now()`
  - 设置 `status = CLOSED`
  - 返回 `RecordingSessionMetadata`（包含所有字段的快照）
  - 对已 CLOSED 的 session 再次调用 close() 抛出 `IllegalStateException`
- `RecordingSessionMetadata` record：
  - `sessionId`, `runId`, `executorConfig`, `startedAt`, `closedAt`, `snapshotCount`, `status`
  - 不可变
- `FileBackedEvidenceRecorder` 内部管理 session：
  - `startSession(String runId, ManagedExecutorConfig config)` → 创建 ACTIVE session
  - `closeSession(String runId)` → 关闭 session，返回 metadata，同时将 metadata 序列化为 JSON 写入 `outputs/reports/v0.11.0/session-<runId>.json`
  - 对已存在 ACTIVE session 的 runId 再次调用 `startSession()` 抛出 `IllegalStateException`
  - `closeSession()` 自动调用 `flush()`
- 不得修改 `EvidenceRecorder` 接口（会话管理是 `FileBackedEvidenceRecorder` 的扩展，非接口要求）

优先级：P0。

### IR-v0.11-004 LivePressureSampler

系统需要 `LivePressureSampler` 按可配置的固定间隔从 `ManagedExecutor` 自主读取状态并采样。

候选验收语义：

- 实现 `PressureSampler` 接口（保持与 `ManualPressureSampler` 相同的接口契约）
- 构造参数：`ManagedExecutor executor`、`EvidenceRecorder recorder`、`SnapshotAssembler assembler`、`LivePressureSamplerConfig config`
- `start(String runId)` 必须：
  - 使用 `ScheduledExecutorService` 按 `config.pollIntervalMs()` 间隔触发采样
  - 每次触发：从 `ManagedExecutor` 读取当前状态 → 构建 `RuntimeObservation`（复用 `ManagedExecutorScenarioRunner.buildObservation()` 的读取逻辑：activeCount/poolSize/queueSize/completedTaskCount/keepAliveTimeSeconds/largestPoolSize/taskCount 设为 present，cpuUtilization 设为 absent）→ 调用 `assembler.assemble()` → 调用 `recorder.record()`
  - 对已 start 的 sampler 再次调用 `start()` 抛出 `IllegalStateException`
- `stop()` 必须：
  - 关闭 `ScheduledExecutorService`，等待当前正在执行的采样完成（`awaitTermination` 超时 10s）
  - 超时后强制 `shutdownNow()`
  - 返回 `true` 如果成功停止，`false` 如果超时强制停止
- `sample(String runId, RuntimeObservation observation, Instant at)` 方法（来自 `PressureSampler` 接口）必须仍然可用——直接委托给 `assembler.assemble()` 并写入 `recorder`，与自主调度不冲突
- `isRunning()` 返回当前是否在自主采样
- `LivePressureSamplerConfig` record：
  - `pollIntervalMs`: long（默认 1000ms，最小 100ms）
  - `autoStart`: boolean（默认 false）
  - `sessionId`: String
- 线程安全：`ManagedExecutor` 的状态读取方法是线程安全的（委托给 TPE 的 getter，均为 volatile/同步方法）
- 不得在采样过程中修改 executor 状态（只读）
- 调度使用 `scheduleWithFixedDelay()`（固定延迟），确保前一次采样完成后才调度下一次，避免采样积压

优先级：P0。

### IR-v0.11-005 ManagedExecutorScenarioRunner 集成

系统需要 `ManagedExecutorScenarioRunner` 支持注入 `LivePressureSampler` 作为替代采样路径。

候选验收语义：

- `ManagedExecutorScenarioRunner` 新增构造器重载或 Builder，支持注入 `LivePressureSampler`：
  - 若注入 `LivePressureSampler`，runner 使用自主定时采样路径
  - 若不注入（现有构造器），保持现有 step 内手动采样路径（不变）
- 注入 `LivePressureSampler` 时：
  - Phase 1 后：runner 调用 `liveSampler.start(runId)` 启动自主采样
  - Phase 3（step 执行循环）：跳过手动 `sampler.sample()` 调用（自主采样已在后台运行），但保留 step 任务的提交和执行
  - Phase 5 前：runner 调用 `liveSampler.stop()` 停止自主采样
- 自主采样路径与手动采样路径的 `ScenarioRunOutcome` 结构一致（runId, evidenceCount 等字段均有值）
- 现有所有 `ManagedExecutorScenarioRunnerTest` 测试（8 个）必须继续通过（使用手动采样路径）
- 不得修改现有公开 API 的语义

优先级：P0。

### IR-v0.11-006 端到端持久化录制验证

系统需要端到端集成测试验证完整的持久化录制和自主采样流程。

候选验收语义：

- 测试 1：持久化录制 → 关闭会话 → 从磁盘读取 → 反序列化 → 验证数据完整性
  1. 创建 `FileBackedEvidenceRecorder` 指向临时目录
  2. `startSession(runId, config)` → 录制 10 个 `ObservedSnapshot`（通过 `ManualPressureSampler`）
  3. `closeSession(runId)` → 验证 `session-<runId>.json` 文件存在且元数据正确
  4. 创建新的 `FileBackedEvidenceRecorder` 指向同一目录
  5. 调用 `snapshots(runId)` → 验证返回 10 个快照，每个字段值与原快照一致（往返序列化验证）
- 测试 2：LivePressureSampler 自主采样 + FileBackedEvidenceRecorder 集成
  1. 创建 `FileBackedEvidenceRecorder`
  2. 创建 `ManagedExecutor` + 注册
  3. 创建 `LivePressureSampler` + `start(runId)`（pollIntervalMs=200ms）
  4. 提交一些任务使 executor 有活动
  5. 运行 2 秒 → `stop()`
  6. 验证录制的快照数 >= 5（200ms 间隔，2 秒至少 5 个）
  7. 验证所有快照的 runId 一致，时间戳单调递增
- 测试 3：ManagedExecutorScenarioRunner + LivePressureSampler 集成
  1. 创建 `FileBackedEvidenceRecorder` + `LivePressureSampler`
  2. 将 LivePressureSampler 注入 `ManagedExecutorScenarioRunner`
  3. 运行 scenario → 验证 `ScenarioRunOutcome.evidenceCount > 0`
  4. 从磁盘读取快照，验证与 outcome 一致
- 测试 4：并发写入 FileBackedEvidenceRecorder
  1. 多个线程同时调用 `record()` 写入同一 runId
  2. 验证所有快照都被记录，无数据丢失、无文件损坏
- 测试 5：LivePressureSampler.stop() 正确停止
  1. `start()` → 等待 500ms → `stop()`
  2. 记录当前 snapshot 数量
  3. 等待 1 秒 → 验证 snapshot 数量不变（确认调度已停止）
- 测试 6：LivePressureSampler 二次 start 检测
  1. `start()` → `start()` → 验证抛出 `IllegalStateException`
- 所有测试的 `@AfterEach` 必须：删除临时目录下的所有文件
- 现有 535 测试零回归

优先级：P0。

## 6. 风险和延期项

| 风险 | 当前判断 | 后续触发条件 |
|---|---|---|
| MetricValue JSON 反序列化的类型推断 | P2 风险 | `MetricValue<T>` 的 `T` 在反序列化时需从 JSON value 类型推断（整数→Integer，浮点→Double）。当前所有 `MetricValue` 的使用都是明确类型（`MetricValue<Integer>` 等），不会出现类型混淆。但如果有两个字段都是 `Integer` 但在不同场景下需要不同精度，可能出问题——当前场景不存在此问题 |
| LivePressureSampler 与 step 内任务提交的时序 | P2 风险 | 如果 `LivePressureSampler` 在 runner 的 step 之间采样（当前 step 刚提交任务但任务尚未开始执行），`activeCount` 可能为 0。这不是 bug——采样器按固定间隔读取当前状态，精确反映了瞬时值。不影响数据正确性 |
| FileBackedEvidenceRecorder 文件 I/O 错误处理 | P1 风险 | 磁盘满、权限不足等 I/O 错误可能导致 `record()` 失败。IR 要求 `record()` 在 I/O 失败时抛出 unchecked exception（保留失败证据）。SR 需定义异常类型和恢复策略 |
| LivePressureSampler 与 executor shutdown 的时序 | P1 风险 | 如果 `LivePressureSampler` 正在采样时 executor 被外部 shutdown，采样读到的状态应该是 post-shutdown 状态（activeCount=0 等），不应抛异常。SR 需定义 `buildObservation()` 在 executor shutdown 后的行为 |
| AcquisitionJsonWriter 扩展的 API 膨胀 | P2 风险 | 当前 `AcquisitionJsonWriter` 只处理 `Map<String, Object>` 和列表/原始类型。新增 6 个类型特定的方法会显著扩大其 API 表面积。SR 需考虑是否将快照序列化拆分为独立类（如 `SnapshotJsonSerializer`）以保持 `AcquisitionJsonWriter` 的职责单一 |
