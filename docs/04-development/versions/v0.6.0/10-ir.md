# v0.6.0 IR 需求分析草案

## Header

- Document type: IR requirement draft
- Version name: `v0.6.0`
- Status: `DRAFT`
- Current phase: `PRESSURE_DATA_ACQUISITION_REQUIREMENT_DRAFT`
- Authoring date: `2026-06-06`
- Current conclusion: 本文只定义压测数据获取需求，不授权 SR、OpenSpec change、Java 实现或实际压测执行

## 1. 需求来源

### 1.1 用户确认方向

用户明确要求开始 `v0.6.0` 压测数据获取需求设计，基于 superspec / 管理变更流程推进，先输出 IR 草案和实验数据获取计划，不实现新业务代码。

### 1.2 项目现状

当前已交付能力提供了数据获取链路的基础：

| 已交付能力 | 可复用输入 | 当前限制 |
| --- | --- | --- |
| `scenario-runner-and-baseline` | steady/ramp/burst deterministic scenario、fixed baseline executor、run outcome | 非 adaptive，不产生 scale decision 或 adjustment |
| `metrics-snapshot-and-recording` | pressure snapshots、append-only evidence、summary | 只观察，不评价 policy，不 mutation |
| `adaptive-policy-and-control-gate` | threshold policy、control gate、reasoned decision、`ScaleDecision` conversion | 不接入 scenario runner 或 executor mutation |
| `offline-replay-and-readiness-gate` | replay validation、summary、sensitivity、readiness assessment | 只读分析，不证明 runtime mutation 收益 |
| `executor-adapter-and-adjustment-evidence` | adjustment command、safety gate、in-memory probe、adjustment evidence | 不接入生产 executor，不做 queue resizing |

当前缺口：

- 缺少标准化压测数据获取需求。
- 缺少固定实验矩阵。
- 缺少数据质量门禁。
- 缺少 baseline pressure 与 policy replay 输入之间的追踪规则。
- 缺少“何时数据足够支持下一阶段设计”的判定标准。
- 缺少“何时数据不足，必须停止”的阻塞规则。

### 1.3 需求判断

`v0.6.0` 不应直接进入 executor mutation、queue resizing 或新控制器实现。合理下一步是先定义并获取可复现的压力数据，以便：

- 证明现有 baseline scenario 是否能产生足够区分度的 pressure pattern；
- 让 offline replay 和 threshold sensitivity 有可靠输入；
- 让 readiness assessment 不再只依赖少量或偶然样本；
- 为后续 runtime adjustment 或 queue resizing SR 提供数据依据；
- 避免在没有实验数据的情况下扩展运行时突变能力。

## 2. 范围

### 2.1 范围内

- 压测数据获取需求。
- 实验矩阵设计。
- baseline pressure evidence 需求。
- offline replay 输入质量需求。
- policy config sensitivity 输入需求。
- 数据质量门禁。
- 报告输出和证据路径约定。
- 后续 OpenSpec change 候选能力识别。

### 2.2 范围外

- Java 源码实现。
- 测试代码实现。
- 实际压测执行。
- 自动化 runner / CLI / report writer 实现。
- executor mutation。
- queue resizing。
- 生产 `ThreadPoolExecutor` 集成。
- closed-loop controller 或 scheduler。
- 新依赖、数据库、REST/API/UI。
- 任何 throughput improvement claim。

### 2.3 术语

| 术语 | 定义 |
| --- | --- |
| Pressure data acquisition | 受控采集 baseline scenario pressure snapshots、run summary 和后续 replay 输入的过程 |
| Baseline pressure evidence | 未进行 adaptive adjustment 的 scenario run pressure snapshot 和 summary |
| Experiment matrix | scenario profile、seed、step count、work units、baseline preset、policy config、run repetition 的组合 |
| Data quality gate | 判定数据是否可进入 replay、sensitivity、readiness 或后续 SR 的门禁 |
| Controlled report artifact | 可审阅、受控大小、可版本化的摘要报告，不包含未经压缩的大型原始数据 |
| Candidate next capability | IR/SR 后可能创建的 superspec OpenSpec change，不在当前 IR 阶段创建 |

## 3. IR 条目草案

### IR-v0.6-001 可复现实验矩阵

系统需要定义可复现的 pressure data acquisition 实验矩阵。

候选验收语义：

- 必须覆盖 `STEADY`、`RAMP`、`BURST` 三类 scenario profile。
- 每个 profile 必须定义固定 seed、step count、base work units 和 run repetition。
- 每组实验必须记录 baseline executor preset，包括 core pool size、maximum pool size、queue capacity 和 baseline policy id。
- 不得在矩阵中引入 adaptive executor mutation 或 queue resizing。
- 每个 run 必须能通过 run id 追踪到 scenario definition、baseline preset 和采样 evidence。

优先级：P0。

### IR-v0.6-002 baseline pressure evidence

系统需要定义 baseline pressure evidence 的最小字段和完整性要求。

候选验收语义：

- 每个 run 至少需要记录 run metadata、scenario id、scenario profile、seed、baseline preset、start/end timestamp 或等价 deterministic time bounds。
- 每个 run 必须记录按时间顺序排列的 pressure snapshots。
- snapshot 必须保留 run id、sample timestamp、active count、pool size、queue size、completed task count 或明确的 unavailable marker。
- evidence 必须是 append-only，不得覆盖同一 run 的历史样本。
- evidence 不得包含 runtime adjustment evidence 或 offline replay evidence 字段。

优先级：P0。

### IR-v0.6-003 数据质量门禁

系统需要定义数据进入 replay 和后续设计前的质量门禁。

候选验收语义：

- 每个 run snapshot 数量必须达到最小阈值，草案默认 `sampleCount >= 3`，SR 可提高阈值。
- 同一 run 内 snapshot `runId` 必须一致。
- snapshot timestamp 必须非降序。
- 每个 required profile 至少有一个有效 run，草案建议每个 profile 至少 `3` 个重复 run。
- 若任一 required profile 缺失、snapshot 数量不足、run id 不一致或时间戳无序，数据集 MUST 标记为 `INVALID_FOR_READINESS`。
- 数据质量门禁失败时不得进入 executor mutation 或 queue resizing SR。

优先级：P0。

### IR-v0.6-004 policy replay 输入映射

系统需要定义 baseline pressure evidence 如何进入 offline policy replay。

候选验收语义：

- replay 输入必须从 baseline pressure evidence 派生，不能从 runtime adjustment evidence 派生。
- replay 必须保留 scenario profile 和 run metadata。
- replay policy config 至少覆盖既有 `default`、`conservative`、`aggressive` 三组配置。
- replay decision timestamp 必须来自 source snapshot timestamp。
- replay 输出必须可追踪回 source snapshot index。

优先级：P0。

### IR-v0.6-005 threshold sensitivity 与 readiness 判定数据要求

系统需要定义 threshold sensitivity 和 readiness assessment 所需的数据要求。

候选验收语义：

- 数据集必须支持按 profile 聚合 action counts、gate counts、hold ratio、capped ratio、direction flip count 和 alternating streak max。
- readiness 只能基于通过质量门禁的数据集。
- `READY`、`READY_WITH_RISK`、`NOT_READY` 结论必须记录触发原因和数据来源。
- 若数据集只覆盖单一 profile，不得声明对整体 mutation readiness 的结论。

优先级：P0。

### IR-v0.6-006 报告输出与 evidence hygiene

系统需要定义压测数据报告输出和 evidence hygiene。

候选验收语义：

- 报告目录草案为 `outputs/reports/v0.6.0/`。
- 报告必须区分 raw evidence、summary artifact、readiness artifact 和 run manifest。
- 默认纳入版本控制的只能是最小必要摘要或 manifest，不得误提交大型 raw evidence。
- 报告命名必须包含 version、scenario profile、run group 或 policy config label。
- 每个报告必须记录生成输入、命令、时间、数据质量状态和 residual risk。

优先级：P1。

### IR-v0.6-007 后续能力分解边界

系统需要定义从 v0.6.0 IR/SR 到后续 OpenSpec change 的边界。

候选验收语义：

- IR 阶段不得创建 OpenSpec change。
- 若后续需要自动化压测 runner 或 report writer，必须在 SR 闭环后基于 `schema: superspec` 创建新 change。
- 后续 change 名称草案为 `pressure-data-acquisition-and-baseline`，但当前 IR 不授权创建。
- executor mutation、queue resizing、closed-loop controller 必须在数据质量和 readiness 结论满足门槛后单独设计。

优先级：P0。

## 6. 风险和延期项

| 风险 | 当前判断 | 后续触发条件 |
| --- | --- | --- |
| 现有 scenario runner 可能不足以产生真实压力分布 | P1 风险 | SR 必须确认是否需要新 runner 或更高 workload 控制 |
| 当前 evidence 数量过少导致 readiness 偶然性 | P0 阻塞风险 | 必须定义 profile/run/sample 最小覆盖 |
| raw evidence 体积过大污染仓库 | P1 风险 | 必须定义 summary-only versioned artifact 策略 |
| 压测环境差异影响可比性 | P1 风险 | 必须记录 JDK、OS、CPU、运行命令和环境摘要 |
| 把 offline replay 结论误当 runtime mutation 收益 | P0 风险 | 文档必须禁止 throughput improvement claim |
| 数据获取需求被误解为实现授权 | P0 风险 | current-state 必须明确不授权 Java 实现或 OpenSpec change |

## 9. 当前结论

`v0.6.0` IR 草案已定义压测数据获取的需求方向、实验矩阵、数据质量门禁、replay/readiness 输入要求和 evidence hygiene。本文不能授权实现、压测执行或 OpenSpec change；下一步是独立 IR review。
