- Current conclusion: functional design draft only; not an OpenSpec change and not an implementation authorization

## 1. 设计目标

`v0.6.0` SR 将已闭环 IR 转成后续 OpenSpec change 可执行的功能设计。目标不是直接实现压测，而是定义一个受控、可审阅、可复现的 pressure data acquisition capability，使后续数据获取、offline replay、sensitivity comparison 和 readiness assessment 使用同一套证据约束。

本设计只描述下一步能力边界，不授权 Java 实现，不授权实际压测执行，不授权 OpenSpec change 创建。

## 2. 设计结论

- `v0.6.0` 的第一批后续 change 候选应聚焦 `pressure-data-acquisition-and-baseline`，而不是 executor mutation。
- 数据获取能力必须以 `scenario-runner-and-baseline`、`metrics-snapshot-and-recording`、`adaptive-policy-and-control-gate`、`offline-replay-and-readiness-gate` 为输入基础。
- 压测数据获取必须生成受控 run manifest、pressure summary、replay summary 和 readiness summary，不得默认把大型 raw evidence 当成版本化交付物。
- 数据质量门禁必须在任何 replay 或 readiness 结论之前执行。
- `v0.6.0` 的目标是可复现的数据证据，而不是 throughput improvement claim。
- 后续 runtime mutation 或 queue resizing 仍然是下一阶段候选，不属于本 SR 的授权范围。

## 3. 模块边界

| 模块 | 职责 | 禁止事项 |
| --- | --- | --- |
| `experiment.scenario` | 提供 deterministic scenario definition、profile 和 run plan 输入 | 不执行 pressure acquisition 工作流本身，不引入 adaptive behavior |
| `experiment.metrics` | 继续负责 pressure snapshot collection、append-only recording、summary generation | 不做 replay、不做 readiness judgement、不做 mutation |
| `experiment.policy` | 继续负责 threshold policy evaluation 和 control gate | 不直接承担 pressure acquisition orchestration |
| `experiment.analysis` | 继续负责 offline replay、summary aggregation、threshold sensitivity、readiness assessment | 不执行 runtime mutation，不创建 pressure acquisition artifacts |
| `experiment.acquisition`（候选） | 后续 change 候选层；负责受控 acquisition manifest、采样调度、summary/report artifact 组织 | 不实现 executor mutation、不做 queue resizing、不接入生产 `ThreadPoolExecutor` |

## 4. 设计输入与输出

### 4.1 输入基线

后续实现必须显式读取或接收以下输入：

- `ScenarioDefinition`
- `ScenarioPlan`
- `BaselineExecutorPreset`
- `PressureSnapshot`
- `PolicyConfig`
- `ReplayReadinessRules`
- `environmentSummary`
- `commandLine`
- `runId`
- `profile`
- `seed`

### 4.2 输出基线

后续实现必须生成以下输出：

| 输出 | 说明 |
| --- | --- |
| `RunManifest` | 一次 acquisition 运行的输入签名、环境指纹和参数摘要 |
| `PressureSummary` | 按 run 聚合的 pressure snapshot 摘要 |
| `ReplaySummary` | replay decision/action/gate/oscillation summary |
| `ReadinessSummary` | readiness status、reason、blocking condition 或 accepted residual risk |
| `EvidenceIndex` | run 到 artifact 的可追踪索引 |

### 4.3 证据边界

| 证据类型 | 允许内容 | 禁止内容 |
| --- | --- | --- |
| Baseline pressure evidence | 运行时压力快照、摘要、运行元数据 | runtime adjustment evidence、queue resizing evidence |
| Replay evidence | offline replay decisions、summary、sensitivity | runtime mutation commands |
| Readiness evidence | readiness status、reason、blocking condition | runtime execution authorization |
| Raw evidence | 原始 snapshot stream | 默认 versioned large artifact、production mutation inputs |

## 5. 运行模型

### 5.1 Acquisition flow

推荐的受控数据获取流如下：

1. 固定 scenario profile、seed、step count、baseline preset。
2. 运行 deterministic scenario，采集 pressure snapshots。
3. 生成 run manifest 和 pressure summary。
4. 对有效 run 执行 offline policy replay。
5. 聚合 replay summary、threshold sensitivity 和 readiness summary。
6. 应用数据质量门禁。
7. 输出受控报告 artifact。
8. 若数据不足，阻塞后续 SR 或 change 提案。

### 5.2 执行边界

- 采样必须只读，不得修改 executor 状态。
- replay 必须只读，不得驱动 runtime mutation。
- report writer 必须只输出受控摘要，不得默认复制大型 raw evidence。
- readiness 的输出必须明确“可用于后续设计”还是“仍需补证据”。

## 7. 数据质量与门禁

SR 必须把 IR 中定义的数据质量门禁固化成可执行的设计要求：

| 门禁 | 设计要求 |
| --- | --- |
| Required profiles | `STEADY`、`RAMP`、`BURST` 都必须存在 |
| Run repetition | 每个 profile 至少 3 个有效 run |
| Snapshot minimum | 每个 run 至少 3 个 snapshot，SR 可提高阈值 |
| Run identity | 同一 run 内所有 snapshot `runId` 一致 |
| Timestamp order | snapshot timestamp 非降序 |
| Metadata completeness | run metadata 必须包含 scenario、seed、preset、environment |
| Replay guard | `decisionCount + skippedCount == evidenceCount` |
| Raw evidence hygiene | 默认不把 raw evidence 纳入版本控制 |

## 8. 报告与输出

建议版本化输出目录：

```text

```

建议报告集合：

- run manifest
- pressure summary
- replay summary
- readiness summary
- evidence index

报告必须：

- 可按 run 追溯；
- 可按 profile 追溯；
- 可按 policy config 追溯；
- 可按 command line 和 environmentSummary 重建执行背景；
- 不默认包含大型 raw evidence。

## 9. 测试与验收策略

后续 OpenSpec change 的测试应验证：

- pressure acquisition 输入矩阵覆盖 `STEADY`、`RAMP`、`BURST`；
- run manifest、pressure summary、replay summary 和 readiness summary 字段齐全；
- 数据质量门禁在缺失 profile、无序 timestamp、run id 不一致或样本不足时阻断；
- raw evidence 默认不进入版本控制；
- replay 与 readiness 只能消费 baseline pressure evidence，不得消费 runtime adjustment evidence；
- 文档/实现不越权到 runtime mutation、queue resizing 或生产 executor 集成。

## 10. Change decomposition

SR 闭环后，建议的后续 OpenSpec change 候选：

- `pressure-data-acquisition-and-baseline`

候选范围：

- 受控 pressure acquisition manifest
- pressure summary / replay summary / readiness summary artifact
- evidence index
- data quality validator
- report hygiene

明确非范围：

- executor mutation
- queue resizing
- closed-loop controller
- 生产 `ThreadPoolExecutor` 集成
- persistence、REST/API/UI

## 11. Execution authorization

本 SR 不授权：

- Java 实现；
- OpenSpec change 创建；
- 实际压测执行；
- 新依赖；
- queue resizing；
- executor mutation；
- throughput improvement claim。

若未来需要实现本设计，必须先完成 SR review、disposition、closure verification，并由 `docs/00-project/current-state.md` 明确进入后续 change decomposition 授权状态。

## 12. 当前结论

`v0.6.0` SR 功能设计草案已定义 pressure data acquisition 的边界、输入输出、数据模型、门禁、报告和 change 候选范围。下一步是独立 SR review。
