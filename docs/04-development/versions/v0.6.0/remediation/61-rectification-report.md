# v0.6.0 补救任务整改报告

## 1. 结论

本次偏差已经纠正。整改后的补救包现在明确区分了两件事：

- 原始 `v0.6.0` 主方案已经归档，不再作为执行入口。
- `v0.6.0-remediation` 是独立的补救设计与交接包，用于处理“真实实验数据未落盘”的缺口。

当前已补齐的交付资产包括：

- 补救设计包索引
- 补救 IR / SR 闭环文档
- 补救执行任务文档
- 可直接转交给下游 agent 的 handoff note

## 2. 本次偏差

我前面把“补救路径”误写成了“主方案采集任务”，导致下游启动词仍然沿着主方案门禁去执行。

具体表现是：

- 一度把 `v0.6.0` 主线的采集计划当成执行口令。
- 没有先把补救执行包收敛成独立入口。
- 给出的交接文本没有明确锁定在 `remediation/`，导致下游仍然按照主方案门禁判断。

## 3. 根因

### 3.1 路径混淆

我把“能力闭环已完成”和“真实数据缺口待补救”混在一起，错误地向主方案靠拢。

### 3.2 入口不清

没有先把补救包整理成单独的执行资产，就直接尝试生成启动文本，导致任务语义不稳定。

### 3.3 门禁识别不足

没有始终把 `docs/00-project/current-state.md` 的 `NONE` 作为补救执行的硬前置条件，结果输出了会被门禁拦截的下游口令。

## 4. 纠正动作

- 已创建独立补救执行任务文档 `[30-execution-task.md](./30-execution-task.md)`。
- 已把补救执行入口挂回 `remediation/README.md`。
- 已把补救包的执行边界固定为：
  - 不改原始 `v0.6.0` 文档
  - 不新增 OpenSpec change
  - 不改代码和测试
  - 不做 queue resizing
  - 不接入 production `ThreadPoolExecutor`
- 已把任务语义统一为“补救执行包准备 / 授权后执行”，不再假装当前已经可以直接采集。

## 5. 当前可下发状态

现在可下发的内容是补救任务包，不是实际采集启动命令。

下游 agent 应该先做的是：

- 检查授权状态
- 确认是否仍为 `NONE`
- 若未授权，只能返回阻塞说明
- 若已授权，再按补救包执行

## 6. 后续约束

以后涉及 `v0.6.0-remediation` 时，必须先保持以下顺序：

1. 先确认授权状态
2. 再确认补救包边界
3. 最后才生成下游执行文本

不得再次把主方案口径塞进补救路径。

## 7. 最终整改结论

整改结果是可接受的，但前提是后续所有交付都必须以 `remediation/` 为唯一入口，不再回到主方案语义。

## 8. 项目层反思

- 我没有始终把仓库当前授权状态当作第一约束，导致思考重心偏向“如何继续推进任务”，而不是“当前是否允许推进”。
- 我对 `v0.6.0` 的判断一度受“能力已完成”这个事实影响，错误地把“能力闭环”当成了“补救执行条件已满足”。
- 我没有始终保持主方案与补救方案的边界，导致在写交接文本时不断回到主线语义。
- 这说明后续处理同类问题时，必须先锁定项目状态，再谈任务语义；否则即使文档完整，也可能把正确内容放在错误上下文里。

## 9. 流程层反思

- 我在流程上犯了一个顺序错误：先写了面向执行的启动词，再回头补授权与边界。
- 正确顺序应该是：
  1. 先确认 current-state 和授权边界。
  2. 再确认补救包是否已经形成独立入口。
  3. 最后才生成下游执行文本。
- 我还把“任务描述”与“可执行授权”混用了。对于这种受控流程，任务文本只能描述工作边界，不能替代授权本身。
- 如果后续还要配合其他 agent，必须把预检门禁写成任务的第一段，而不是藏在停止条件里。

## 10. 设计方案层反思

- 早期补救任务单的设计不够稳健，问题不在于内容少，而在于它对“当前不可执行”的表达不够强。
- 任务单应该显式分成两部分：
  - `preflight`：只做授权与边界确认
  - `execution`：只有授权通过后才能进入
- 我前面的写法过度强调了输出目录、文件名和数据门禁，反而弱化了最关键的前置条件：当前状态为 `NONE` 时不能执行。
- 这个设计缺陷会让下游 agent 误以为“只要照着产物清单跑就行”，从而在门禁处反复失败。
- 所以后续补救方案如果要发给弱执行 agent，必须把“不可执行条件”放在比“产物清单”更前的位置，并且用明显的阻断语句标出来。

## 11. 下一步改进计划

### 11.1 任务下发改进

- 将补救任务固定拆成两个独立文本：
  - `preflight-note`：只负责授权确认、边界确认、阻断条件确认
  - `execution-handoff`：只在授权通过后下发，包含具体采集步骤和产物清单
- 以后不再把“启动口令”和“授权检查”写在同一段里。
- 任何面向下游的任务，第一屏必须先出现 `current-state` 的判定逻辑，再出现执行内容。

### 11.2 门禁前置改进

- 在补救包中增加一个固定的“先决条件摘要”小节，字段只保留三项：
  - 当前授权状态
  - 当前允许的工作类型
  - 是否允许进入执行阶段
- 若结果为 `NONE`，则下游文本只能输出阻塞说明，不得输出采集步骤。
- 把这个前置判断作为下游任务的标准模板，后续所有同类任务复用。

### 11.3 方案结构改进

- 将补救设计文档中的顺序固定为：
  1. 问题定义
  2. 当前授权判断
  3. 范围边界
  4. 输出契约
  5. 数据门禁
  6. 执行步骤
  7. 停止条件
- 以后不允许把“文件名清单”放在“授权判断”前面。
- 任何补救方案都要明确区分：
  - 设计包
  - 执行包
  - 结果包

### 11.4 质量检查改进

- 在交付给下游前，增加一个人工自检问题清单：
  - 当前是否允许执行？
  - 是否把主方案和补救方案混写了？
  - 是否把授权检查放在第一段？
  - 是否存在任何会诱导下游直接开跑的句子？
- 若任一问题答案不清晰，则不允许发给执行 agent。

### 11.5 交付标准改进

- 下游可执行文本必须满足三个条件：
  - 可判断是否能执行
  - 可判断执行后要产出什么
  - 可判断什么时候必须停
- 若当前授权未通过，只交付 preflight，不交付 execution。
- 若授权通过，才交付 execution handoff，并附带明确的产物路径与停止条件。

### 11.6 预期产出

后续每次做同类补救任务时，至少要有以下三份可复用资产：

- `preflight-note.md`
- `execution-handoff.md`
- `dispatch-checklist.md`

当前补充形成的流程资产：

- `62-dispatch-process.md`
- `dispatch-checklist.md`

这三份资产的目标是把“是否能执行”与“怎么执行”彻底拆开，避免再次把错误任务下发给下游。
