## 1. 设计目标

本 SR 的目标是把“真实实验数据未落盘”这一问题，设计成一套可执行、可验证、可交接的补救流程。

它要回答的不是“要不要再做一个新版本”，而是：

- 真实数据要怎么补采；
- 输出要写到哪里；
- 哪些数据质量门禁必须通过；
- 补采完成后如何证明它是真的、完整的、可追溯的。

## 2. 设计结论

- 补救流程必须独立于原始 `v0.6.0` 文档存在；
- 补救输出必须落到固定目录；
- 补救产物必须包括 manifest、summary、evidence index 和必要时的 raw evidence；
- 任何真实数据补采都不得扩展为 queue resizing、production executor integration 或 closed-loop controller；
- 补救设计必须允许弱执行 agent 按步骤推进，而不是靠推断。

## 3. 模块边界

| 模块 | 职责 | 禁止事项 |
| --- | --- | --- |
| `remediation.campaign` | 定义补救活动边界、执行顺序和输出约定 | 不发明新的业务能力 |
| `remediation.data` | 定义 manifest、summary、evidence index、raw evidence 目录规则 | 不把 raw evidence 误当版本化交付物 |
| `remediation.gate` | 定义数据质量门禁与拒绝理由 | 不做 runtime mutation 判断 |
| `remediation.report` | 定义补救报告和交接摘要 | 不默认纳入新依赖或生产控制 |

## 5. 运行模型

### 5.1 Remediation flow

1. 固定 profile、seed、step count 和 baseline preset。
2. 运行数据采集。
3. 生成 manifest 与 summary。
4. 检查数据质量门禁。
5. 生成 evidence index 与补救报告。
6. 如果数据不足，阻断后续验收。

### 5.2 执行边界

- 采集必须只读。
- 报告必须可审阅。
- raw evidence 默认不版本化。
- readiness 不得隐含 runtime mutation authorization。

## 7. 数据质量与门禁

| 门禁 | 设计要求 |
| --- | --- |
| Required profiles | `STEADY`、`RAMP`、`BURST` 必须存在 |
| Run repetition | 每个 profile 至少 3 个有效 run |
| Snapshot minimum | 每个 run 至少 3 个 snapshot |
| Timestamp order | timestamp 非降序 |
| Run identity | 同一 run 内 `runId` 一致 |
| Metadata completeness | scenario、seed、preset、environment 完整 |
| Evidence traceability | `EvidenceIndex` 必须可追踪到 run |
| Raw evidence hygiene | 默认不入版本控制 |

建议报告集合：

## 9. 测试与验收策略

后续执行应验证：

- 补救流程的 output 契约完整；
- 数据质量门禁在缺失 profile / 样本不足 / 时间戳异常时阻断；
- raw evidence 默认不版本化；
- report 可追溯到 run；
- 补救流程不扩大到 queue resizing 或生产 executor 集成。

## 10. Change decomposition

若后续需要执行补救流程，建议作为独立 bounded change 分解，而不是改写原始 v0.6.0 文档。

候选 scope：

- remedial pressure acquisition manifest
- pressure summary / readiness summary / evidence index
- data quality validator
- report hygiene

非范围：

- executor mutation
- queue resizing
- closed-loop controller
- production `ThreadPoolExecutor` integration

## 11. Execution authorization

本 SR 不授权：

- Java 实现；
- OpenSpec change 创建；
- 实际补救采集执行；
- 新依赖；
- queue resizing；
- executor mutation。

## 12. 当前结论

这是一套独立、完整、可执行的补救设计，但它仍然只是设计，不是执行授权。
