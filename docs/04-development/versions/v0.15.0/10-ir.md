# v0.15.0 IR Requirements Analysis

## Header

- Document type: IR requirement draft
- Version name: `v0.15.0`
- Status: `READY_FOR_REVIEW` — draft complete, pending independent review
- Current phase: `IR_DRAFT`
- Authoring date: `2026-06-17`
- Current conclusion: This document defines multi-executor coordination and closed-loop validation requirements. It does not authorize SR, OpenSpec change, or Java implementation.

## 1. Requirements Source

### 1.1 Project Current State

v0.14.0 delivered autonomous closed-loop adjustment for a single `ManagedExecutor`. The system can now:
- Classify pressure states across 6 states with confidence scores (v0.13.0)
- Score and rank multiple threshold policies (v0.13.0)
- Run a closed control loop: sample → classify → score → select → adjust → observe (v0.14.0)
- Detect and prevent oscillation in adjustment patterns (v0.14.0)
- Record adjustment history and calibrate scoring weights from feedback (v0.14.0)

857 tests pass with 0 failures. The single-executor closed-loop is stable and validated.

Two structural gaps were explicitly deferred as v0.14.0 DFR-01 and DFR-04:

1. **No multi-executor coordination** — Each `AdjustmentLoop` runs independently. When multiple executors share a resource pool (total threads, memory), independent loops can conflict — e.g., two loops simultaneously scale up, exceeding shared limits. There is no mechanism to coordinate adjustments across executors.

2. **No empirical validation** — The closed-loop can run autonomously, but we have not proven it outperforms alternatives. v0.12.0's comparison infrastructure (`ComparableScenarioRunner`, `NormalizedComparisonMetrics`, `ComparisonReportArtifact`) has been idle since delivery. No controlled experiment compares closed-loop against static-policy and no-adjustment baselines.

### 1.2 Structural Gaps

Five specific gaps that v0.15.0 must address:

1. **No group abstraction** — There is no way to declare "these three executors belong together and share resources." The `ExecutorRegistry` stores executors by name but has no grouping concept. Missing: `ExecutorGroup` that associates multiple `ManagedExecutor` instances under a shared identity and resource budget.

2. **No coordination mechanism** — When two `AdjustmentLoop` instances both decide to scale up, their decisions are applied independently through separate `ExecutorAdjustmentAdapter` instances. Neither loop knows about the other's pending adjustment or the total resource consumption. Missing: `GroupCoordinator` that intercepts decisions, evaluates them against a shared `ResourceBudget`, and resolves conflicts.

3. **No resource budgeting** — Each executor's `maxPoolSize` is set independently. There is no enforcement that `sum(executor.maxPoolSize) <= totalAvailableThreads`. Missing: `ResourceBudget` that tracks total limits and per-executor allocation, with atomic reserve/release operations.

4. **No prioritization** — When resources are constrained, there is no way to specify which executor should get priority. A background-task executor could starve a request-processing executor. Missing: `AdjustmentPriority` that enables higher-priority executors to preempt lower-priority ones.

5. **No closed-loop validation** — The system can run closed-loop but cannot answer: "Is closed-loop better than the best static policy? By how much? Is the difference statistically significant?" v0.12.0 comparison infrastructure exists but has never been used to validate closed-loop outcomes. Missing: `ClosedLoopValidationRunner` that executes 3-way comparison (closed-loop vs static-policy vs baseline) and produces statistically-validated evidence.

### 1.3 Why Now

- v0.14.0 DFR-01 (multi-executor coordination) and DFR-04 (cross-validation) explicitly deferred to v0.15.0
- Single-executor closed-loop is stable (857 tests, 0 failures, 0 known defects)
- Multiple `AdjustmentLoop` instances can already run concurrently in the same JVM — they just don't coordinate. Coordination is the safety mechanism that prevents their independent decisions from conflicting.
- v0.12.0 comparison infrastructure was designed for exactly this validation use case — it has been waiting for a consumer.
- Without coordination, deploying closed-loop to multiple executors is unsafe. Without validation, the closed-loop feature lacks empirical justification.
- The decorator pattern (`CoordinatedAdjustmentAdapter` wrapping `ExecutorAdjustmentAdapter`) allows coordination to be added without modifying v0.14.0 components — minimizing regression risk.

| Term | Definition |
|---|---|
| ExecutorGroup | A named collection of ManagedExecutors that share a resource budget and are coordinated together |
| GroupCoordinator | Centralized interceptor that evaluates pending adjustment decisions against the shared resource budget and resolves conflicts |
| ResourceBudget | Tracks total resource limits (max threads, max queue capacity) and per-executor allocation |
| AdjustmentPriority | Enum (CRITICAL/HIGH/NORMAL/LOW) assigned to each executor; determines resource allocation precedence |
| Preemption | When a higher-priority executor claims resources currently allocated to a lower-priority executor |
| GroupLoopOrchestrator | Manages the lifecycle of multiple AdjustmentLoop instances as a coordinated group |
| Cross-executor oscillation | Oscillation pattern spanning multiple executors (e.g., A scales up while B scales down, repeatedly) |

| Closed-loop validation | 3-way comparison experiment: closed-loop adjustment vs best static policy vs no-adjustment baseline |

| ValidationComparisonReport | Side-by-side comparison of metrics across all three modes with statistical significance tests |
| Statistical significance | Paired t-test with Cohen's d effect size; p < 0.05 threshold |
| Cooldown | Per-executor cooldown from v0.14.0 SafetyGate continues to operate independently |
| Group health | Aggregated status of all loops in a group, including per-executor pressure states and budget utilization |
| Fail-open | When coordinator is unavailable (timeout), allow uncoordinated adjustment (vs fail-closed: reject) |

## 3. IR Entries

### IR-v0.15-001 ExecutorGroup and ExecutorGroupConfig

System needs `ExecutorGroup` to associate multiple `ManagedExecutor` instances under a shared identity and `ExecutorGroupConfig` to define group-level parameters.

Candidate acceptance semantics:

- `ExecutorGroup` class:
  - Constructor: `ExecutorGroup(ExecutorGroupConfig config, List<ManagedExecutor> members, ResourceBudget budget)`
  - `getConfig()` returns `ExecutorGroupConfig`
  - `getMembers()` returns unmodifiable `List<ManagedExecutor>`
  - `getBudget()` returns `ResourceBudget`
  - `getCoordinator()` returns `GroupCoordinator` (created internally or injected)
  - `getHistory()` returns `GroupCoordinationHistory`
  - `size()` returns member count
  - `contains(String executorId)` checks membership
- `ExecutorGroupConfig` record fields:
  - `groupId`: `String` — unique group identifier, non-blank
  - `maxTotalThreads`: `int` — sum of all executor maxPoolSizes cannot exceed this, >= 1
  - `maxTotalQueueCapacity`: `int` — sum of all executor queue capacities cannot exceed this, 0 = unbounded
  - `defaultPriority`: `AdjustmentPriority` — priority for members without explicit priority, default NORMAL
  - `memberPriorities`: `Map<String, AdjustmentPriority>` — executorId → priority, empty by default
  - `coordinationTimeoutMs`: `long` — max wait for coordination decision, >= 100, default 5000
  - `failOpen`: `boolean` — if true, uncoordinated adjustment allowed when coordinator unavailable, default false
- `ExecutorGroupConfig` static factory: `defaults(String groupId, int maxTotalThreads)` returns config with sensible defaults
- Config validation in compact constructor: all constraints checked at construction time
- Member list is validated at group construction: must not be empty, no duplicate executorIds
- **Group construction budget validation** (IR disposition P1-03):
  - `sum(member.getCorePoolSize()) <= config.maxTotalThreads()` — if violated, throw `IllegalArgumentException` with details (which executors exceed, by how much)
  - If `config.maxTotalQueueCapacity() > 0`: `sum(member.getQueueCapacity()) <= config.maxTotalQueueCapacity()` — same validation for queues
  - Queue budget is construction-time only (queue capacity cannot change at runtime)
- Package: `experiment.coordination`

Priority: P0.

### IR-v0.15-002 ResourceBudget

System needs `ResourceBudget` to track total resource limits and per-executor allocation with thread-safe reserve/release operations.

Candidate acceptance semantics:

- `ResourceBudget` class:
  - Constructor: `ResourceBudget(int maxTotalThreads, int maxTotalQueueCapacity)`
  - `maxTotalThreads >= 1`, `maxTotalQueueCapacity >= 0` (0 = unbounded queue, no enforcement)
- Query methods:
  - `availableThreads()`: `int` — `maxTotalThreads - sum(currentAllocations)`
  - `availableQueueCapacity()`: `int` — `maxTotalQueueCapacity - sum(currentQueueAllocations)`, returns `Integer.MAX_VALUE` if `maxTotalQueueCapacity == 0`
  - `allocatedThreads(String executorId)`: `int` — current allocation for executor, 0 if not allocated
  - `allocatedQueueCapacity(String executorId)`: `int`
  - `getThreadAllocations()`: `Map<String, Integer>` — read-only snapshot (defensive copy)
  - `totalAllocatedThreads()`: `int`
- Mutating methods (thread-safe, synchronized):
  - `reserve(String executorId, int threadDelta)`: reserves `threadDelta` threads for executor. Throws `IllegalStateException` if `threadDelta > availableThreads()`. `threadDelta` may be negative (scale-down)
  - `release(String executorId, int threadDelta)`: releases `threadDelta` threads back to budget. `threadDelta >= 0`
  - Note: Queue capacity is immutable at runtime (set at executor construction). `maxTotalQueueCapacity` is validated at group construction time only; no runtime reserve/release for queue.
- Invariants (always true after any operation):
  - `sum(threadAllocations.values()) <= maxTotalThreads`
  - Each individual allocation >= 0
  - `availableThreads() >= 0`
- `reserve()` and `release()` must be atomic with respect to each other
- Thread-safe: multiple loop threads and coordinator thread may call concurrently
- No external dependencies, no file I/O

Priority: P0.

### IR-v0.15-003 AdjustmentPriority

System needs `AdjustmentPriority` enum for assigning resource allocation precedence to executors.

Candidate acceptance semantics:

- `AdjustmentPriority` enum values: `CRITICAL(4)`, `HIGH(3)`, `NORMAL(2)`, `LOW(1)`
- `canPreempt(AdjustmentPriority other)`: returns true if `this.level > other.level`
- `getLevel()`: returns numeric level (1-4)
- Preemption rules:
  - CRITICAL can preempt HIGH, NORMAL, LOW
  - HIGH can preempt NORMAL, LOW
  - NORMAL can preempt LOW
  - LOW cannot preempt anyone
- Equal priority executors use first-come-first-served (arrival order within the coordination cycle)
- Default priority for unconfigured executors: `NORMAL`
- Priority is assigned per executor in `ExecutorGroupConfig.memberPriorities`
- Package: `experiment.coordination`

Priority: P0.

### IR-v0.15-004 GroupCoordinator and GroupCoordinationResult

System needs `GroupCoordinator` to intercept adjustment decisions, evaluate them against shared budget, and resolve conflicts by priority.

Candidate acceptance semantics:

- `GroupCoordinator` class:
  - Constructor: `GroupCoordinator(ExecutorGroupConfig config, ResourceBudget budget, GroupCoordinationHistory history, CrossExecutorOscillationDetector crossDetector, Map<String, ExecutorAdjustmentAdapter> adapters)`
  - `coordinate(ScaleAdjustmentCommand command, ManagedExecutor source)`: `GroupCoordinationResult`
    - The single entry point for all adjustment coordination
    - IR disposition P0-01 resolved: coordinator accepts `ScaleAdjustmentCommand` (not `AdjustmentDecision`). Command carries `targetPoolSize()`, `currentPoolSize()`, `reason()`, `sourceDecisionRef()` — sufficient for all budget arithmetic. No need for pressure classification or policy score context.
    - Must be thread-safe (called by multiple loop threads)
    - Must NOT block for extended periods (budget check + oscillation check only, no I/O)
- `coordinate()` algorithm:
  1. If `command.isNoOp()` → return `APPROVED_AS_IS` immediately (no resource impact)
  2. `currentPoolSize = command.currentPoolSize()` (from command metadata)
  3. `targetPoolSize = command.targetPoolSize()`
  4. `delta = targetPoolSize - currentPoolSize`
  5. If `delta <= 0` (scale-down or hold):
     - Release `abs(delta)` threads back to budget: `budget.release(executorId, abs(delta))`
     - Append scale-down info to rationale
     - Return `APPROVED_AS_IS`
  6. If `delta > 0` (scale-up):
     a. `priority = config.memberPriorities().getOrDefault(sourceId, config.defaultPriority())`
     b. Check `budget.availableThreads() >= delta`:
        - If sufficient → `budget.reserve(executorId, delta)`, return `APPROVED_AS_IS`
     c. If insufficient:
        i. Scan all other executors with lower priority, sorted by priority (lowest first)
        ii. For each, calculate `preemptible = allocated - minPoolSize`
        iii. Sum preemptible across candidates
        iv. If sum >= delta → preempt from candidates in priority order, allocate to requestor
        v. If sum < delta but > 0 → preempt what we can, cap request to available + preempted → return `CAPPED`
        vi. If sum == 0 → return `REJECTED` (no preemptible budget)
  7. Run `crossDetector.wouldCrossOscillate(decision, source, history)`:
     - If detected → set `crossOscillationDetected = true` in result, include in rationale, but do NOT block (cross-oscillation is advisory, not blocking)
  8. Record `GroupCoordinationEntry` in history
  9. Return `GroupCoordinationResult`
- `GroupCoordinationResult` record fields:
  - `command`: `ScaleAdjustmentCommand` — the submitted command
  - `approvedCommand`: `ScaleAdjustmentCommand` — the command after coordination (same as original if APPROVED_AS_IS; modified target if CAPPED)
  - `outcome`: `CoordinationOutcome` — APPROVED_AS_IS, MODIFIED, REJECTED, CAPPED
  - `rationale`: `String` — human-readable explanation of coordination decision
  - `conflicts`: `List<String>` — conflicting executor IDs and descriptions
  - `crossOscillationDetected`: `boolean`
  - `coordinatedAt`: `Instant`
- `CoordinationOutcome` enum:
  - `APPROVED_AS_IS` — no conflict, decision applied unchanged
  - `MODIFIED` — preempted others to accommodate
  - `REJECTED` — cannot allocate, decision blocked
  - `CAPPED` — partial allocation, granted less than requested
- Instance method: `isApproved()` returns true for APPROVED_AS_IS and MODIFIED
- `buildPreemptedCommand(executorId, newTargetSize)`: constructs a `ScaleAdjustmentCommand` to preempt a lower-priority executor
- Package: `experiment.coordination`

Priority: P0.

### IR-v0.15-005 CoordinatedAdjustmentAdapter

System needs `CoordinatedAdjustmentAdapter` as a decorator implementing `ExecutorAdjustmentAdapter`, injecting coordination before delegation. IR disposition P0-01 resolved: coordinator accepts `ScaleAdjustmentCommand` directly — no decision reconstruction needed.

Candidate acceptance semantics:

- `CoordinatedAdjustmentAdapter` class:
  - Implements `ExecutorAdjustmentAdapter`
  - Constructor: `CoordinatedAdjustmentAdapter(ExecutorAdjustmentAdapter delegate, GroupCoordinator coordinator, ManagedExecutor executor, Supplier<Instant> clock)`
  - `currentState()`: delegates directly to `delegate.currentState()` (no coordination needed for reads)
  - `apply(ScaleAdjustmentCommand command)`:
    1. Call `coordinator.coordinate(command, executor)` → `GroupCoordinationResult`
    2. If `!result.isApproved()`:
       - Return `AdjustmentResult` with status `REJECTED`, failureCode = COORDINATION_REJECTED or COORDINATION_CAPPED, reason from result.rationale()
    3. If `result.outcome() == CAPPED`:
       - Use `result.approvedCommand()` with capped pool size
       - Delegate to `delegate.apply(result.approvedCommand())`
    4. If `result.outcome() == APPROVED_AS_IS` or `MODIFIED`:
       - Delegate to `delegate.apply(command)` (command unchanged)
    5. After successful delegation:
       - If command represents scale-down → coordinator releases resources (via `ResourceBudget.release()`)
       - Return the AdjustmentResult from delegate
- **Safety gate interaction** (IR disposition P1-01): The `AdjustmentLoop` already performs `safetyGate.evaluate()` at Step 8 before calling `adapter.apply()`. The coordinator adds resource conflict checking between safety gate and adapter. The delegate adapter's internal safety gate check is NOT bypassed — it runs as normal. The triple-check sequence is:
  1. Loop Step 8: `safetyGate.evaluate()` — pre-filter (cooldown, boundary checks)
  2. Coordinator: resource budget + priority conflict resolution
  3. Delegate adapter: `safetyGate.evaluate()` — enforcement (same SafetyGate instance, applies cooldown via `recordApplied()`)
  This triple-check is the existing design pattern (double-gating in v0.14.0 + coordination in v0.15.0). No changes to v0.14.0 safety gate logic.
- **Preemption enforcement** (IR disposition P1-02): When coordinator decides to preempt executor-B:
  1. Coordinator calculates `newTargetPoolSize` for executor-B
  2. Coordinator builds a `ScaleAdjustmentCommand` for executor-B
  3. Coordinator calls `executorB.adapter.apply(preemptCommand)` directly — no async signal needed
  4. B's loop discovers the changed pool size on its next iteration via `adapter.currentState()`
- Does NOT modify `ExecutorAdjustmentAdapter` interface
- Does NOT modify `AdjustmentLoop`
- Package: `experiment.coordination`

Priority: P0.

### IR-v0.15-006 GroupLoopOrchestrator and GroupHealth

System needs `GroupLoopOrchestrator` to manage the lifecycle of multiple `AdjustmentLoop` instances as a coordinated group.

Candidate acceptance semantics:

- `GroupLoopOrchestrator` class:
  - Constructor: `GroupLoopOrchestrator(ExecutorGroup group, ExecutorRegistry registry)`
  - `loops`: `Map<String, AdjustmentLoop>` — executorId → loop, populated by startAll()
- Lifecycle methods:
  - `startAll(Map<String, List<ThresholdPolicyConfig>> policiesByExecutor)`: `Map<String, LoopSession>`

      - `LoopConfig.defaults(policiesByExecutor.get(executorId))`

    - Return map of executorId → LoopSession

  - `startLoop(String executorId, List<ThresholdPolicyConfig> policies)`: `LoopSession` — start a single executor's loop
  - `pauseAll()`: pause all RUNNING loops
  - `resumeAll()`: resume all PAUSED loops
  - `stopAll()`: `Map<String, LoopSession>` — stop all, return final sessions
  - `emergencyStopAll(String reason)`: emergency stop all loops (e.g., cross-executor oscillation detected at group level)
- `getGroupHealth()`: `GroupHealth` — aggregated group state snapshot
- `GroupHealth` record fields:
  - `groupId`: `String`
  - `totalExecutors`: `int`
  - `runningLoops`: `int`
  - `pausedLoops`: `int`
  - `stoppedLoops`: `int`
  - `emergencyStoppedLoops`: `int`
  - `currentPressureStates`: `Map<String, PressureState>` — executorId → current pressure state
  - `budgetSnapshot`: `Map<String, Integer>` — current thread allocation per executor
  - `budgetAvailable`: `int`
  - `activeWarnings`: `List<String>` — e.g., "budget >= 90% utilized", "cross-executor oscillation suspected"
- Group-level emergency stop conditions:
  - Budget exhausted and two or more executors in OVERLOAD simultaneously
  - Cross-executor oscillation detected for >= 3 consecutive coordination cycles
  - Any CRITICAL executor emergency-stops (cascading stop)

### IR-v0.15-008 CrossExecutorOscillationDetector

System needs `CrossExecutorOscillationDetector` to detect oscillation patterns spanning multiple executors.

Candidate acceptance semantics:

- `CrossExecutorOscillationDetector` class:
  - Constructor: `CrossExecutorOscillationDetector(int windowSize)` — window size default 8 (slightly larger than per-executor window of 6)
- `wouldCrossOscillate(AdjustmentDecision pending, ManagedExecutor source, GroupCoordinationHistory history)`: `boolean`
  - Parameters: pending decision for source executor, plus group coordination history
  - Returns true if executing this decision would create a cross-executor oscillation pattern
- Three detection patterns:
  1. **Lockstep counter-adjustment**: source scales up while another executor recently scaled down by similar magnitude, forming A↑B↓A↑B↓ pattern
     - Detection: check if `sign(delta_source)` is opposite to `sign(delta_other)` for the same other executor in the window, and this has alternated >= 2 times
  2. **Resource ping-pong**: the same thread units being claimed by A, then released by A, then claimed by B, then released by B, then claimed by A again
     - Detection: check if the same resource units appear in reserve/release pairs between the same two executors >= 3 times in the window
  3. **Priority thrashing**: a higher-priority executor repeatedly preempts a lower-priority one (>= 3 times in window), causing the lower-priority executor's pool size to oscillate
     - Detection: check count of MODIFIED outcomes where the same (source, target) pair appears in `conflicts` >= 3 times
- `detectedPattern(GroupCoordinationHistory history)`: `Optional<String>` — descriptive name of detected pattern
- Empty history or insufficient entries → return false
- Detection is advisory — the result is recorded in `GroupCoordinationResult` but does NOT block the adjustment (unlike per-executor oscillation detection which triggers emergency stop)
- Pure function: no mutable state, input history + pending → output boolean
- Package: `experiment.coordination`

Priority: P1.

### IR-v0.15-009 ClosedLoopValidationRunner

System needs `ClosedLoopValidationRunner` to execute 3-way comparison (closed-loop vs static-policy vs baseline) and produce a validation report.

Candidate acceptance semantics:

- `ClosedLoopValidationRunner` class:
  - Constructor: `ClosedLoopValidationRunner(Supplier<Instant> clock)` — no `ComparableScenarioRunner` dependency (IR disposition P1-04: all three modes use `ManagedExecutorScenarioRunner` for managed-vs-managed comparison)
  - `validate(ValidationScenario scenario)`: `ValidationComparisonReport`
- `ValidationScenario` record fields:
  - `scenarioId`: `String` — unique scenario identifier, non-blank
  - `workload`: `LoadScenario` — identical workload for all three modes
  - `executorConfig`: `ManagedExecutorConfig` — starting executor configuration
  - `candidatePolicies`: `List<ThresholdPolicyConfig>` — for closed-loop mode, non-empty
  - `bestStaticPolicy`: `ThresholdPolicyConfig` — for static-policy mode
  - `duration`: `Duration` — how long each mode runs, minimum 30s
  - `minIterations`: `int` — minimum loop iterations for closed-loop mode, default 10
  - `warmupPeriodMs`: `long` — warmup before measurements start, default 10000
- `validate()` execution flow:
  ```
  Mode A — Closed-Loop:
    1. Create ManagedExecutor from executorConfig, register in ExecutorRegistry
    2. Create InMemoryEvidenceRecorder
    3. Start LivePressureSampler (pollInterval = 500ms)
    4. Create AdjustmentLoop with candidatePolicies (using LoopConfig.defaults)
    5. Run workload via workload executor (not ComparableScenarioRunner — this is a loop scenario, not a baseline comparison)
    6. Start AdjustmentLoop
    7. Wait warmupPeriodMs
    8. Run for duration
    9. Stop loop, stop sampler, collect snapshots and metrics
    10. Compute metric values from snapshots

  Mode B — Best Static Policy:
    1. Create ManagedExecutor from executorConfig
    2. Apply bestStaticPolicy at start (one-time adjustment)
    3. Create InMemoryEvidenceRecorder, start LivePressureSampler
    4. Run workload
    5. Wait warmupPeriodMs, run for duration
    6. Stop sampler, collect metrics

  Mode C — Baseline (No Adjustment):
    1. Create ManagedExecutor from executorConfig (no policy applied)
    2. Create InMemoryEvidenceRecorder, start LivePressureSampler
    3. Run workload
    4. Wait warmupPeriodMs, run for duration
    5. Stop sampler, collect metrics

  4. Compute MetricComparison for each of 7 metrics
  5. Run StatisticalSignificanceCalculator for each metric (closed-loop vs baseline, closed-loop vs static)
  6. Assemble ValidationComparisonReport with overall conclusion
  ```
- `ValidationComparisonReport` record fields:
  - `reportId`: `String` — UUID
  - `scenario`: `ValidationScenario`
  - `closedLoopResult`: `ValidationRunResult`
  - `staticPolicyResult`: `ValidationRunResult`
  - `baselineResult`: `ValidationRunResult`

### IR-v0.15-010 Statistical Significance Calculator

System needs `StatisticalSignificanceCalculator` to compute statistical tests for validation comparisons.

Candidate acceptance semantics:

- `StatisticalSignificanceCalculator` class:
  - All methods are static (stateless utility)
  - No external library dependencies
- `compare(double[] modeAValues, double[] modeBValues, String metricName)`: `StatisticalSignificance`
  - Computes paired t-test, Cohen's d, and 95% confidence interval
- `StatisticalSignificance` record fields:
  - `metricName`: `String`
  - `pValue`: `double` — from paired t-test
  - `confidenceIntervalLow`: `double`
  - `confidenceIntervalHigh`: `double`
  - `effectSize`: `double` — Cohen's d
  - `isSignificant`: `boolean` — pValue < 0.05
  - `sampleSize`: `int`
- Algorithms (in-project implementation):
  1. Paired t-test:
     - `differences[i] = modeA[i] - modeB[i]`
     - `meanDiff = mean(differences)`
     - `stdErr = stddev(differences) / sqrt(n)`
     - `t = meanDiff / stdErr`
     - p-value from t-distribution CDF (Abramowitz and Stegun approximation or Student's t table lookup)
  2. Cohen's d:
     - `d = meanDiff / pooledStdDev`
     - `pooledStdDev = sqrt(((nA-1)*varA + (nB-1)*varB) / (nA + nB - 2))`
  3. 95% CI:
     - `CI = meanDiff ± t_critical * stdErr`
     - `t_critical` for df = n-1, alpha = 0.05
- Edge cases:
  - n < 2 → return non-significant with note "insufficient samples"
  - All differences identical → stdErr = 0 → return non-significant with note "no variance"
  - Extreme t-values → clamp p-value to [0.0001, 0.9999]
- Accuracy: p-value within ±0.01 of reference implementation for n >= 10
- Package: `experiment.validation`

Priority: P1.

## 6. Risks and Deferred Items

| Risk | Current Assessment | Trigger Condition |
|---|---|---|
| `CoordinatedAdjustmentAdapter` decision reconstruction | P1 risk — IR-v0.15-005 open question. The coordinator needs target pool size and source executor info. `ScaleAdjustmentCommand` already carries `targetPoolSize()`, `currentPoolSize()`, `reason()`, `sourceDecisionRef()`. Decision: should coordinator accept `AdjustmentDecision` (full diagnosis chain) or `ScaleAdjustmentCommand` (simpler reconstruction)? SR must decide. | SR resolution of IR-v0.15-005 open question |
| `GroupCoordinator.coordinate()` thread safety under concurrent loop threads | P1 risk — multiple loops call `coordinate()` concurrently. The coordinator uses `synchronized` methods or a `ReentrantLock` to serialize budget operations. Risk: lock contention delays loop iterations. Mitigation: budget check is O(n) where n = group size (small, typically < 10). Non-blocking fast path for scale-down decisions (no lock needed). | SR design of synchronization strategy |
| `ResourceBudget` preemption changes executor state outside its own loop | P2 risk — when coordinator preempts executor-B to give resources to executor-A, executor-B's pool size is reduced by the coordinator, not by B's own loop. B's loop may observe the changed pool size on its next iteration and react (potentially re-requesting scale-up). This is the expected coordination feedback loop, but could cause loop confusion. Mitigation: preemption is communicated to B's loop via `PREEMPT` signal in the coordination result; B's loop sees the result in its next `adapter.apply()` call. | Over-correction pattern in E2E tests |
| Cross-executor oscillation detection sensitivity | P2 risk — lockstep counter-adjustment detection uses pool size delta sign matching. If two executors naturally have complementary workloads (one is busy while the other is idle), this could produce false positives. Mitigation: detection is advisory, not blocking. Only logged in GroupHealth warnings. | False positive rate in E2E tests |
| `ComparableScenarioRunner` workload identity vs closed-loop dynamic adjustment | P2 risk — `ClosedLoopValidationRunner` does NOT use `ComparableScenarioRunner.compare()` directly because that method runs baseline vs managed comparison, not closed-loop. The validation runner runs all three modes independently with the same `LoadScenario`. Workload identity is guaranteed by using the same `LoadScenario` instance for all three modes. | SR verification of workload identity preservation |
| `ClosedLoopValidationRunner` sequential execution time | P3 risk — 3 modes × 30s each + warmup = ~2 minutes minimum. Acceptable for a test/development context. Not on the critical path. | Test timeout configuration |
| Statistical accuracy of in-project t-distribution CDF | P3 risk — Abramowitz and Stegun approximation is accurate to ~0.001 for df >= 5. For sample sizes >= 30, this is adequate. For n < 30, accuracy degrades but p-value direction (significant vs not) remains reliable at p=0.05 threshold. | SR verification with reference values |
| `LoopSession.ended()` constructor validation requires `iterationCount >= adjustmentCount` | P2 risk — When preemption causes an adjustment to be applied outside the executor's own loop, the loop's iteration counter won't account for it. The loop's `adjustmentCount` from `history.totalAdjustmentCount()` may include preempted adjustments. Mitigation: preempted adjustments are recorded in the preempted executor's `AdjustmentHistory` through the adapter. | SR design of preemption history tracking |
