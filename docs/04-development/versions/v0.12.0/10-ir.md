# v0.12.0 IR 需求分析草案

## Header

- Document type: IR requirement draft
- Version name: `v0.12.0`
- Status: `DRAFT`
- Current phase: `BASELINE_COMPARISON_REQUIREMENT_DRAFT`
- Authoring date: `2026-06-14`
- Current conclusion: 本文只定义 baseline comparison experiment framework 需求，不授权 SR、OpenSpec change、Java 实现

## 1. 需求来源

### 1.1 项目现状

v0.7.0 交付了 ManagedExecutor 域（ManagedExecutor, ExecutorRegistry, AdjustmentAdapter）。v0.3.0 交付了场景运行基础设施（ScenarioExperimentRunner, BaselineWorkloadExecutor, ScenarioPlanner）。v0.8.0 交付了真实数据获取管道（ManagedExecutorScenarioRunner）。v0.11.0 交付了持久化证据录制和自主采样。

系统已具备独立运行 baseline executor 和 managed executor 的能力，但两者之间没有比较框架。运行 baseline 和运行 managed 是两个完全独立的路径，无法在同一个实验运行中收集两组结果并进行对比。

### 1.2 结构性缺口

五个具体缺口在 `00-objectives-and-scope.md` §1.2 中已详细描述：

1. **无 executor baseline 目录** — `BaselineExecutorPreset` 只能承载单个预设。没有注册表来定义和管理多个常见 thread-pool 配置，无法在一次实验运行中系统性地对比多种 executor 配置。

2. **无可比场景运行器** — `ScenarioExperimentRunner` 每次运行仅使用单一 `BaselineWorkloadExecutor`；`ManagedExecutorScenarioRunner` 每次运行仅使用单一 `ManagedExecutor`。不存在"同一 scenario、两个 executor 类型、可比较结果"的运行器。

3. **无归一化结果模型** — `ScenarioRunOutcome` 仅包含简单字段（stepCount, workUnits, evidenceCount）。`PressureSnapshot` 和 `RuntimeObservation` 的指标命名和语义在不同 executor 类型间不统一（`BaselineWorkloadExecutor.completedTaskCount()` 返回 `completedWorkUnits` 而非真实 task count）。缺少跨 executor 类型可比较的归一化度量模型。

4. **无比较报告产物** — 所有现有报告（`AcquisitionReportWriter`、`ReplayReportWriter`）各自针对单一 executor 类型。不存在包含"baseline vs managed"并列对比、delta 计算、结论摘要的标准化报告。

5. **无法证明 managed executor 的优势** — roadmap 的核心战略问题（"managed executor 是否优于 common thread-pool baseline"）无法用记录证据回答。

### 1.3 为什么是现在

- 三个动态配置维度（v0.7.0–v0.10.0）+ 持久化证据录制 + 自主采样（v0.11.0）全部到位，可以进行有意义的端到端比较
- 在没有比较框架之前，无法用数据证明"为什么需要 managed executor"——这是 roadmap 中整个 evidence-first 序列的逻辑起点
- `ScenarioExperimentRunner` 和 `ManagedExecutorScenarioRunner` 各自的独立运行能力已经过 646 个测试验证
- 比较框架是 v0.13.0（pressure classification）、v0.14.0（adaptive closed-loop）、v0.15.0（strategy explanation）的前提 — 必须先有比较基线
- roadmap 明确："v0.12.0 的第一个可接受切片应证明至少一个 common thread-pool baseline 和一个 managed-executor run 可以在同一 scenario 下进行比较，产出持久化的、可审查的结果产物"

## 2. 范围

### 2.1 范围内

- `CommonExecutorPreset` record：标准化 executor 预设描述（预设ID、类型、core/max/queue、描述）
- `BaselineExecutorCatalog`：预设注册表，支持注册、查询、默认预设集（6个JDK标准类型）
- `ComparableScenarioRunner`：接受 scenario + baseline preset + managed config，依次运行两者，收集两组结果
- `NormalizedComparisonMetrics` record：9 个归一化度量指标（跨 executor 类型可比较）
- `ComparisonResult` record：包含两组 run 结果和逐 metric delta 的比较结果
- `ComparisonReportArtifact` record：比较报告产物
- `ComparisonJsonWriter`：比较报告 JSON 序列化/反序列化（手写 JSON，复用 AcquisitionJsonWriter 模式）
- `AcquisitionReportPaths` 扩展：comparison 报告文件路径
- `ScenarioExperimentRunner` 扩展：为 `ComparableScenarioRunner` 暴露工厂或运行方法
- `MetricDelta` record：单指标 delta（baselineValue, managedValue, absoluteDelta, relativeDelta, direction）
- 现有 646 测试零回归

### 2.2 范围外

- 多场景批量比较（单 scenario 1:1 比较）
- 多于 2 个 executor 的并行比较（仅 1:1）
- 统计显著性检验（t-test、confidence intervals）
- 时间序列可视化或图表生成
- pressure classification（v0.13.0 候选）
- adaptive closed-loop adjustment（v0.14.0 候选）
- strategy explanation（v0.15.0 候选）
- CPU utilization 真实数据源（DFR-01）
- 跨 run 证据聚合（DFR-03）
- 复杂 workload 类型（burst/long-tail/mixed — v0.16.0 候选）
- CLI entry
- 修改 ManagedExecutor、EvidenceRecorder、PressureSampler 接口

### 2.3 术语

| 术语 | 定义 |
|---|---|
| BaselineExecutorCatalog | 注册和管理多个 `CommonExecutorPreset` 的注册表，提供默认 JDK 标准预设集，支持按 presetId 查询 |
| CommonExecutorPreset | 不可变 record，描述通用 executor 预设的标准化属性：presetId、executorType（FIXED_THREAD_POOL / CACHED_THREAD_POOL / SINGLE_THREAD_EXECUTOR）、corePoolSize、maxPoolSize、queueCapacity（-1 为无界）、description |
| ComparableScenarioRunner | 比较场景运行器：接受 ScenarioDefinition + baseline preset ID + ManagedExecutorConfig，先运行 baseline executor 再运行 managed executor，收集两组 ObservedSnapshot，产出 ComparisonResult |
| NormalizedComparisonMetrics | 不可变 record，将不同 executor 类型的 observation 映射到统一的 9 个可比较指标，可从 List\<ObservedSnapshot\> 计算 |
| ComparisonResult | 不可变 record，包含 comparisonId、scenarioId、两组 ScenarioRunOutcome、两组 NormalizedComparisonMetrics、逐 metric delta Map、createdAt |
| MetricDelta | 不可变 record，单指标比较 delta：baselineValue、managedValue、absoluteDelta（managed - baseline）、relativeDelta（相对于 baseline 的百分比）、direction（IMPROVED / REGRESSED / NEUTRAL） |
| ComparisonReportArtifact | 不可变 record：comparisonId、scenarioId、createdAt、baselinePreset、managedConfig、ComparisonResult、conclusion（人类可读结论文本） |
| ComparisonJsonWriter | 比较报告 JSON 序列化器，手写 JSON（无外部依赖），复用 AcquisitionJsonWriter 的序列化模式。支持 writeComparisonReport() 和 readComparisonReport() |
| 归一化指标 | 从不同 executor 类型的原始快照中计算出的可比较度量：completedTaskCount、rejectedTaskCount、avgQueueDepth、maxQueueDepth、totalDurationMs、throughputPerSecond、avgActiveThreads、maxPoolSize、snapshotCount |

## 3. IR 条目草案

### IR-v0.12-001 BaselineExecutorCatalog

系统需要 `BaselineExecutorCatalog` 注册和管理多个常见 thread-pool 预设配置。

候选验收语义：

- `BaselineExecutorCatalog` 类必须包含：
  - `register(CommonExecutorPreset)`：注册 preset，对重复 presetId 抛出 `IllegalArgumentException`
  - `get(String presetId)`：按 ID 查询，不存在时抛出 `NoSuchElementException`
  - `presetIds()`：返回所有已注册 presetId 的不可变集合
  - `size()`：返回已注册 preset 数量
- 静态工厂方法 `withDefaults()` 必须注册至少 6 个预设：
  - `fixed-2`：FIXED_THREAD_POOL, core=2, max=2, queue=-1（无界）
  - `fixed-4`：FIXED_THREAD_POOL, core=4, max=4, queue=-1（无界）
  - `fixed-8`：FIXED_THREAD_POOL, core=8, max=8, queue=-1（无界）
  - `cached`：CACHED_THREAD_POOL, core=0, max=Integer.MAX_VALUE, queue=0（SynchronousQueue）
  - `single`：SINGLE_THREAD_EXECUTOR, core=1, max=1, queue=-1（无界）
  - `fixed-2-bounded`：FIXED_THREAD_POOL, core=2, max=2, queue=10（有界队列）
- `BaselineExecutorCatalog` 本身不可变（构造后 preset 集合不变），不支持 unregister
- 不得依赖任何外部配置文件或数据库

优先级：P0。

### IR-v0.12-002 CommonExecutorPreset

系统需要 `CommonExecutorPreset` record 提供标准化 executor 预设描述。

候选验收语义：

- `CommonExecutorPreset` record 字段：
  - `presetId`: String — 不为 null、不为 blank
  - `executorType`: String — 限定为 `"FIXED_THREAD_POOL"` / `"CACHED_THREAD_POOL"` / `"SINGLE_THREAD_EXECUTOR"`
  - `corePoolSize`: int — >= 0
  - `maxPoolSize`: int — >= corePoolSize
  - `queueCapacity`: int — -1 表示无界（LinkedBlockingQueue default）、0 表示 SynchronousQueue、>0 表示有界队列容量
  - `description`: String — 可为 null（无描述）
- 构造时执行参数验证，不合法参数抛出 `IllegalArgumentException`
- `executorType` 必须是上述三个枚举值之一，其他值抛出 `IllegalArgumentException`
- 不可变 record
- **CommonExecutorPreset → BaselineExecutorPreset 转换规则**（F04 fix）:
  - `queueCapacity == -1` → 转换为 `BaselineExecutorPreset` 的 `queueCapacity = Integer.MAX_VALUE`（语义：无界）
  - `queueCapacity == 0` → 转换为 `queueCapacity = 0`（语义：SynchronousQueue — baseline 不使用真实队列，保留原始值作记录）
  - `queueCapacity > 0` → 直接传递
  - 不修改 `BaselineExecutorPreset` 的现有验证逻辑；转换由 `ComparableScenarioRunner` 内部执行
  - `policyId` 直接映射到 `presetId`

优先级：P0。

### IR-v0.12-003 ComparableScenarioRunner

系统需要 `ComparableScenarioRunner` 接受同一 scenario，依次运行 baseline executor 和 managed executor，并收集两组可比较的结果。

候选验收语义：

- 构造参数：
  - `ExperimentCoordinator baselineCoordinator` — baseline run 的 coordinator
  - `ExperimentCoordinator managedCoordinator` — managed run 的 coordinator
  - `ScenarioPlanner planner`
  - `BaselineExecutorCatalog baselineCatalog`
  - `EvidenceRecorder baselineRecorder` — baseline run 的快照写入此 recorder
  - `EvidenceRecorder managedRecorder` — managed run 的快照写入此 recorder
  - `Supplier<Instant> clock`
- **Runner 实例化策略**（F05 fix）:
  - `ComparableScenarioRunner` 不在构造时持有 `ScenarioExperimentRunner` 或 `ManagedExecutorScenarioRunner` 实例
  - 在 `compare()` 内部，根据 `baselinePresetId` 动态创建 `ScenarioExperimentRunner`（每个 baseline preset 对应一个新的 runner 实例）
  - 每次 `compare()` 调用动态创建 `ManagedExecutorScenarioRunner`（注入 `managedRecorder` 和 `managedCoordinator`）
  - 不得持有单一 runner 实例并假设可重复用于不同 preset
- `compare(ScenarioDefinition scenario, String baselinePresetId, ManagedExecutorConfig managedConfig)` 方法必须按以下精确步骤执行（F01 fix）:

```
1. CommonExecutorPreset preset = catalog.get(baselinePresetId)
   // presetId 不存在 → NoSuchElementException
2. BaselineExecutorPreset bPreset = toBaselinePreset(preset)
   // queueCapacity 转换: -1 → Integer.MAX_VALUE, 0 → 0, >0 → 直接传递
3. BaselineWorkloadExecutor bExecutor = new BaselineWorkloadExecutor(bPreset)
4. ScenarioExperimentRunner baselineRunner = new ScenarioExperimentRunner(
       baselineCoordinator, planner, bExecutor, baselineSampler, baselineRecorder, clock)
5. long baselineStartMs = clock.get().toEpochMilli()
6. ScenarioRunOutcome bOutcome = baselineRunner.run(scenario, bPreset)
7. long baselineEndMs = clock.get().toEpochMilli()
8. List<ObservedSnapshot> bSnapshots = baselineRecorder.snapshots(bOutcome.runId())
9. ManagedExecutorScenarioRunner managedRunner = new ManagedExecutorScenarioRunner(
       managedCoordinator, planner, managedSampler, managedRecorder, clock)
10. long managedStartMs = clock.get().toEpochMilli()
11. ScenarioRunOutcome mOutcome = managedRunner.run(scenario, managedConfig)
12. long managedEndMs = clock.get().toEpochMilli()
13. List<ObservedSnapshot> mSnapshots = managedRecorder.snapshots(mOutcome.runId())
14. NormalizedComparisonMetrics bMetrics = NormalizedComparisonMetrics.fromSnapshots(
        bSnapshots, baselineEndMs - baselineStartMs, bPreset.corePoolSize())
15. NormalizedComparisonMetrics mMetrics = NormalizedComparisonMetrics.fromSnapshots(
        mSnapshots, managedEndMs - managedStartMs, managedConfig.corePoolSize())
16. Map<String, MetricDelta> deltas = computeDeltas(bMetrics, mMetrics)
17. return new ComparisonResult(comparisonId, scenario.scenarioId(),
        baselinePresetId, managedConfig.toPresetSummary().policyId(),
        bOutcome, mOutcome, bMetrics, mMetrics, deltas, clock.get())
```

- 关键数据流澄清:
  - snapshots 通过 `recorder.snapshots(outcome.runId())` 获取，**非**从 runner 的返回值直接获取。`ScenarioRunOutcome` 不含 snapshots 列表
  - `totalDurationMs` 从 wall-clock 计时计算（step 5/7、step 10/12），非从 snapshots 推断
  - `fallbackPoolSize` 传入 `preset.corePoolSize()`（baseline）或 `managedConfig.corePoolSize()`（managed）
- baseline run 中如有异常，不得尝试 managed run（fail-fast）
- baseline run 和 managed run 必须顺序执行（非并发）
- `ComparableScenarioRunner.compare()` 返回前必须确保两次 run 均已 `finalizeRun()`（由各自的 runner 内部完成）
- 两次 run 使用独立的 `runId`（由各自的 `ExperimentCoordinator` 生成），通过 `ComparisonResult` 关联

优先级：P0。

### IR-v0.12-004 NormalizedComparisonMetrics

系统需要 `NormalizedComparisonMetrics` record 提供跨 executor 类型的归一化度量。

候选验收语义：

- `NormalizedComparisonMetrics` record 字段（9 个）：
  - `completedTaskCount`: long — 完成任务总数
  - `rejectedTaskCount`: long — 拒绝任务数
  - `avgQueueDepth`: double — 所有 snapshot 的 queueSize 平均值
  - `maxQueueDepth`: int — 所有 snapshot 的 queueSize 最大值
  - `totalDurationMs`: long — 总运行时长（milliseconds）
  - `throughputPerSecond`: double — `completedTaskCount / (totalDurationMs / 1000.0)`
  - `avgActiveThreads`: double — 所有 snapshot 的 activeThreads 平均值
  - `maxPoolSize`: int — 所有 snapshot 的 poolSize 最大值
  - `snapshotCount`: int — 快照总数
- 静态工厂方法 `fromSnapshots(List<ObservedSnapshot> snapshots, long totalDurationMs, int fallbackPoolSize)` 必须：
  - 从快照列表计算所有聚合值
  - `fallbackPoolSize` 用于 snapshot 列表为空时的 `maxPoolSize` 和 `avgActiveThreads` fallback
  - snapshot 列表为空时不抛异常，返回所有值为 0 的 metrics（`totalDurationMs` 除外）
  - `throughputPerSecond` 在 `totalDurationMs == 0` 时返回 0.0（不抛除零异常）
- **`totalDurationMs` 参数来源**（F06 fix）:
  - 由 `ComparableScenarioRunner.compare()` 在每个 run 前后调用 `clock.get()` 记录 wall-clock 时间戳
  - `totalDurationMs = Duration.between(startInstant, endInstant).toMillis()`
  - 使用 wall-clock 计时（而非 snapshots 的 first/last timestamp 差值），因为它包含 setup/teardown 开销，更准确反映 executor 的端到端性能
  - `fromSnapshots()` 接受外部传入的 `totalDurationMs`，不从 snapshots 内部推断
- `completedTaskCount`：从最后一个 snapshot 的 `completedTaskCount`（PressureSnapshot 字段）取值，或从 observation 的 `completedTaskCount` MetricValue 提取（如 Present）
- `rejectedTaskCount`：baseline executor 当前无法提供此数据，默认返回 0。managed executor 从 `ManagedExecutor` 的拒绝计数获取
- 不可变 record

优先级：P0。

### IR-v0.12-005 ComparisonResult 与 MetricDelta

系统需要 `ComparisonResult` 和 `MetricDelta` record 承载比较结果。

候选验收语义：

- `ComparisonResult` record 字段：
  - `comparisonId`: String — UUID
  - `scenarioId`: String
  - `baselinePresetId`: String
  - `managedConfigId`: String — managed executor config 的标识
  - `baselineOutcome`: ScenarioRunOutcome
  - `managedOutcome`: ScenarioRunOutcome
  - `baselineMetrics`: NormalizedComparisonMetrics
  - `managedMetrics`: NormalizedComparisonMetrics
  - `deltas`: Map\<String, MetricDelta\> — key 为 metric name（如 "throughputPerSecond"）
  - `createdAt`: Instant
- `MetricDelta` record 字段：
  - `metricName`: String
  - `baselineValue`: double
  - `managedValue`: double
  - `absoluteDelta`: double — `managedValue - baselineValue`
  - `relativeDelta`: double — `(managedValue - baselineValue) / baselineValue * 100.0`（baselineValue == 0 时返回 0.0）
  - `direction`: String — `"IMPROVED"` / `"REGRESSED"` / `"NEUTRAL"`
- `ComparisonResult` 的 `deltas` Map 必须包含全部 9 个归一化指标的 delta
- 不可变 record

优先级：P0。

### IR-v0.12-006 ComparisonReportArtifact 与 ComparisonJsonWriter

系统需要 `ComparisonReportArtifact` 作为比较报告的持久化产物，以及 `ComparisonJsonWriter` 进行 JSON 序列化。

候选验收语义：

- `ComparisonReportArtifact` record 字段：
  - `comparisonId`: String
  - `scenarioId`: String
  - `createdAt`: Instant
  - `baselinePreset`: CommonExecutorPreset
  - `managedConfig`: ManagedExecutorConfig
  - `result`: ComparisonResult
  - `conclusion`: String — 人类可读结论文本
- `ComparisonJsonWriter` 类：
  - 构造参数：`AcquisitionReportPaths paths`
  - `writeComparisonReport(ComparisonReportArtifact)` 必须：
    - 将 artifact 序列化为格式化的 JSON 字符串
    - 写入文件：`outputs/reports/v0.12.0/comparison-<comparisonId>.json`
    - 返回文件路径字符串
  - `readComparisonReport(Path filePath)` 必须：
    - 从 JSON 文件反序列化 `ComparisonReportArtifact`
    - 对所有字段进行完整性验证（无 null 字段、无类型不匹配）
    - JSON 不合法时抛出明确异常
  - `writeComparisonReport(ComparisonReportArtifact, Path outputPath)` 重载：
    - 支持指定输出路径（方便测试使用临时目录）
- `ComparisonJsonWriter` 使用手写 JSON（`StringBuilder` + 字段逐行写入），与 `AcquisitionJsonWriter` 和 `MinimalJsonWriter` 模式一致
- 不引入任何外部 JSON 库依赖
- **`ManagedExecutorConfig` JSON 格式**（F02 fix）:
  ```json
  "managedConfig": {
    "corePoolSize": 4,
    "maximumPoolSize": 8,
    "queueCapacity": 20,
    "keepAliveTime": 60,
    "keepAliveTimeUnit": "SECONDS",
    "threadMode": "PLATFORM"
  }
  ```
  - `keepAliveTimeUnit` 使用 `TimeUnit.name()` 序列化（返回 "SECONDS" / "MILLISECONDS" 等），`TimeUnit.valueOf(string)` 反序列化
  - `threadMode` 使用 `ThreadMode.name()` 序列化，`ThreadMode.valueOf(string)` 反序列化
  - 与 `AcquisitionJsonWriter` 处理枚举的模式一致（enum.name() 序列化）
- `AcquisitionReportPaths` 新增方法：
  - `comparisonReportFile(String comparisonId)`：返回 `outputs/reports/v0.12.0/comparison-<comparisonId>.json`

优先级：P0。

### IR-v0.12-007 BaselineWorkloadExecutor 到 NormalizedComparisonMetrics 映射

系统需要明确定义 baseline executor 的各指标到归一化指标的映射规则。

候选验收语义：

| NormalizedComparisonMetrics 字段 | BaselineWorkloadExecutor 数据来源 | ManagedExecutor 数据来源 |
|---|---|---|
| `completedTaskCount` | `baselineExecutor.completedWorkUnits()` | snapshots 中最后一个 observation 的 `completedTaskCount` Present 值 |
| `rejectedTaskCount` | 0（baseline executor 无拒绝机制） | 从 executor 或 snapshots 获取 |
| `avgQueueDepth` | 0.0（baseline executor 无队列） | 所有 snapshots 的 `queueSize` Present 值平均值，排除 Absent |
| `maxQueueDepth` | 0 | 所有 snapshots 的 `queueSize` Present 值最大值 |
| `totalDurationMs` | `Duration.between(baselineStart, baselineEnd).toMillis()` | 同 baseline |
| `throughputPerSecond` | `completedTaskCount / (totalDurationMs/1000.0)` | 同 baseline |
| `avgActiveThreads` | 0.0（baseline 同步执行，无真实线程池） | 所有 snapshots 的 `activeThreads` Present 值平均值 |
| `maxPoolSize` | `preset.corePoolSize()`（fallback 值） | 所有 snapshots 的 `poolSize` Present 值最大值 |
| `snapshotCount` | `baselineRecorder.snapshots(runId).size()` | 同 baseline |

- `NormalizedComparisonMetrics.fromSnapshots()` 必须接受 `fallbackPoolSize` 参数，当快照列表为空或所有值均为 Absent 时使用
- baseline executor 的 `completedTaskCount` 映射到 `completedWorkUnits` 而非真实 task count — 在 comparison report 中记录此映射差异

优先级：P0。

### IR-v0.12-008 端到端比较验证

系统需要端到端集成测试验证完整的 baseline vs managed 比较流程。

候选验收语义：

- 测试 1：BaselineExecutorCatalog 默认预设
  1. `BaselineExecutorCatalog.withDefaults()` → 验证 size() == 6
  2. 验证 `get("fixed-4")` 返回 preset（core=4, max=4, type=FIXED_THREAD_POOL）
  3. 验证 `get("cached")` 返回 preset（core=0, max=Integer.MAX_VALUE, queueCapacity=0）
  4. 验证 `get("nonexistent")` 抛出 `NoSuchElementException`
  5. 验证重复注册 presetId 抛出 `IllegalArgumentException`
- 测试 2：NormalizedComparisonMetrics 计算
  1. 使用 `ScenarioExperimentRunner` 运行一个有 100 个 steps 的 scenario
  2. 从 recorder 获取 snapshots → 调用 `fromSnapshots()`
  3. 验证 `completedTaskCount == 100`（每个 step 1 workUnit）
  4. 验证 `avgActiveThreads == 0.0`（baseline 无真实线程）
  5. 验证 `totalDurationMs > 0`
  6. 验证 `throughputPerSecond > 0`
- 测试 3：ComparableScenarioRunner 双 run 流程
  1. 创建 scenario（100 steps）
  2. `compare(scenario, "fixed-4", managedConfig)` 
  3. 验证返回的 `ComparisonResult.baselineOutcome.scenarioId() == scenario.scenarioId()`
  4. 验证 `ComparisonResult.managedOutcome.scenarioId() == scenario.scenarioId()`
  5. 验证 `ComparisonResult.deltas.size() == 9`
  6. 验证每个 delta 的 `baselineValue` 和 `managedValue` 非负
  7. 验证 baseline run 和 managed run 的 runId 不同
- 测试 4：ComparisonJsonWriter 序列化往返
  1. 运行 comparison → 得到 `ComparisonResult`
  2. 构建 `ComparisonReportArtifact`
  3. `writeComparisonReport()` → 临时文件

### IR-v0.12-009 ManagedExecutor rejection counting（F03 fix — 新增）

系统需要 `ManagedExecutor` 暴露拒绝任务计数，以支持 `NormalizedComparisonMetrics.rejectedTaskCount` 的真实数据源。

候选验收语义：

- `ManagedExecutor` 新增方法 `getRejectedTaskCount()`：返回 `long`
- 构造时自动包装 `RejectedExecutionHandler`：当原始 handler 的 `rejectedExecution(Runnable, ThreadPoolExecutor)` 被调用时，先递增内部 `AtomicLong` 计数器，再委托给原始 handler 的 `rejectedExecution()`
- 内部包装对外部透明：构造器签名不变（不添加新参数），`getRejectionPolicy()` 返回原始 handler（非包装器）
- PLATFORM 模式：包装 TPE 的 `RejectedExecutionHandler`
- VIRTUAL 模式：包装 `virtualRejectionHandler`
- 现有所有 `ManagedExecutor` 测试（`ManagedExecutorTest`、`ManagedExecutorConfigThreadModeTest` 等）继续通过
- 线程安全：`AtomicLong` 保证并发递增正确
- 新增 `ManagedExecutorTest` 测试用例：提交超过 queueCapacity + maxPoolSize 的任务 → 验证 `getRejectedTaskCount() > 0`

优先级：P0（v0.12.0 prerequisite — `rejectedTaskCount` 是 comparison 框架的关键可靠性指标）。

## 6. 风险和延期项

| 风险 | 当前判断 | 后续触发条件 |
|---|---|---|
| BaselineWorkloadExecutor 的 completedWorkUnits vs 真实 task count 差异 | P2 风险 | `BaselineWorkloadExecutor` 是同步执行器，`completedTaskCount()` 返回 `completedWorkUnits`。在归一化指标中，baseline executor 的 `completedTaskCount` 是 scenario step 的 workUnits 计数，而 managed executor 的是 TPE 的真实 task count。如果 scenario 中每个 step 的 workUnits=1，两者等价。当前所有 scenario 的 workUnits 均为 1，差异不可见。SR 需在 comparison report 中记录此映射语义 |
| managed executor 的 rejectedTaskCount 来源 | ~~P1 风险~~ → **已处置（F03 FIX）** | IR-v0.12-009 新增 ManagedExecutor rejection counting wrapper。方案确定：`AtomicLong` + `RejectedExecutionHandler` 包装器。在 IR 层面已解决 |
| BaselineExecutorPreset → CommonExecutorPreset 转换 | P2 风险 | `BaselineExecutorPreset` 仅包含 policyId + core/max/queue 三个数值字段。`CommonExecutorPreset` 额外包含 executorType 和 description。转换方向是 CommonExecutorPreset → BaselineExecutorPreset（单方向），已在 F04 fix 中定义转换规则 |
| ManagedExecutorScenarioRunner 集成点 | ~~P1 风险~~ → **已处置（F01/F05 FIX）** | `ComparableScenarioRunner` 在 `compare()` 内部动态创建 `ScenarioExperimentRunner` 和 `ManagedExecutorScenarioRunner` 实例。两者的构造器均支持注入 `EvidenceRecorder`。IR-v0.12-003 已补充精确数据流 |
| ComparisonJsonWriter 的 schema 兼容性 | P2 风险 | 手写 JSON 序列化没有 schema 验证，格式变更需要手动同步 reader 和 writer。6 个 record 类型（CommonExecutorPreset、NormalizedComparisonMetrics、MetricDelta、ComparisonResult、ComparisonReportArtifact） + ManagedExecutorConfig 的 JSON 表示需要精确定义。F02 fix 已补充 ManagedExecutorConfig JSON schema。剩余 4 个嵌套 record 格式延后到 SR |
| catalog 中 fixed-2/fixed-4/fixed-8 的无界队列风险 | P3 风险 | `LinkedBlockingQueue` 的无界队列可能导致 OOM。但在 comparison 测试场景中，每个 run 是短时的、确定性的 steps 执行，不会无限增长队列。`fixed-2-bounded` 预设覆盖了有界队列场景。不需要额外缓解措施 |
