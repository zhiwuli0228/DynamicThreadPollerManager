- Document type: IR requirement draft

## 1. 需求来源

### 1.1 用户确认方向

用户要求设计完整的测试数据获取方案并输出为标准测试文档。`15-experiment-data-acquisition-plan.md` 已完成方案设计，明确了架构、场景矩阵、指标采集、质量门禁和执行计划。经 `00-objectives-and-scope.md` 和 `decision-log.md` 基线确认后，进入 IR 需求分析阶段。方向明确：在真实 ManagedExecutor 上运行多场景数据获取，集成 ExecutorStateSnapshot 到标准 metrics 管道。

### 1.2 项目现状

v0.7.0 已交付 ManagedExecutor 域和首次闭环实验验证（412 tests, 0 failures）。但以下能力缺失：

| 已交付能力 | 与真实数据获取的关系 | 当前限制 |
|---|---|---|
| `ScenarioExperimentRunner` + `BaselineWorkloadExecutor` | v0.3.0 交付，运行无真实线程的场景 | `activeThreads()` 恒为 0，`queueSize()` 恒为 0 |
| `ManagedExecutor` + `ExecutorRegistry` | v0.7.0 交付，可包装真实 TPE | 只在闭环实验中单次使用，未在多场景中运行 |
| `ManagedExecutorAdjustmentAdapter` | v0.7.0 交付，可读取真实状态 | 只在闭环实验中验证，未在 STEADY/RAMP/BURST 中采集 |
| `AcquisitionReportWriter` + `DataQualityValidator` | v0.6.0 交付，成熟的报告流水线 | 路径硬编码 v0.6.0，门禁未覆盖 TPE 扩展字段 |
| `SnapshotAssembler` / `PressureSampler` | v0.2.0 交付，确定性快照组装 | 没有从 `ExecutorStateSnapshot` 构建的入口 |

当前结构性缺口：

- **没有标准化真实数据获取能力**：v0.7.0 闭环实验是一次性手动编排，不是可配置、可重复的标准化数据采集。无法在 STEADY/RAMP/BURST 三种场景下系统性地获取真实线程池压力数据。
- **ExecutorStateSnapshot 不经过 metrics 管道**：闭环实验中 `PressureSnapshot` 是手动 `new` 出来的（`ClosedLoopExperimentTest:97-103`），绕过了 `SnapshotAssembler` 和 `PressureSampler`。这意味着 metrics 管道（`EvidenceRecorder` → `AcquisitionReportWriter`）无法接收来自 ManagedExecutor 的状态数据。
- **AcquisitionReportPaths 不支持多版本**：`OUTPUT_DIRECTORY` 硬编码为 `outputs/reports/v0.6.0`。v0.7.0 和 v0.8.0 的数据需分别输出到各自版本目录，但当前路径逻辑不支持版本参数。
- **数据质量门禁未感知 TPE 扩展字段**：G1-G6 检查 profile 覆盖、snapshot 计数、时间序和 metadata 完整性，但不知道 `poolSize`、`completedTaskCount` 等字段是否从真实 TPE 采集到了有效值。在 v0.6.0 的探针基线中这些字段永远为 null，门禁并不关心。在 v0.8.0 的真实数据采集中，这些字段 non-null 是基本质量要求。

### 1.3 需求判断

此时引入真实数据获取和 metrics 管道集成是合理的下一步，理由：

- v0.7.0 的 `ManagedExecutor` 和 `ManagedExecutorAdjustmentAdapter` 已经验证了单个端到端路径的正确性。
- `15-experiment-data-acquisition-plan.md` 已经完成了完整的方案设计，包括场景矩阵、质量门禁、风险缓解。
- v0.6.0 的 `AcquisitionReportWriter`、`AcquisitionDataQualityValidator`、`AcquisitionReadinessClassifier` 可直接复用，只需扩展而非重写。
- v0.7.0 回溯中 "闭环实验的 PressureSnapshot 不经过 metrics 管道" 是明确记录的残余风险，本版本直接处置。
- 不修改 `ScenarioExperimentRunner`、不引入新外部依赖、不做 queue resizing — 风险可控。

## 2. 范围

### 2.1 范围内

- `ManagedExecutorConfig` record，封装 ManagedExecutor 创建参数（core, max, keepAlive, queue）。
- `ManagedExecutorScenarioRunner`，在真实 TPE 上运行 STEADY/RAMP/BURST 三种场景。
- `ManagedExecutorScenarioRunnerTest`，集成测试验证 runner 正确性和各 profile 行为。
- `SnapshotAssembler.fromExecutorState(ExecutorStateSnapshot)` 工厂方法。
- `AcquisitionReportPaths.forVersion(String versionTag)` 静态工厂。
- `AcquisitionDataQualityValidator` 扩展 G7/G8/G9 门禁。
- 执行 9 个真实数据获取 run（3 profiles × 3 seeds），产出标准化报告 artifact。
- 现有 412 测试无回归。

### 2.2 范围外

- Queue resizing（queue capacity 动态修改）。
- 闭环调度器/控制器（自动连续运行、定时触发）。
- 持久化（数据库、文件存储）。
- REST / API / UI 暴露。
- 生产环境集成。
- 外部依赖引入。
- Rejection policy 运行时切换。
- 多执行器协调或分布式场景。
- Throughput improvement claim。
- CLI/main 入口（通过 JUnit 测试执行数据获取）。
- 修改 `ScenarioExperimentRunner` 或 `BaselineWorkloadExecutor`。

### 2.3 术语

| 术语 | 定义 |
|---|---|
| ManagedExecutorConfig | 不可变 record，封装创建 ManagedExecutor 所需的全套参数 |
| ManagedExecutorScenarioRunner | 在真实 ManagedExecutor 上按 profile 规则提交阻塞任务、采样、记录的核心 runner |
| Step-level latch | 每个 step 独立的 `CountDownLatch`，用于在采样后统一释放该步提交的所有阻塞任务 |
| Metrics pipeline integration | 在 `SnapshotAssembler` 新增 `fromExecutorState()` 方法，消除手动构造 `PressureSnapshot` |
| G7-G9 gates | 针对真实 TPE 数据的质量门禁：扩展字段 non-null (G7)、queue pressure 证据 (G8)、线程泄漏 (G9) |
| Report path versioning | `AcquisitionReportPaths.forVersion(versionTag)` 支持多版本输出目录并存 |
| Blocking task model | 提交到 `ManagedExecutor` 的 `await(latch)` 任务，阻塞在 CountDownLatch 上直到采样完成 |

## 3. IR 条目草案

### IR-v0.8-001 ManagedExecutorConfig

系统需要 `ManagedExecutorConfig` record 封装 ManagedExecutor 的创建参数，供 runner 和其他调用方使用。

候选验收语义：

- 必须包含字段：`corePoolSize` (int, > 0)、`maximumPoolSize` (int, >= corePoolSize)、`queueCapacity` (int, >= 0)、`keepAliveTime` (long, >= 0)、`keepAliveTimeUnit` (TimeUnit, non-null)。
- 必须提供紧凑构造器或工厂方法，在构造时验证所有不变量。
- 必须提供 `toManagedExecutor()` 方法，使用配置参数创建对应的 `ManagedExecutor` 实例（使用 `LinkedBlockingQueue`，默认 threadFactory 和 AbortPolicy）。
- 必须提供 `toPresetSummary()` 方法，返回 `RunManifest.BaselinePresetSummary`（复用 v0.6.0 的 manifest 结构）。
- 必须不可变（record 或 final class with final fields）。

优先级：P0。

### IR-v0.8-002 ManagedExecutorScenarioRunner

系统需要 `ManagedExecutorScenarioRunner` 在真实 `ManagedExecutor` 上运行 STEADY/RAMP/BURST 三种场景，每步提交阻塞任务、等待线程调度、采样真实 TPE 状态、释放任务，最终产出 `ScenarioRunOutcome`。

候选验收语义：

- 必须接受构造参数：`ExperimentCoordinator`、`ScenarioPlanner`（复用 `DeterministicScenarioPlanner`）、`PressureSampler`（复用 `ManualPressureSampler`）、`EvidenceRecorder`、`Supplier<Instant>` clock。
- `run(ScenarioDefinition definition, ManagedExecutorConfig config)` 方法必须返回 `ScenarioRunOutcome`。
- `ExecutorRegistry` 和 `AtomicDeletionSafety` 由 runner 内部创建，不作为构造参数注入。调用方不感知 registry 的存在。
- Runner 不创建 `ManagedExecutorAdjustmentAdapter`——runner 只采样不调整，通过 `executor.toSnapshot()` 直接读取 TPE 状态。
- 执行流程必须遵循 `15-experiment-data-acquisition-plan.md` 2.2 节定义，简化为 7 个 Phase：
  - Phase 1: 创建 `ManagedExecutor` 并注册到内部 `ExecutorRegistry`
  - Phase 2: 协调 `ExperimentCoordinator` 生命周期（create → start）
  - Phase 3: For each step in `DeterministicScenarioPlanner.plan(definition)`:
    - 按 profile 规则提交阻塞任务（任务在独立 `CountDownLatch` 上 await）
    - 等待线程调度生效（`Thread.sleep(100)` 或等效同步机制；SR 可选择 `startedLatch` 等确定性屏障替代）
    - 通过 `executor.toSnapshot()` 读取真实 TPE 状态
    - 构建 `RuntimeObservation` → `ObservedSnapshot`
    - `EvidenceRecorder.record(snapshot)`
    - `latch.countDown()` 释放该步所有阻塞任务
    - 等待 executor 回到空闲状态（SR 定义空闲判断标准）
  - Phase 4: 协调 `ExperimentCoordinator` 生命周期（stop → finalize）
  - Phase 5: 关闭并终止 `ManagedExecutor`（先 countDown 所有 latch，再 shutdown + awaitTermination）
  - Phase 6: 从 `ExecutorRegistry` 移除（先确认 `isTerminated()`）
  - Phase 7: 返回 `ScenarioRunOutcome`
- STEADY profile：每步固定 2 个阻塞任务，8 steps。
- RAMP profile：第 i 步（0-indexed）提交 `2 + i` 个任务，8 steps。当 `2 + i > queueCapacity + maximumPoolSize` 时，提交 `queueCapacity + maximumPoolSize` 个任务（不抛 `RejectedExecutionException`）。默认配置（core=2, max=4, queue=10）下 `2+7=9 < 14`，cap 不会被触发。
- BURST profile：`i % 3 == 0` 时提交 6 个任务，否则 2 个任务，9 steps。
- 异常路径：若任一步抛出 `RuntimeException`，必须 shutdown executor 并尝试终止（best-effort cleanup），不得泄漏线程。
- 不得在 runner 中执行 policy evaluation 或 adjustment（runner 只采集，不调整）。
- 不得修改 `DeterministicScenarioPlanner` 的 step 生成逻辑。

优先级：P0。

### IR-v0.8-003 ManagedExecutorScenarioRunner 集成测试

系统需要为 `ManagedExecutorScenarioRunner` 提供集成测试，验证三个 profile 的行为正确性。

候选验收语义：

- 必须测试 STEADY profile：验证每个 snapshot 的 `activeCount` >= 0，`queueSize` 在稳态负载下合理。
- 必须测试 RAMP profile：验证后期 step 的 `queueSize` 趋势 > 早期 step（递增压力证据）。
- 必须测试 BURST profile：验证 burst step 的 `queueSize` 趋势 > 普通 step。
- 必须测试 runner 清理：`@AfterEach` 后 executor 已终止、无线程泄漏。
- 必须测试异常清理路径：runner 在异常时正确 shutdown executor。
- 所有测试必须使用真实 `ManagedExecutor`（不可 mock `ThreadPoolExecutor`）。
- 必须遵循 v0.7.0 回溯 P6 修复：`@AfterEach` 中先释放所有 latch 再 shutdown + awaitTermination。

优先级：P0。

### IR-v0.8-004 Metrics 管道集成

系统需要在 `SnapshotAssembler` 中新增从 `ExecutorStateSnapshot` 构建 `ObservedSnapshot` 的方法，消除闭环实验和 runner 中手动构造 `PressureSnapshot` 的重复代码。

候选验收语义：

- `SnapshotAssembler` 接口必须新增 `fromExecutorState(String runId, ExecutorStateSnapshot state)` 默认方法。
- `DefaultSnapshotAssembler` 必须实现该方法，转换规则：
  - `activeThreads` ← `state.activeCount()`，若 null 则 `MetricValue.absent()`
  - `poolSize` ← `state.poolSize()`，若 null 则 `MetricValue.absent()`
  - `queueSize` ← `state.queueSize()`，若 null 则 `MetricValue.absent()`
  - `completedTaskCount` ← `state.completedTaskCount()`，若 null 则 `MetricValue.absent()`
  - `cpuUtilization` ← `MetricValue.absent()`
  - `timestamp` ← `state.observedAt()`
- 转换结果必须可通过 `PressureSnapshot` 正常访问。
- 默认方法确保现有 `SnapshotAssembler` 实现者不被迫修改（二进制兼容）。
- `ManualPressureSampler` 必须支持直接接受 `ExecutorStateSnapshot` 的 `sample()` 重载。
- 不得修改现有 `assemble(String, RuntimeObservation)` 方法签名。
- 不得在 `SnapshotAssembler` 中引入 `ManagedExecutor` 依赖（只依赖 `ExecutorStateSnapshot`，它在 `experiment.adjustment` 包中）。

优先级：P0。

### IR-v0.8-005 AcquisitionReportPaths 版本化

系统需要支持按版本标签参数化输出目录，v0.7.0 和 v0.8.0 的数据分别输出到各自版本目录。

候选验收语义：

- `AcquisitionReportPaths` 必须新增 `forVersion(String versionTag)` 静态工厂方法。
- `forVersion("v0.8.0")` 返回的 `OUTPUT_DIRECTORY` 等效于 `"outputs/reports/v0.8.0"`。
- 无参行为必须保持向后兼容：不传版本时 `OUTPUT_DIRECTORY` 仍为 `"outputs/reports/v0.6.0"`。
- 版本标签验证：必须拒绝含路径分隔符（`/`、`\`）或 `..` 的 versionTag。
- `reportDirectory(Path outputRoot)` 方法必须接受版本化目录路径。
- 现有 `AcquisitionContractsTest` 中的路径断言必须不经修改即可通过（向后兼容）。
- 不得支持自动版本推断（版本标签必须由调用方显式传入）。

优先级：P1。

### IR-v0.8-006 数据质量门禁扩展（G7-G9）

系统需要在 `AcquisitionDataQualityValidator` 中新增 3 个针对真实 TPE 数据的质量门禁。

候选验收语义：

- G7（扩展字段 non-null）：`AcquisitionDataSet.RunSnapshot` 新增可选字段 `Map<String, Boolean> extendedFieldPresence`，默认值为空 Map（nullable，null 等同于空 Map）。Map 的 key 使用 `ExecutorStateSnapshot` 的 getter 名：`"poolSize"`, `"completedTaskCount"`, `"keepAliveTimeSeconds"`, `"largestPoolSize"`, `"taskCount"`。value 为 `true` 表示该字段在 run 的所有 snapshot 中均 non-null。若 `extendedFieldPresence` 为空或 null，G7 跳过该 run（向后兼容 v0.6.0 BaselineWorkloadExecutor 数据）。G7 失败条件：`extendedFieldPresence` 非空但任一 required key 的 value 为 `false` 或缺失（P0）。
- G8（queue pressure 证据）：`STEADY` profile 不要求 `queueSize > 0`（稳态无队列堆积是预期行为）。`RAMP` profile 至少 1 个 snapshot 的 `queueSize > 0`。`BURST` profile 至少 2 个 snapshot 的 `queueSize > 0`。全部为 0 则 G8 失败（P1 blocking）。若 run 的 profile 信息不可得，降级为至少 1 个 snapshot `queueSize > 0`。
- G9（无线程泄漏）：runner 的 `@AfterEach` / cleanup 路径验证 `executor.isTerminated() == true` 且 `registry.size() == 0`。此门禁在 runner 层面保证，validator 接收 `threadLeakFree: boolean` 标记确认（P0）。
- `AcquisitionDataSet.RunSnapshot` 可能需要新增 `extendedFieldPresence` 和 `threadLeakFree` 字段（SR 确认具体设计）。
- 不得删除或弱化现有 G1-G6 门禁。
- G7-G9 只适用于 ManagedExecutor 数据；BaselineWorkloadExecutor 数据不受影响（G7 字段为 null 是合理的）。

优先级：P0 (G7, G9)，P1 (G8)。

### IR-v0.8-007 Runner-to-Report Bridge

系统需要将 `ManagedExecutorScenarioRunner` 的产出（`ScenarioRunOutcome` + `EvidenceRecorder` 中的 snapshots）桥接到 v0.6.0 的 acquisition report 流水线，产出标准化的 5 个 JSON artifact。

候选验收语义：

- Runner 完成后，必须从 `EvidenceRecorder.snapshots(runId)` 提取所有 `ObservedSnapshot`。
- 必须聚合 snapshot 数据为 `PressureSummary`：
  - `totalSnapshotCount` = snapshots 数量
  - `peakObservedQueueDepth` = max(queueSize 在所有 snapshot 中)
  - `meanObservedQueueDepth` = mean(queueSize 在所有 snapshot 中)
  - `scaleEventCount` = 0（runner 不执行调整，仅采集）
  - `scaleUpCount` = 0, `scaleDownCount` = 0
- 必须从 `ManagedExecutorConfig` + `ScenarioDefinition` + 环境信息构建 `RunManifest`：
  - `runId` 和 `scenarioId` 来自 `ScenarioRunOutcome`
  - `scenarioProfile` 来自 `ScenarioDefinition.profile()`
  - `seed` 来自 `ScenarioDefinition.seed()`
  - `stepCount` 来自 `ScenarioRunOutcome.completedStepCount()`
  - `baselinePolicyId` 使用 `ManagedExecutorConfig.toPresetSummary().policyId()`
  - `baselinePreset` 使用 `ManagedExecutorConfig.toPresetSummary()`
  - `environmentSummary` 来自 `System.getProperty()` 采集
  - `commandLine` 来自运行时参数或占位值
- 必须调用 `AcquisitionReportWriter.writeAll(manifest, pressureSummary, replaySummary, readinessSummary, evidenceIndex)` 产出 5 个 JSON artifact。
- `ReplaySummary` 在 runner-only 模式下填默认值（`evidenceCount`=snapshotCount, `decisionCount`=0, 因为没有 policy replay；其他计数字段填 0）。
- `ReadinessSummary` 在 runner-only 模式下不产出（或使用 `NOT_EVALUATED` 占位状态）。
- 此桥接逻辑归属由 SR 确定：可作为 runner 的内部 finalize 步骤，也可作为独立后处理步骤由调用方执行。

优先级：P0。

## 6. 风险和延期项

| 风险 | 当前判断 | 后续触发条件 |
|---|---|---|
| 线程调度不确定性导致 G8 (queue pressure) 偶发失败 | P1 风险 | SR 可降低 G8 阈值或使用 CountDownLatch 同步屏障替代 sleep |
| RAMP 场景后期任务数超 queueCapacity + max 导致 RejectedExecutionException | P1 风险 | SR 确认 capping 策略：hard cap 还是 LinkedBlockingQueue 容量扩大 |
| 9 个 run 的执行时间过长（每个 step 有 100ms sleep） | P2 风险 | SR 可减少 step 数或调整 sleep 策略 |
| `fromExecutorState()` 默认方法语义与某些 `SnapshotAssembler` 实现不兼容 | P2 风险 | 默认方法提供标准实现，自定义实现可覆盖 |
| `RunSnapshot` 扩展（新增 `extendedFieldPresence` 等字段）影响现有测试 | P1 风险 | SR 确认扩展方式：新增可选字段 vs 新建子类 |
| 把数据获取的实验结果误读为生产性能基准 | P0 风险 | 文档必须明确禁止 performance claim |
