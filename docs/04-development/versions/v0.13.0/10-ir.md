# v0.13.0 IR 需求分析草案

## Header

- Document type: IR requirement draft
- Version name: `v0.13.0`
- Status: `DRAFT`
- Current phase: `PRESSURE_CLASSIFICATION_REQUIREMENT_DRAFT`
- Authoring date: `2026-06-14`
- Current conclusion: 本文只定义 pressure classification and policy scoring 需求，不授权 SR、OpenSpec change、Java 实现

## 1. 需求来源

### 1.1 项目现状

v0.12.0 交付了 baseline comparison experiment framework — 系统可以在同一 workload 下运行 baseline executor 和 managed executor，产出 NormalizedComparisonMetrics 和 ComparisonReportArtifact。v0.11.0 交付了持久化证据录制和自主采样（LivePressureSampler）。v0.4.0 交付了 ThresholdPolicyEvaluator（单快照阈值评估）。

系统已具备完整的"采样 → 录制 → 比较"流水线，但缺少诊断层：

1. `ThresholdPolicyEvaluator` 根据单快照阈值做出 SCALE_UP/SCALE_DOWN/HOLD 决策，但从不说"当前处于 overload 状态"或"正经历 queue buildup"。策略评估关注"应该做什么"，不关注"现在是什么状态"。

2. 评估器仅检查单个 `PressureSnapshot` 的即时值，无法区分"队列正在增长"（trend）和"队列稳定但高"（steady state）——这两种状态需要不同的策略响应。

3. 当存在多个 `ThresholdPolicyConfig` 变体时，系统无法评估哪个策略更适合当前压力状态。没有策略评分或排序机制。

4. `PressureSnapshot.cpuUtilization` 字段自 v0.1.0 起定义但始终为 `0.0`，因为 `RuntimeObservation.fromExecutor()` 始终将其设置为 `MetricValue.absent()`。

### 1.2 结构性缺口

五个具体缺口在 `00-objectives-and-scope.md` §1.2 中已描述：

1. **无压力状态分类** — `ThresholdPolicyEvaluator` 做二值决策但不做状态分类。缺少 `PressureState` 枚举和 `PressureClassifier`，无法将快照序列映射到语义化压力状态标签（如 "QUEUE_BUILDUP"、"OVERLOAD"、"RECOVERY"）。

2. **无趋势分析** — 现有评估器仅检查单快照即时值。缺少对快照时间序列的 delta 分析（连续快照间 queueSize 变化率、activeThreads 变化率），无法区分"队列增长中"和"队列稳定但高"。

3. **无策略评分** — 多个 `ThresholdPolicyConfig` 变体之间无法比较优劣。缺少 `PolicyScorer`（多维度评分）和 `PolicyRanker`（排序）。

4. **无归一化压力指标** — `NormalizedComparisonMetrics`（v0.12.0）服务于 A-vs-B 比较，不含派生分类信号（queueGrowthRate, threadUtilizationRatio）。需要一个专门用于分类器输入的 `NormalizedPressureMetrics`。

5. **CPU 利用率数据缺失** — `PressureSnapshot.cpuUtilization` 始终为 0.0（DFR-01）。缺少 `SystemCpuProbe` 和到 `RuntimeObservation` 的集成。

### 1.3 为什么是现在

- v0.12.0 完成了比较框架，系统能用数据证明"managed vs baseline"的差异，但无法诊断"当前是什么压力状态"并据此选择策略
- roadmap 将 v0.13.0 定位为 v0.14.0（adaptive closed-loop adjustment）的直接前置——必须先有诊断层，才能安全地做闭环决策
- 压力分类是安全闭环调整的前提：在不知道"现在是什么状态"之前，不应让系统自主调整 executor 参数
- 策略评分是策略选择的依据：闭环调整需要从多个候选策略中选择最优策略，评分提供了选择标准
- CPU utilization 是区分"CPU 密集型过载"和"IO 等待型队列堆积"的关键信号
- 现有 708 测试提供充分的回归安全保障

## 3. IR 条目草案

### IR-v0.13-001 PressureState 枚举

系统需要 `PressureState` 枚举定义 6 个语义化压力状态标签。

候选验收语义：

- `PressureState` 枚举值：
  - `UNDER_UTILIZED` — 线程空闲，队列空或接近空，资源利用不足
  - `NORMAL` — 平衡状态：线程工作中，队列在可管理范围内
  - `QUEUE_BUILDUP` — 队列持续增长中（正增长率），线程尚未完全饱和
  - `OVERLOAD` — 线程高度饱和，队列深度高，可能接近拒绝边界
  - `REJECTION_ACTIVE` — 检测到任务拒绝（仅 managed executor 可能触发）
  - `RECOVERY` — 先前处于 OVERLOAD/QUEUE_BUILDUP/REJECTION_ACTIVE，现在线程和队列均在减少
- 枚举值顺序即为分类优先级（从高到低）：REJECTION_ACTIVE > OVERLOAD > QUEUE_BUILDUP > RECOVERY > UNDER_UTILIZED > NORMAL
- RECOVERY 和 QUEUE_BUILDUP 使用纯趋势特征（queueGrowthRate 方向），不依赖跨调用状态
- 每个枚举值有一个 `description()` 方法返回人类可读的中文或英文描述
- 枚举定义在 `experiment.classification` 包

优先级：P0。

### IR-v0.13-002 PressureClassifier 接口和 SnapshotPressureClassifier

系统需要 `PressureClassifier` 接口和趋势感知的 `SnapshotPressureClassifier` 实现，从快照时间序列分类压力状态。

候选验收语义：

- `PressureClassifier` 接口方法：
  ```java
  PressureClassification classify(List<ObservedSnapshot> snapshots, ClassifierConfig config);
  ```
- `SnapshotPressureClassifier` 实现必须：
  1. 从快照列表计算 `NormalizedPressureMetrics`（含 queueGrowthRate, threadUtilizationRatio）
  2. 检查拒绝信号：如果 `rejectedTaskCount > 0`（且 rejectionWindowSize 个快照内有拒绝相关特征）→ REJECTION_ACTIVE
  3. 计算趋势：对最近 trendWindowSize 个快照的 queueSize 做线性回归，得到 queueGrowthRate
  4. 应用触发条件规则（按优先级）：
     - REJECTION_ACTIVE: rejectedTaskCount > 0（通过 withRejectedTaskCount() 注入后）
     - OVERLOAD: threadUtilizationRatio >= 0.8 且 maxQueueDepth >= queueCapacity * 0.5。当 queueCapacity == Integer.MAX_VALUE（无界队列）时，退化为 threadUtilizationRatio >= 0.8 且 maxQueueDepth > 0。当 queueCapacity == 0（SynchronousQueue）时，threadUtilizationRatio >= 0.8 即触发
     - QUEUE_BUILDUP: queueGrowthRate > queueGrowthThreshold 且 threadUtilizationRatio < 0.8
     - RECOVERY: queueGrowthRate < -queueGrowthThreshold（队列显著下降）且 threadUtilizationRatio < 0.5 且 maxQueueDepth > 0（曾有队列压力证据——区分于始终空闲的 UNDER_UTILIZED）
     - UNDER_UTILIZED: threadUtilizationRatio < 0.3 且 maxQueueDepth == 0 且 rejectedTaskCount == 0
     - NORMAL: fallback（以上条件均不满足）
  5. 计算置信度（0.0-1.0）：基于条件匹配的充分程度
  6. 组装 evidence 列表（触发条件、当前值、阈值）
- 短序列处理（< trendWindowSize 个快照）：
  - 退化为单快照分类（trend 相关信号使用 0）
  - 置信度降低（乘以 `snapshots.size() / trendWindowSize`）
  - 不抛异常
- 空快照列表：返回 NORMAL 状态，confidence=0.0
- `SnapshotPressureClassifier` 是无状态实现（可安全共享）
- 不得依赖外部配置文件或数据库
- 不使用反射或动态代理

优先级：P0。

### IR-v0.13-003 PressureClassification 和 ClassifierConfig

系统需要 `PressureClassification` record 承载分类结果，以及 `ClassifierConfig` record 提供分类器配置。

候选验收语义：

- `PressureClassification` record 字段：
  - `state`: PressureState — 分类结果状态
  - `confidence`: double — 置信度 [0.0, 1.0]
  - `evidence`: List\<String\> — 分类依据列表（人类可读），不可变
  - `metrics`: NormalizedPressureMetrics — 分类时计算的指标
  - `classifiedAt`: Instant — 分类时间戳
- `PressureClassification` 构造时验证：
  - `state` 非 null
  - `confidence` 在 [0.0, 1.0] 范围内，越界抛出 IllegalArgumentException
  - `evidence` 非 null（可为空列表）
  - `metrics` 非 null
  - `classifiedAt` 非 null
- `ClassifierConfig` record 字段：
  - `trendWindowSize`: int — 趋势计算窗口（快照数），必须 >= 2，默认 5
  - `queueGrowthThreshold`: double — 队列增长率阈值（/快照），默认 0.1
  - `rejectionWindowSize`: int — 拒绝检测窗口（快照数），必须 >= 1，默认 10
  - `queueCapacity`: int — executor 的队列容量，用于 OVERLOAD 条件中的相对阈值计算。默认 `Integer.MAX_VALUE`（表示无界队列——此时相对阈值退化为绝对条件）
- `ClassifierConfig` 提供静态工厂方法 `defaults()` 返回默认配置
- 两个 record 均为不可变

优先级：P0。

### IR-v0.13-004 NormalizedPressureMetrics

系统需要 `NormalizedPressureMetrics` record 提供分类器输入的归一化压力指标。

候选验收语义：

- `NormalizedPressureMetrics` record 字段（11 个）：
  - `completedTaskCount`: long — 完成任务总数
  - `rejectedTaskCount`: long — 拒绝任务数
  - `avgQueueDepth`: double — 所有 snapshot 的 queueSize 平均值
  - `maxQueueDepth`: int — 所有 snapshot 的 queueSize 最大值
  - `totalDurationMs`: long — 总运行时长（milliseconds）
  - `throughputPerSecond`: double — `completedTaskCount / (totalDurationMs / 1000.0)`
  - `avgActiveThreads`: double — 所有 snapshot 的 activeThreads 平均值
  - `maxPoolSize`: int — 所有 snapshot 的 poolSize 最大值
  - `snapshotCount`: int — 快照总数
  - `queueGrowthRate`: double — 最近 trendWindowSize 个快照的 queueSize 线性回归斜率（每快照增长率）
  - `threadUtilizationRatio`: double — `avgActiveThreads / maxPoolSize`（maxPoolSize==0 时返回 0.0）
- 静态工厂方法 `fromSnapshots(List<ObservedSnapshot> snapshots, long totalDurationMs, int fallbackPoolSize, int trendWindowSize)` 必须：
  - 从快照列表计算所有 11 个指标
  - 前 9 个基础指标与 `NormalizedComparisonMetrics.fromSnapshots()` 使用相同的计算逻辑
  - `queueGrowthRate` 使用最近 trendWindowSize 个快照的 queueSize 值进行简单线性回归（最小二乘）
  - `threadUtilizationRatio` = `avgActiveThreads / maxPoolSize`（maxPoolSize == 0 时返回 0.0）
  - 空快照列表：返回所有值为 0 的 metrics（除 `totalDurationMs` 保留外部传入值）
  - `totalDurationMs == 0` 时 `throughputPerSecond == 0.0`（不除零）
  - `trendWindowSize <= 0` 时 `queueGrowthRate == 0.0`
- 实例方法 `withRejectedTaskCount(long rejected)`：
  - 返回新的 `NormalizedPressureMetrics` 实例，`rejectedTaskCount` 设置为传入值，其他 10 个字段保持不变
  - 与 `NormalizedComparisonMetrics.withRejectedTaskCount()` 模式一致（v0.12.0）
  - `fromSnapshots()` 中 `rejectedTaskCount` 初始为 0——消费方需从 `ScenarioRunOutcome.rejectedTaskCount()` 获取真实值并通过此方法注入
- `NormalizedPressureMetrics` 与 `NormalizedComparisonMetrics` 在类型系统中无继承关系（独立 record）
- 不可变 record

优先级：P0。

### IR-v0.13-005 PolicyScore、PolicyScorer 和 ThresholdPolicyScorer

系统需要策略评分模型。

候选验收语义：

- `PolicyScore` record 字段：
  - `policyId`: String — 策略标识
  - `compositeScore`: double — 综合评分 [0.0, 1.0]
  - `responsivenessScore`: double — 响应性维度 [0.0, 1.0]
  - `safetyScore`: double — 安全性维度 [0.0, 1.0]
  - `stabilityScore`: double — 稳定性维度 [0.0, 1.0]
  - `efficiencyScore`: double — 效率维度 [0.0, 1.0]
  - `explanation`: String — 人类可读的评分解释
- `PolicyScore` 构造时验证：
  - `policyId` 非 null、非 blank
  - 所有评分在 [0.0, 1.0] 范围内
  - `compositeScore` 应近似等于 `responsivenessScore * 0.35 + safetyScore * 0.30 + stabilityScore * 0.20 + efficiencyScore * 0.15`（允许微小浮点误差）
- `PolicyScorer` 接口方法：
  ```java
  PolicyScore score(PressureClassification classification, ThresholdPolicyConfig config);
  ```
- `ThresholdPolicyScorer` 实现必须按以下 4 维度评分：

| 维度 | 权重 | 评分逻辑 |
|---|---|---|
| Responsiveness | 0.35 | 策略阈值与当前压力水平的匹配度。scaleUpActiveThreadsThreshold 与当前 activeThreads 的距离、scaleUpQueueSizeThreshold 与当前 queueSize 的距离。阈值越接近实际压力水平（但不低于），分数越高。OVERLOAD 状态下激进的 scale-up 策略（低阈值）得分高 |
| Safety | 0.30 | 相对于当前压力状态的合理性检查：（1）容量充足性：maxPoolSize < metrics.maxPoolSize() 时策略无法容纳当前负载 → safety 降低；（2）步长合理性：scaleStep > maxPoolSize * 0.5 时可能导致剧烈波动 → safety 降低；（3）边界合理性：maxPoolSize > 128 或 maxPoolSize < 1 时超出系统安全边界 → safety 降低 |
| Stability | 0.20 | scaleStep 与 queueGrowthRate 的匹配度。高波动压力（|queueGrowthRate| > 0.5）+ 大步长（scaleStep > 4）→ 低分。低波动 + 适中步长 → 高分 |
| Efficiency | 0.15 | maxPoolSize 相对于 metrics().maxPoolSize()（观测到的最大池大小）的过度配置程度。maxPoolSize >> metrics().maxPoolSize() → 低分。maxPoolSize 接近 metrics().maxPoolSize() → 高分 |

- `ThresholdPolicyScorer` 构造时接受权重配置（默认使用上述权重），允许覆盖
- 综合评分 = 各维度加权和
- 评分过程不得修改 policy config 或 classification
- 所有 scored policy 必须以 `explanation` 字段提供人类可读的解释
- 不得依赖外部服务或机器学习模型

优先级：P0。

### IR-v0.13-006 PolicyRanker

系统需要策略排序器对多个策略配置评分并排序。

候选验收语义：

- `PolicyRanker` 类：
  - 构造参数：`PolicyScorer scorer`
  - `rank(PressureClassification classification, List<ThresholdPolicyConfig> candidates)` 方法必须：
    - 对每个 candidate 调用 `scorer.score(classification, candidate)`
    - 按 `compositeScore` 降序排序（高分在前）
    - 返回 `List<PolicyScore>`（不可变副本）
    - 空 candidates 列表返回空列表（不抛异常）
  - `best(PressureClassification classification, List<ThresholdPolicyConfig> candidates)` 方法必须：
    - 返回排序后的第一个（最高分），包装为 `Optional<PolicyScore>`
    - 空列表返回 `Optional.empty()`
- 如果两个策略得分相同，保持原始输入顺序（稳定排序）
- 排序过程不得修改任何输入参数

优先级：P0。

### IR-v0.13-007 SystemCpuProbe 和 RuntimeObservation 集成

系统需要真实 CPU 利用率数据源。

候选验收语义：

- `SystemCpuProbe` 类：
  - 构造时获取 `OperatingSystemMXBean`（通过 `ManagementFactory.getOperatingSystemMXBean()`）
  - `sampleProcessCpuLoad()` 方法必须：
    - 如果 `osBean` 是 `com.sun.management.OperatingSystemMXBean` 实例：
      - 调用 `getProcessCpuLoad()` 获取进程级 CPU 使用率
      - 返回值为 double [0.0, 1.0]
      - 如果返回 < 0（表示不可用）→ 返回 0.0
    - 如果 `osBean` 不是 Sun 扩展（非 Sun JDK）→ 返回 0.0
  - `sampleSystemCpuLoad()` 方法必须：
    - 调用 `osBean.getSystemLoadAverage()`
    - 返回值为 double，< 0 时返回 0.0
  - 两个方法均为无参、无副作用、线程安全
  - 不执行任何 I/O 或网络调用
  - 不缓存历史值（每次调用读取最新值，除非性能需要——但必须记录原因）

- `RuntimeObservation` 修改（`fromExecutor()` 工厂方法）：
  - **新增重载方法** `fromExecutor(ManagedExecutor executor, Instant timestamp, SystemCpuProbe cpuProbe)`：
    - 使用传入的 `cpuProbe.sampleProcessCpuLoad()` 填充 `cpuUtilization`
    - 如果 CPU 读取返回 < 0 或 probe 为 null，`cpuUtilization` 保持 `MetricValue.absent()`
  - **保持原方法签名** `fromExecutor(ManagedExecutor executor, Instant timestamp)` 不变：
    - 内部委托到重载方法：`return fromExecutor(executor, timestamp, new SystemCpuProbe())`
    - 行为变更：`cpuUtilization` 从始终 absent → 变为调用真实 CPU probe
  - **向后兼容性**：`DefaultSnapshotAssembler` 已正确处理 absent → 0.0 映射，无需修改
  - **测试可注入性**：测试可通过重载方法注入 mock `SystemCpuProbe`（返回固定值），实现可重现测试

- `DefaultSnapshotAssembler`：无需修改——其 `resolveDoubleOrDefault(MetricValue<Double>, double)` 方法已正确处理 absent → 0.0 映射

优先级：P0。

### IR-v0.13-008 端到端验证

系统需要端到端集成测试验证分类→评分→排序完整链路。

候选验收语义：

- 测试 1：PressureState 枚举完整性
  1. 验证 6 个枚举值均存在
  2. 验证优先级序：REJECTION_ACTIVE > OVERLOAD > QUEUE_BUILDUP > RECOVERY > UNDER_UTILIZED > NORMAL
  3. 验证每个值的 description() 非空

- 测试 2：SnapshotPressureClassifier 全状态分类
  1. 构造 UNDER_UTILIZED 快照序列（activeThreads=0, queueSize=0, 5+ 快照）→ 验证分类结果 = UNDER_UTILIZED，confidence > 0.8

  3. 对 NORMAL 状态：适中策略的 stabilityScore > 激进或保守策略

## 6. 风险和延期项

| 风险 | 当前判断 | 后续触发条件 |
|---|---|---|
| 分类器准确性与人工标注的一致性 | P2 风险 | 6 种状态的触发条件基于启发式规则（阈值 + 趋势），未使用机器学习。阈值的具体数值（如 threadUtilizationRatio >= 0.8）可在 SR 阶段微调。分类器可为每个分类提供 evidence 列表供人工审查 |
| `NormalizedPressureMetrics` 与 `NormalizedComparisonMetrics` 的 9 字段重复 | P2 风险 | 两个 record 在类型系统中独立，但 9 个基础字段命名和语义相同。如果未来 NormalizedComparisonMetrics 增加新字段，NormalizedPressureMetrics 需手动同步。当前版本不引入继承/组合，避免耦合。SR 可考虑提取公共接口 |
| `SystemCpuProbe` 在非 Sun JDK 上返回 0.0 | P2 风险 | 主流 OpenJDK 发行版（Eclipse Temurin, Amazon Corretto, Oracle OpenJDK）均包含 `com.sun.management` 扩展。仅在极罕见的非 Sun API JVM 上会 fallback 到 0.0。`sampleSystemCpuLoad()` 提供 Unix fallback |
| `queueGrowthRate` 线性回归精度 | P3 风险 | 对 trendWindowSize 个点的简单线性回归在短窗口中可能对极值敏感。分类器使用 queueGrowthRate 仅判断方向（正/负/~0），不要求高精度。使用最小二乘斜率，不实现权重回归 |
| REJECTION_ACTIVE 状态的检测依赖 rejectedTaskCount 数据 | P2 风险 | `ManagedExecutor.getRejectedTaskCount()`（v0.12.0 IR-v0.12-009 添加）提供此数据。baseline executor 的 rejectedTaskCount 始终为 0。分类器通过 `NormalizedPressureMetrics.rejectedTaskCount > 0` 检测拒绝 |
| 分类器对 scenario-specific 参数的依赖 | P3 风险 | OVERLOAD 条件中的 `queueCapacity` 和 `maxPoolSize` 从 Metrics 或外部传入的 ClassifierConfig 获取。baseline executor 场景中无真实队列，需使用 preset 的配置值作为 fallback |
