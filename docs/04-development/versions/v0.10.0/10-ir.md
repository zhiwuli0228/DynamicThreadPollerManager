## 1. 需求来源

### 1.1 项目现状

v0.9.0 完成了 queue capacity 动态调整。三个动态配置维度中，两个已兑现：

| 能力 | 动态调整 | 实现版本 |
|---|---|---|
| corePoolSize | 可动态调整 | v0.7.0 (`ScaleAdjustmentCommand`) |
| maximumPoolSize | 可动态调整 | v0.7.0 (`ScaleAdjustmentCommand`) |
| queueCapacity | 可动态调整 | v0.9.0 (`QueueResizeCommand`) |
| keepAliveTime | 可动态调整 | v0.7.0 (`RuntimeSetting`) |
| **rejectionPolicy** | **不可动态调整** | **从未实现** |

### 1.2 结构性缺口

与 v0.9.0 的 queue resize 不同，**rejection policy 替换不需要 executor rebuild**：

- `ThreadPoolExecutor.setRejectedExecutionHandler(RejectedExecutionHandler)` 是 JDK 公开的、线程安全的 mutator（`RejectedExecutionHandler` 字段为 `volatile`）
- Java 标准库提供四种内置策略：`AbortPolicy`（默认）、`CallerRunsPolicy`、`DiscardPolicy`、`DiscardOldestPolicy`
- 但 `ManagedExecutor` 将 `rejectionPolicy` 存储为 `private final`，无公开 setter——调用方无法通过 `ManagedExecutor` 修改策略

两个具体缺口：

1. **ManagedExecutor 无 setter**：`getRejectionPolicy()` 存在但只读；`private final RejectedExecutionHandler rejectionPolicy` 阻止修改
2. **ExecutorRebuildStrategy 硬编码策略丢失**：`rebuild()` 第 75 行使用 `new ThreadPoolExecutor.AbortPolicy()`，导致 queue resize rebuild 后丢失原始 rejection policy。这是一个 v0.9.0 遗留缺陷

### 1.3 为什么是现在

- v0.9.0 完成了三个动态维度中最难的一个（queue resize），证明调整链路成熟
- Rejection policy 替换技术难度远低于 queue resize（JDK 原生支持，无需 rebuild）
- `ExecutorRebuildStrategy` 的策略丢失 bug 是真实缺陷，v0.10.0 是修复的自然时机
- 完成 v0.10.0 后，`DynamicThreadPollerManager` 的三个动态配置维度全部兑现
- `exploration-boundaries.md` 和 `operational-and-evolution-boundaries.md` 的 "Runtime rejection-policy replacement" 禁令可在本版本解除

## 2. 范围

### 2.1 范围内

- `RejectionPolicyCommand` record，封装目标 `RejectedExecutionHandler` 及替换参数
- `ManagedExecutor.setRejectionPolicy(RejectedExecutionHandler)` 方法，委托给底层 TPE
- `RejectionPolicyAdjustmentAdapter`，接收 RejectionPolicyCommand，执行策略替换
- `RejectionPolicySafetyGate`，检查替换操作的安全性
- `PolicyReplacementEvidence` record，记录替换 before/after
- `ExecutorRebuildStrategy` 修复：rebuild 后保留原始 rejection policy
- 端到端集成测试：policy switch → 过载场景 → 验证新策略行为差异可观测
- 现有 476 测试零回归

### 2.2 范围外

- 自定义 `RejectedExecutionHandler` 实现（可接受但不作为设计目标；仅使用 JDK 内置四种策略验证）
- 自动触发 policy 替换（closed-loop controller）
- 多执行器协调 policy 替换
- 持久化 policy 替换历史
- CLI entry
- 生产环境集成
- 新的调整维度（thread count、queue capacity、rejection policy 三者之外）

### 2.3 术语

| 术语 | 定义 |
|---|---|
| RejectionPolicyCommand | 不可变 record，封装目标 RejectedExecutionHandler，类似 QueueResizeCommand 但操作 rejection policy |
| RejectionPolicyAdjustmentAdapter | Adapter，接收 RejectionPolicyCommand，通过 safety gate 评估后调用 ManagedExecutor.setRejectionPolicy() |
| RejectionPolicySafetyGate | 在 policy 替换前评估安全性的门禁：executor 状态、policy 有效性、幂等保护 |
| PolicyReplacementEvidence | policy 替换操作的证据：before/after policy class name、executor state snapshot、timestamp、success |
| setRejectedExecutionHandler | JDK `ThreadPoolExecutor` 公开方法，线程安全（volatile 字段），直接替换 rejection handler |

## 3. IR 条目草案

### IR-v0.10-001 RejectionPolicyCommand

系统需要 `RejectionPolicyCommand` record 封装 rejection policy 替换请求。

候选验收语义：

- 必须包含字段：`targetPolicy` (RejectedExecutionHandler, 非 null)、`reason` (String, 非空)、`createdAt` (Instant)
- 构造时必须验证 `targetPolicy != null`，否则抛出 `NullPointerException`
- 必须提供 `fromCurrent(RejectedExecutionHandler current, RejectedExecutionHandler target, String reason)` 工厂方法：若 `target.getClass() == current.getClass()` 且两者为同类型（例如都是 AbortPolicy），返回 `Optional.empty()`（无需替换）
- 注意：JDK 四种内置策略都是无状态单例（每个 policy 类的行为完全由类决定），因此同类型 = 同行为。但自定义 RejectedExecutionHandler 可能有状态——IR 阶段识别此风险，SR 决定是否使用 `equals()` 或仅比较 class
- 不可变（record）
- 不强制要求与 `ScaleAdjustmentCommand` 或 `QueueResizeCommand` 共享基类或接口（三者操作不同维度）

优先级：P0。

### IR-v0.10-002 ManagedExecutor.setRejectionPolicy()

系统需要 `ManagedExecutor` 添加 `setRejectionPolicy(RejectedExecutionHandler)` 方法。

候选验收语义：

- `setRejectionPolicy(RejectedExecutionHandler newPolicy)` 必须：
  - 验证 `newPolicy != null`
  - 调用 `this.executor.setRejectedExecutionHandler(newPolicy)` 委托给底层 TPE
  - 更新 `this.rejectionPolicy = newPolicy`（当前为 `private final`，需改为非 final）
- `getRejectionPolicy()` 在 setter 调用后必须返回新 policy（一致性与 TPE 保持同步）
- `rejectionPolicy` 字段从 `private final` 改为 `private volatile`（与底层 TPE 的 volatile 语义一致）
- 现有构造器和所有 public API 行为不变
- 不得移除或修改现有 `getRejectionPolicy()` 方法签名

优先级：P0。

### IR-v0.10-003 RejectionPolicyAdjustmentAdapter

系统需要 `RejectionPolicyAdjustmentAdapter` 接收 RejectionPolicyCommand 并执行策略替换。

候选验收语义：

- 构造参数：`ExecutorRegistry`、`RejectionPolicySafetyGate`
- `apply(String executorId, RejectionPolicyCommand command)` 方法返回 `PolicyReplacementResult`（专用 result 类型，遵循 v0.9.0 复盘流程改进 #2 "独立 result 类型模式"）
- `apply()` 流程：
  1. 通过 registry 查找目标 ManagedExecutor
  2. 若 executor 不存在 → 返回 `PolicyReplacementResult.failed("EXECUTOR_NOT_FOUND", ...)`
  3. 调用 `RejectionPolicySafetyGate.evaluate(command, executor)`
  4. 若 DENY → 返回 `PolicyReplacementResult.denied(gateResult.reason(), evidence)`
  5. 若 PERMIT → 调用 `executor.setRejectionPolicy(command.targetPolicy())`
  6. 记录 `PolicyReplacementEvidence`（before/after policy class name, executor state snapshot）
  7. 返回 `PolicyReplacementResult.success(evidence)`
- 不得绕过 `ManagedExecutor.setRejectionPolicy()` 直接操作底层 TPE
- 不得实现幂等保护（policy 替换不涉及 executor 重建，无并发风险；不同于 QueueResizeAdjustmentAdapter）
- 不得修改现有 `ManagedExecutorAdjustmentAdapter` 或 `QueueResizeAdjustmentAdapter`

优先级：P0。

### IR-v0.10-004 RejectionPolicySafetyGate

系统需要在 policy 替换前评估安全性。

候选验收语义：

- 使用独立接口（不实现 `ControlGate<T>`），遵循 v0.9.0 复盘流程改进 #3 "ControlGate 接口的适用边界"：policy safety gate 不需要 readiness 参数，不需要 ExecutorStateSnapshot，模式与 QueueResizeSafetyGate 相同
- `evaluate(RejectionPolicyCommand command, ManagedExecutor executor)` 方法返回 `EvaluationResult`
- 安全检查至少包括：
  - **Executor 状态**：executor 未 shutdown/terminated → 若已终止则 DENY
  - **Policy 有效性**：`command.targetPolicy() != null`（command 构造时已验证，safety gate 二次确认）
  - **变更检测**：`command.targetPolicy().getClass() != executor.getRejectionPolicy().getClass()` → 同类型则 DENY（no-op）
  - **并发 resize 保护**：若 executor 正在 resize 中，DENY（通过 `QueueResizeAdjustmentAdapter` 的 `resizeInProgress` 标记检查，或独立标记）
- 注意：`QueueResizeAdjustmentAdapter.resizeInProgress` 是 `private` 的 `ConcurrentHashMap`，不可从外部访问。SR 需决定是暴露此状态还是使用独立保护机制
- DENY 结果必须包含明确的拒绝原因字符串
- 不得在 safety gate 中直接修改 executor 状态（只读检查）

优先级：P0。

### IR-v0.10-005 PolicyReplacementEvidence

系统需要为每次 policy 替换操作记录证据。

候选验收语义：

- `PolicyReplacementEvidence` record 必须包含：
  - `beforePolicyClass`: String（旧 policy 的 canonical class name）
  - `afterPolicyClass`: String（新 policy 的 canonical class name）
  - `executorState`: ExecutorStateSnapshot（替换时刻的 executor 状态）
  - `replacedAt`: Instant
  - `success`: boolean
  - `reason`: String
- 通过 `PolicyReplacementResult.evidence()` 携带，不经过 `EvidenceRecorder`（遵循 v0.9.0 IR F04 处置：evidence 通过 result 直接携带，不扩展 EvidenceRecorder 接口）
- `PolicyReplacementEvidence` 不可变（record）

优先级：P1。

### IR-v0.10-006 ExecutorRebuildStrategy 策略保留修复

系统需要修复 `ExecutorRebuildStrategy.rebuild()` 中硬编码 `AbortPolicy()` 的缺陷。

候选验收语义：

- `rebuild()` 第 75 行：将 `new ThreadPoolExecutor.AbortPolicy()` 替换为 `oldTpe.getRejectedExecutionHandler()`
- 修复后，rebuild 生成的 ManagedExecutor 的 rejection policy 与旧 executor 一致
- 不影响现有 queue resize 测试（所有测试使用默认 AbortPolicy，修复后行为不变）
- 新增测试：使用非默认 policy（如 CallerRunsPolicy）的 executor 经过 rebuild 后，新 executor 保持 CallerRunsPolicy

优先级：P0。

### IR-v0.10-007 端到端 Policy 替换验证

系统需要端到端集成测试验证完整的 policy 替换流程。

候选验收语义：

- 测试流程：
  1. 创建 ManagedExecutor（使用 AbortPolicy），注册到 registry
  2. 提交任务填满 queue + 所有线程，触发过载状态
  3. 验证过载时 AbortPolicy 行为：`RejectedExecutionException` 抛出
  4. 发出 RejectionPolicyCommand（targetPolicy=CallerRunsPolicy）
  5. 验证替换成功：`executor.getRejectionPolicy()` 返回 CallerRunsPolicy
  6. 再次提交过载任务，验证 CallerRunsPolicy 行为：无异常（调用方线程执行）
  7. 验证 @AfterEach cleanup（shutdown → awaitTermination → registry.remove）
- 必须测试所有四种 JDK 内置策略的切换：
  - AbortPolicy → CallerRunsPolicy
  - AbortPolicy → DiscardPolicy（验证任务被静默丢弃）
  - AbortPolicy → DiscardOldestPolicy（验证最旧任务被替换）
- 必须测试 safety gate DENY：
  - 对已 shutdown 的 executor 替换 → DENY
  - 替换为相同类型 policy → DENY（no-op 检测）
- 必须测试 ExecutorRebuildStrategy 修复：
  - 创建 executor（CallerRunsPolicy）→ queue resize（EXPAND）→ 新 executor 仍为 CallerRunsPolicy
- 现有 476 测试零回归

优先级：P0。

## 6. 风险和延期项

| 风险 | 当前判断 | 后续触发条件 |
|---|---|---|
| 自定义 RejectedExecutionHandler 的相等性判断 | P2 风险 | JDK 四种内置策略都是无状态单例，class 比较即语义比较。但自定义 handler 可能有状态——`fromCurrent()` 使用 class 比较可能误判为 no-op。SR 决定是否使用 `equals()` 或限制 class 比较仅适用于 JDK 内置策略 |
| Policy 替换与 queue resize 的并发交互 | P1 风险 | 若 queue resize 正在执行（rebuild 中），policy 替换可能在旧 executor（即将被 shutdown）或新 executor（刚创建）上执行。IR-v0.10-004 要求的并发 resize 保护可防御此问题——SR 需设计保护机制 |
| DiscardPolicy/DiscardOldestPolicy 的行为验证 | P2 风险 | 这两种策略静默丢弃任务，可观测信号较弱。端到端测试需通过 task count / queue size 差异间接验证行为——比 AbortPolicy（抛异常）和 CallerRunsPolicy（调用方执行）更难断言 |
| `rejectionPolicy` 字段从 `final` 改为 `volatile` 的兼容性 | P2 风险 | 字段可见性变更不影响公开 API 签名，但若存在序列化/反序列化依赖则需注意。当前项目无序列化需求，风险可控 |

## 9. 当前结论

v0.10.0 IR 草案已定义 runtime rejection-policy replacement 的需求方向：7 条 IR 覆盖 RejectionPolicyCommand（命令封装）、ManagedExecutor.setRejectionPolicy()（API 扩展）、RejectionPolicyAdjustmentAdapter（调整链路集成）、RejectionPolicySafetyGate（安全门禁）、PolicyReplacementEvidence（证据记录）、ExecutorRebuildStrategy 修复（策略保留）、端到端验证（四种策略切换 + rebuild 保留 + DENY 路径）。与 v0.9.0 的关键差异：rejection policy 替换不需要 executor rebuild（TPE 有公开 setter），技术难度显著低于 queue resize。本文不授权实现或 OpenSpec change；下一步是 IR review。
