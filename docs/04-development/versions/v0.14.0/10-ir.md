## 1. 需求来源

### 1.1 项目现状

v0.13.0 交付了压力分类与策略评分诊断层——系统可以分类压力状态（6 种状态 + 置信度）并对多个策略评分排序。v0.12.0 交付了基线比较框架。v0.11.0 交付了自主采样（`LivePressureSampler`）和持久化证据录制。v0.7.0-v0.10.0 交付了三种动态配置能力（pool size、queue capacity、rejection policy）及其 `AdjustmentAdapter` 执行层。

系统已具备完整的"观察→诊断"能力链和"执行"能力，但缺少将两者连接起来的闭环控制器：

1. `LivePressureSampler` 周期性采样，但采样结果需要外部消费。`ThresholdPolicyEvaluator` 生成决策，但决策需要外部触发执行。没有任何组件将采样→分类→评分→决策→执行串联为自主运行的闭环。

2. 现有的 `SafetyGate` 仅校验单次调整的边界合法性（min/max），不检测跨调整的振荡模式（如连续 scale-up→scale-down→scale-up）。

3. `AdjustmentEvidence` 记录单次调整结果，但没有结构化的调整历史来追踪"过去 5 次调整中哪些改善了压力状态"。

4. `SnapshotPressureClassifier` 是无状态的（每次 `classify()` 独立执行），不追踪压力状态之间的转换历史。v0.13.0 DFR-02 将此延后到 v0.14.0。

5. `ThresholdPolicyScorer` 的 4 维评分权重（0.35/0.30/0.20/0.15）是静态的。v0.13.0 DFR-01 要求基于实际调整结果校准权重。

### 1.2 结构性缺口

五个具体缺口在 `00-objectives-and-scope.md` §1.2 中已描述：

1. **无自主循环控制器** — 缺少 `AdjustmentLoop` 管理闭环生命周期（IDLE→RUNNING→PAUSED→STOPPED→EMERGENCY_STOPPED），并周期性编排采样→分类→评分→选择→决策→执行→观察循环。

2. **无振荡防护** — 缺少 `OscillationDetector` 检测跨调整的模式（乒乓振荡、过度调整、策略切换振荡），并在检测到振荡时触发紧急停止。

3. **无调整历史与结果追踪** — 缺少 `AdjustmentHistory` 结构化记录每次调整的 before/after 信息，支持查询"过去 N 次调整的成功率"。

4. **无状态转换模型** — 缺少 `PressureStateMachine` 定义 6 种压力状态之间的合法/异常/非法转换，追踪转换历史。

5. **无反馈驱动的权重校准** — 缺少 `FeedbackCalibrator` 基于调整结果（压力状态是否改善）校准评分权重。

### 1.3 为什么是现在

- v0.13.0 完成了诊断层 — 系统现在能回答"当前是什么状态"和"哪个策略最适合"
- 闭环调整是 roadmap 中诊断层的直接后继 — 没有闭环执行器，分类器和评分器的价值停留在诊断层面
- v0.13.0 DFR-01（权重校准）和 DFR-02（状态转换模型）都明确指向 v0.14.0
- 振荡防护是实现"安全自主调整"的必要前提 — 没有防护的闭环会导致配置振荡
- 现有 774 测试提供充分的回归安全保障
- 闭环控制器不引入新 executor mutation — 仅编排已有组件，风险可控

## 2. 范围

### 2.1 范围内

- `LoopState` enum（IDLE, RUNNING, PAUSED, STOPPED, EMERGENCY_STOPPED）
- `LoopConfig` record（samplingIntervalMs, maxIterations, snapshotWindowSize, oscillationWindowSize, oscillationPatternThreshold, feedbackCalibrationWindow, emergencyStopThreshold, candidatePolicies）
- `LoopSession` record（sessionId, loopConfig, startTime, endTime, adjustmentCount, finalState, summary）
- `AdjustmentLoop` 类（闭环生命周期管理 + 主循环逻辑）
- `DecisionOrchestrator` 类（编排 classification → scoring → ranking → evaluation → decision）
- `AdjustmentDecision` record（classification, selectedScore, selectedPolicy, policyDecision, rationale, decidedAt）
- `PressureStateTransition` record（from, to, timestamp, trigger, legal）
- `PressureStateMachine` 类（合法转换定义 + 转换验证 + 转换历史）
- `OscillationDetector` 类（滑动窗口振荡模式检测）
- `AdjustmentHistory` 类（调整记录存储 + 查询）
- `HistoryWindow` record（窗口大小 + 调整记录列表）
- `FeedbackCalibrator` 类（基于调整结果校准评分权重）
- `LoopEvidenceRecorder` 接口（闭环迭代证据记录）
- `experiment.loop` 新包
- 现有 774 测试零回归

### 2.2 范围外

- 多 executor 并行闭环协调
- 跨进程/分布式闭环调整
- 策略自动生成或参数自动调优（仅权重校准 + 预定义候选列表）
- 闭环性能优化（吞吐量、延迟基准 — v0.13.0 DFR-04）
- 基于比较运行的交叉验证（v0.12.0 comparison 基础设施用于闭环 vs 静态策略比较 — DFR-04 延后）
- 多维度同时调整（单次调整修改单一维度 — DFR-06 延后至 v0.16.0+）
- 闭环与外部监控系统集成
- CLI entry
- 新 executor mutation 或动态配置维度
- 修改 PressureClassifier、PolicyScorer、PolicyEvaluator、PressureSampler、AdjustmentAdapter 接口

| 术语 | 定义 |

| LoopState | 枚举，闭环生命周期状态：IDLE, RUNNING, PAUSED, STOPPED, EMERGENCY_STOPPED |

| DecisionOrchestrator | 编排器，将分类→评分→排序→评估串联为单一 AdjustmentDecision |
| AdjustmentDecision | 不可变 record，单次闭环迭代的决策输出（分类结果 + 选定策略 + 评分 + PolicyDecision + 理由） |

| OscillationDetector | 振荡检测器，从调整历史中检测乒乓振荡、过度调整、策略切换振荡 |
| AdjustmentHistory | 调整历史存储，记录每次调整的决策→命令→结果→后续观察 |
| HistoryWindow | 不可变 record，定义历史窗口大小和包含的调整记录 |
| FeedbackCalibrator | 权重校准器，基于调整后的实际结果调整 ThresholdPolicyScorer 的 4 维评分权重 |
| LoopEvidenceRecorder | 接口，记录闭环迭代证据（decision → result → observation 三元组） |
| Cooldown | 冷却期，两次调整之间的最小间隔，防止过快连续调整 |
| Emergency stop | 紧急停止，当检测到振荡或异常模式时强制停止闭环 |
| Ping-pong oscillation | 乒乓振荡，连续相反的调整方向（A→B→A→B） |
| Over-adjustment | 过度调整，连续同方向调整（scale-up→scale-up→scale-up） |
| Policy switching oscillation | 策略切换振荡，在多个策略间反复切换 |

## 3. IR 条目草案

### IR-v0.14-001 LoopState 枚举和 LoopConfig

系统需要 `LoopState` 枚举定义闭环生命周期状态，以及 `LoopConfig` record 提供闭环配置。

候选验收语义：

- `LoopState` 枚举值：
  - `IDLE` — 初始状态，未启动
  - `RUNNING` — 闭环运行中
  - `PAUSED` — 暂停（保持状态，可恢复）
  - `STOPPED` — 正常停止
  - `EMERGENCY_STOPPED` — 紧急停止（检测到异常模式如振荡）
- 合法转换：
  - `IDLE → RUNNING`
  - `RUNNING → PAUSED`
  - `PAUSED → RUNNING`
  - `RUNNING → STOPPED`
  - `PAUSED → STOPPED`
  - `RUNNING → EMERGENCY_STOPPED`
  - `PAUSED → EMERGENCY_STOPPED`
  - `EMERGENCY_STOPPED → IDLE`（reset）
  - `STOPPED → IDLE`（reset）
- `LoopConfig` record 字段：
  - `samplingIntervalMs`: long — 采样间隔（毫秒），必须 >= 100，默认 2000
  - `maxIterations`: int — 最大迭代次数，0 = 无限，默认 100
  - `snapshotWindowSize`: int — 分类器输入的快照窗口大小，必须 >= 2，默认 20
  - `oscillationWindowSize`: int — 振荡检测窗口（调整次数），必须 >= 4，默认 6
  - `oscillationPatternThreshold`: int — 触发振荡的最小重复次数，必须 >= 1，默认 2
  - `feedbackCalibrationWindow`: int — 权重校准窗口（调整次数），必须 >= 5，默认 10
  - `emergencyStopThreshold`: int — 紧急停止前允许的连续振荡次数，必须 >= 1，默认 2
  - `candidatePolicies`: `List<ThresholdPolicyConfig>` — 候选策略列表，非空

  注：调整冷却不由 `LoopConfig` 管理，而是委托给 `RuntimeAdjustmentSafetyGate` 内置的 cooldown 机制（`SafetyGateConfig.cooldownDecisionIntervals()`）。闭环每次迭代调用 `safetyGate.evaluate()` 时，SafetyGate 在 cooldown 活跃期间返回 `REJECTED`（failureCode=COOLDOWN_ACTIVE）。
- `LoopConfig` 构造时验证所有字段合法性
- `LoopConfig` 提供静态工厂方法 `defaults(List<ThresholdPolicyConfig> candidates)` 返回默认配置（需传入候选策略列表）
- 枚举定义在 `experiment.loop` 包

优先级：P0。

### IR-v0.14-002 AdjustmentLoop 闭环控制器

系统需要 `AdjustmentLoop` 类管理闭环生命周期并执行主循环。

候选验收语义：

- `AdjustmentLoop` 构造参数：
  - `LoopConfig config`
  - `DecisionOrchestrator orchestrator`
  - `ExecutorAdjustmentAdapter adapter`
  - `RuntimeAdjustmentSafetyGate safetyGate`
  - `OscillationDetector oscillationDetector`
  - `AdjustmentHistory history`
  - `LoopEvidenceRecorder evidenceRecorder`
  - `PressureStateMachine stateMachine`
  - `EvidenceRecorder evidenceRecorder`（快照数据源）
  - 通过 `start()` 方法注入：`ManagedExecutor executor`
- `start(ManagedExecutor executor)` 方法：
  - 状态必须为 IDLE → 转换为 RUNNING
  - 创建新的 `LoopSession`（sessionId = UUID，startTime = now）
  - 启动主循环线程（daemon thread，名称 = `"adjustment-loop-" + sessionId`）
  - 返回 `LoopSession`
  - 如果状态不是 IDLE → `IllegalStateException`
- `pause()` 方法：
  - 状态必须为 RUNNING → 转换为 PAUSED
  - 唤醒等待中的循环线程使其检查状态
- `resume()` 方法：
  - 状态必须为 PAUSED → 转换为 RUNNING
  - 唤醒循环线程继续执行
- `stop()` 方法：
  - 状态必须为 RUNNING 或 PAUSED → 转换为 STOPPED
  - 等待循环线程结束（超时 30s）
  - 设置 session.endTime = now
  - 返回最终的 `LoopSession`
- `emergencyStop(String reason)` 方法：
  - 状态必须为 RUNNING 或 PAUSED → 转换为 EMERGENCY_STOPPED
  - 记录 reason 到 session.summary
  - 行为与 `stop()` 类似但标记为紧急
- `reset()` 方法：
  - 状态必须为 STOPPED 或 EMERGENCY_STOPPED → 转换为 IDLE
  - 清除 `AdjustmentHistory`（创建新实例或清空）
  - 重置 `PressureStateMachine`（清除转换历史）
  - 当前 `LoopSession` 置为 null
  - 其他状态调用 → `IllegalStateException`
- 主循环逻辑（在 RUNNING 状态下周期执行）：
  1. 等待 `config.samplingIntervalMs`
  2. 从 `evidenceRecorder.snapshots(runId)` 获取全部快照，取最近 `config.snapshotWindowSize` 个：
     ```
     List<ObservedSnapshot> all = evidenceRecorder.snapshots(session.sessionId());
     int from = Math.max(0, all.size() - config.snapshotWindowSize());
     List<ObservedSnapshot> recent = all.subList(from, all.size());
     if (recent.isEmpty()) continue; // 数据不足
     ```
  3. 调用 `orchestrator.decide(recent, candidates, executor)` → `AdjustmentDecision`
  4. 如果 decision.isNoOp() → 记录 NO_OP iteration，continue
  5. 调用 `oscillationDetector.wouldOscillate(decision, history)`
  6. 如果检测到振荡 → 递增振荡计数；如果 >= `emergencyStopThreshold` → `emergencyStop("oscillation detected")`
  7. 从 decision 构造 `ScaleAdjustmentCommand`：
     `decision.toCommand(executor, session.sessionId(), Instant::now)`
  8. 调用 SafetyGate（3 参数签名）：
     ```
     ExecutorStateSnapshot executorState = adapter.currentState();
     SafetyGateDecision gateDecision = safetyGate.evaluate(command, executorState, loopReadiness);
     ```
     其中 `loopReadiness` 是在 `start()` 中构造的运行时 `ReadinessAssessment`（status=READY, configLabel="runtime-loop", inputRunIds=[sessionId]）
  9. 检查 gateDecision.outcome()：
     - `REJECTED` → 记录 rejected iteration（含 failureCode），continue
     - `NO_OP` → 记录 no-op iteration，continue
     - `ALLOW` → 继续步骤 10
  10. 调用 `adapter.apply(command)` → `AdjustmentResult`
  11. 调用 `safetyGate.recordApplied(gateDecision)` — 更新 SafetyGate 内部 cooldown
  12. 调用 `history.record(decision, result, beforeClassification, afterClassification)`
  13. 调用 `stateMachine.recordTransition(prevClassification, decision.classification, now, decision.selectedScore().policyId())`
  14. 调用 `evidenceRecorder.recordIteration(session, iterationIndex, decision, result, beforeClassification)`
  15. 如果 `history.totalAdjustmentCount() > 0 && history.totalAdjustmentCount() % config.feedbackCalibrationWindow == 0`：
      `ThresholdPolicyScorer newScorer = calibrator.calibrate(history, currentScorer);`
      `orchestrator.updateScorer(newScorer); currentScorer = newScorer;`
  16. 检查 `maxIterations`：如果达到上限 → `stop()`
- `getState()` 返回当前 `LoopState`
- `getCurrentSession()` 返回当前 `LoopSession`（如果在 RUNNING/PAUSED）
- `getHistory()` 返回 `AdjustmentHistory` 引用
- 循环线程必须是 daemon 线程
- 不得依赖外部配置文件或数据库
- 不使用反射或动态代理

优先级：P0。

### IR-v0.14-003 DecisionOrchestrator 和 AdjustmentDecision

系统需要 `DecisionOrchestrator` 编排分类→评分→排序→评估→决策的完整链路。

候选验收语义：

- `DecisionOrchestrator` 构造参数：
  - `PressureClassifier classifier`
  - `PolicyRanker ranker`（内部已持有 PolicyScorer — 无需重复注入）
  - `PolicyEvaluator evaluator`
  - `ClassifierConfig classifierConfig`
- 提供 `updateScorer(PolicyScorer newScorer)` 方法供 `FeedbackCalibrator` 校准后更新 scorer（内部重新创建 PolicyRanker）
- `decide(List<ObservedSnapshot> snapshots, List<ThresholdPolicyConfig> candidates, ManagedExecutor executor)` 方法：
  1. 获取 `rejectedTaskCount`（从 `executor.getRejectedTaskCount()` — v0.12.0 已添加）
  2. 计算 totalDurationMs（从第一个和最后一个 snapshots 的 `snapshot().timestamp()` 时间戳差）
  3. 调用 `classifier.classify(snapshots, classifierConfig, rejectedTaskCount, totalDurationMs)` → `PressureClassification`
  4. 调用 `ranker.rank(classification, candidates)` → 排序后的 `List<PolicyScore>`
  5. 取最高分 → `PolicyScore`，获取其对应的 `ThresholdPolicyConfig`
  6. 从 `snapshots.get(snapshots.size()-1).snapshot()` 获取最后一个 `PressureSnapshot`
  7. 构造 `PolicyEvaluationInput`：`new PolicyEvaluationInput(runId, lastSnapshot, Instant.now())`
  8. 调用 `evaluator.evaluate(input, selectedConfig)` → `PolicyDecision`
  9. 组装 `AdjustmentDecision` 并返回
- `AdjustmentDecision` record 字段：
  - `classification`: `PressureClassification` — 分类结果
  - `selectedScore`: `PolicyScore` — 选定的策略评分
  - `selectedPolicy`: `ThresholdPolicyConfig` — 选定的策略配置
  - `policyDecision`: `PolicyDecision` — 策略评估产生的决策
  - `rationale`: `String` — 人类可读的决策理由
  - `decidedAt`: `Instant` — 决策时间戳
- `AdjustmentDecision` 构造时验证：
  - 所有字段非 null
  - `rationale` 非 blank
- 实例方法：
  - `isNoOp()`: 当 `policyDecision.action() == HOLD` 时返回 true
  - `toCommand(ManagedExecutor executor, String runId, Supplier<Instant> clock)`: 从 `policyDecision` 和 executor 当前状态构造 `ScaleAdjustmentCommand`。`runId` 由 `AdjustmentLoop` 从 `LoopSession.sessionId` 提供（闭环会话本身即实验运行）
    - 如果 `isNoOp()` → 返回 `ScaleAdjustmentCommand.noOp(runId, timestamp, currentPoolSize, reason, sourceRef, clock)`
    - 否则 → 返回 `ScaleAdjustmentCommand.create(runId, timestamp, currentPoolSize, targetPoolSize, reason, sourceRef, clock)`
- 空快照列表（snapshots.isEmpty()）→ `decide()` 返回 NO_OP 决策（NORMAL + HOLD），不抛异常
- `PolicyEvaluationInput` 构造路径已验证（IR review）：`ObservedSnapshot.snapshot()` 返回 `PressureSnapshot`（含 activeThreads, poolSize, queueSize, completedTaskCount, cpuUtilization），直接传入 `PolicyEvaluationInput(String runId, PressureSnapshot snapshot, Instant evaluatedAt)` 构造器。瞬时值（activeThreads, queueSize）由 `PressureSnapshot` 提供，分类器的聚合值（`classification.metrics()`）不用于构造 PolicyEvaluationInput
- 整个 decide() 过程无副作用、不修改任何输入参数
- 不使用反射或动态代理

优先级：P0。

### IR-v0.14-004 PressureStateMachine 状态转换模型

系统需要 `PressureStateMachine` 定义压力状态之间的合法转换并追踪转换历史（承接 v0.13.0 DFR-02）。

候选验收语义：

- `PressureStateMachine` 类：
  - 持有 `List<PressureStateTransition>` 作为转换历史
  - 构造时可选地传入初始状态（或从第一次 `recordTransition` 推断）
- `PressureStateTransition` record 字段：
  - `from`: `PressureState` — 转换前状态
  - `to`: `PressureState` — 转换后状态
  - `timestamp`: `Instant` — 转换时间
  - `trigger`: `String` — 触发此转换的 adjustment decision reference（可选）
  - `legality`: `TransitionLegality` — LEGAL / ANOMALOUS / ILLEGAL
- `TransitionLegality` enum: `LEGAL`, `ANOMALOUS`, `ILLEGAL`
- 合法转换表（见 `00-objectives-and-scope.md` §7.4）：

| 从 | 到 | 合法性 |
|---|---|---|
| 任意 | NORMAL | LEGAL |
| NORMAL | QUEUE_BUILDUP | LEGAL |
| NORMAL | UNDER_UTILIZED | LEGAL |
| NORMAL | OVERLOAD | LEGAL |
| QUEUE_BUILDUP | OVERLOAD | LEGAL |
| QUEUE_BUILDUP | NORMAL | LEGAL |
| OVERLOAD | RECOVERY | LEGAL |
| OVERLOAD | REJECTION_ACTIVE | LEGAL |
| REJECTION_ACTIVE | RECOVERY | LEGAL |
| RECOVERY | NORMAL | LEGAL |
| RECOVERY | UNDER_UTILIZED | LEGAL |
| UNDER_UTILIZED | NORMAL | LEGAL |
| OVERLOAD | NORMAL | ANOMALOUS（跳过 RECOVERY） |
| RECOVERY | OVERLOAD | ILLEGAL |
| UNDER_UTILIZED | OVERLOAD | ANOMALOUS（应经过中间状态） |
| REJECTION_ACTIVE | NORMAL | ANOMALOUS（应经过 RECOVERY） |

- `isLegalTransition(PressureState from, PressureState to)` 返回 `TransitionLegality`
- `recordTransition(PressureState from, PressureState to, Instant timestamp, String trigger)`：
  - 验证转换合法性
  - 添加 `PressureStateTransition` 到历史
  - 对于 ANOMALOUS 转换 → 不阻塞，但记录 warning
  - 对于 ILLEGAL 转换 → 仍然记录，但触发警告并可用于触发紧急停止
- `currentState()` 返回最后一次转换的 `to` 状态（包装为 Optional）
- `recentTransitions(int count)` 返回最近 count 次转换
- `transitionCount()` 返回转换历史总数

### IR-v0.14-005 OscillationDetector 振荡检测

系统需要 `OscillationDetector` 从调整历史中检测配置振荡模式。

候选验收语义：

- `OscillationDetector` 构造参数：
  - `int windowSize` — 检测窗口大小（调整次数），默认 6
  - `int patternThreshold` — 触发振荡的最小重复次数，默认 2
- `wouldOscillate(AdjustmentDecision pending, AdjustmentHistory history)` 方法：
  - 参数：待执行的 `AdjustmentDecision` + `AdjustmentHistory`
  - 返回：`boolean` — 如果执行此 decision 后会形成振荡模式 → true
- 检测的振荡模式：
  1. **乒乓振荡**（Ping-pong）：最近 windowSize 次调整中，目标 poolSize 形成交替模式
     - 检测算法：计算相邻差值的符号变化。如果在 windowSize 窗口内方向交替 >= patternThreshold 次 → 振荡
     - 示例：target=[10, 20, 10, 20] → 3 次方向的改变 → 振荡
  2. **过度调整**（Over-adjustment）：最近 windowSize 次调整中，连续 >= 3 次同方向
     - 检测算法：检查连续差值的符号是否相同
     - 示例：target=[10, 15, 20, 25] → 连续 3 次 scale-up → 振荡
  3. **策略切换振荡**（Policy switching）：最近 windowSize 次调整中，selectedPolicy 频繁切换
     - 检测算法：窗口内唯一策略数 > 1，且至少一个策略被选中 >= 2 次且中间有不同策略
     - 示例：selected=[A, B, A, C, A] → A 被选中 3 次且被 B/C 隔开 → 振荡
- `detectedPattern(AdjustmentHistory history)` 返回检测到的振荡模式描述（`Optional<String>`）
- 窗口内调整次数不足 windowSize → 不检测振荡（返回 false）
- `AdjustmentHistory` 为空 → 不检测振荡（返回 false）
- 检测仅基于 pool size 的数值序列（乒乓和过度调整）和 policyId（策略切换），不依赖压力分类结果
- 纯函数式：无内部可变状态，输入历史 + 待处理决策 → 输出 boolean

优先级：P0。

### IR-v0.14-006 AdjustmentHistory 调整历史

系统需要 `AdjustmentHistory` 存储和查询调整记录。

候选验收语义：

- `AdjustmentHistory` 类：
  - 持有 `List<HistoryEntry>` 作为调整记录（线程安全 — 使用 `CopyOnWriteArrayList` 或同步）
  - 构造时无需参数（空历史）
- `HistoryEntry` record 字段：
  - `decision`: `AdjustmentDecision` — 调整决策
  - `result`: `AdjustmentResult` — 调整结果
  - `beforeClassification`: `PressureClassification` — 调整前的压力分类
  - `afterClassification`: `PressureClassification` — 调整后（下一个采样周期）的压力分类
  - `recordedAt`: `Instant` — 记录时间
- `HistoryEntry` 构造时验证所有字段非 null
- `record(AdjustmentDecision decision, AdjustmentResult result, PressureClassification before, PressureClassification after)` 方法：
  - 添加新的 `HistoryEntry`
  - 线程安全
- 查询方法：
  - `recent(int count)`: `List<HistoryEntry>` — 最近 count 次调整
  - `since(Instant timestamp)`: `List<HistoryEntry>` — 指定时间之后的调整
  - `totalAdjustmentCount()`: `int` — 总调整次数
  - `successfulAdjustmentCount()`: `int` — 调整后压力状态改善的次数
  - `isEmpty()`: `boolean` — 是否为空
- "调整成功"的判断逻辑（`isImprovement(PressureClassification before, PressureClassification after)`）：
  - 压力等级改善：OVERLOAD→RECOVERY, RECOVERY→NORMAL, QUEUE_BUILDUP→NORMAL, UNDER_UTILIZED→NORMAL, REJECTION_ACTIVE→RECOVERY
  - 维持稳态也算成功：NORMAL→NORMAL
  - 压力等级恶化不算成功：NORMAL→QUEUE_BUILDUP, NORMAL→OVERLOAD, etc.
  - 基于 `PressureState` 枚举序（优先级链）的方向判断：从高压力→低压力 = 改善（除 NORMAL 外）
- `HistoryWindow` record：
  - `size`: `int` — 窗口大小
  - `entries`: `List<HistoryEntry>` — 窗口内的调整记录
  - 构造时验证 `size >= 0` 且 `entries.size() <= size`

优先级：P0。

### IR-v0.14-007 FeedbackCalibrator 权重校准

系统需要 `FeedbackCalibrator` 基于调整结果校准 `ThresholdPolicyScorer` 的评分权重（承接 v0.13.0 DFR-01）。

候选验收语义：

- `FeedbackCalibrator` 类：
  - 构造时无需参数（或接受校准参数：`double maxAdjustmentPerCycle` 默认 0.05, `double minWeight` 默认 0.10, `double maxWeight` 默认 0.50）
- `calibrate(AdjustmentHistory history, ThresholdPolicyScorer currentScorer)` 方法签名：
  - 参数：`AdjustmentHistory history` + `ThresholdPolicyScorer currentScorer`
  - 返回：**新的** `ThresholdPolicyScorer` 实例（不可变模式 — 不修改传入的 `currentScorer`）
  - 通过 `currentScorer.wResponsiveness()` 等 getter 读取当前权重（getter 为包级可见，`experiment.classification` 包内可访问）
  - 从 history 中提取最近 `feedbackCalibrationWindow` 次调整
  - 如果调整次数不足窗口大小 → 不校准（直接返回 `currentScorer`）
  - 对每个维度 d（responsiveness, safety, stability, efficiency）：
    1. 从最近 N 次调整中提取 `(score_d_i, success_i)` 对
    2. 将记录分为"高分"组和"低分"组（以中位数分割）
    3. 计算 `successRate_high` = 高分组中 success=true 的比例
    4. 计算 `successRate_low` = 低分组中 success=true 的比例
    5. `correlation_d = successRate_high - successRate_low`
    6. 如果 `correlation_d > 0.1` → `weight_d += 0.02`（加分）
    7. 如果 `correlation_d < -0.1` → `weight_d -= 0.02`（减分）
    8. 否则 `weight_d` 不变
  - 归一化所有权重使 sum = 1.0
  - Clamp 每个权重到 `[minWeight, maxWeight]`
  - 返回 `new ThresholdPolicyScorer(newWR, newWS, newWSt, newWE)`
- 权重约束：
  - 所有权重之和始终为 1.0（允许浮点误差 0.001）
  - 每个维度权重在 [0.10, 0.50] 范围内
  - 初始权重 = {responsiveness: 0.35, safety: 0.30, stability: 0.20, efficiency: 0.15}（v0.13.0 默认值）
  - `ThresholdPolicyScorer` 需添加包级可见的权重 getter（`experiment.classification` 包内可访问），使 `FeedbackCalibrator` 可读取当前权重
- `calibrate()` 不修改 history
- 不使用机器学习库或外部依赖
- 校准是幂等的——对同一历史数据多次调用产生相同结果

优先级：P1。

### IR-v0.14-009 闭环安全约束

系统需要在闭环运行中实施多个安全约束，覆盖冷却期、最大迭代、紧急停止和 SafetyGate 前置。

候选验收语义：

- **冷却期约束**（cooldown）：
  - 调整冷却由 `RuntimeAdjustmentSafetyGate` 内置 cooldown 机制保证（`DefaultRuntimeAdjustmentSafetyGate` 使用 `SafetyGateConfig.cooldownDecisionIntervals()` 配置冷却间隔）
  - 闭环每次迭代调用 `safetyGate.evaluate(command, executorState, loopReadiness)`
  - SafetyGate 在 cooldown 活跃期间返回 `SafetyGateDecision.Outcome.REJECTED`（failureCode=COOLDOWN_ACTIVE）
  - 闭环记录此 rejection 并 continue（不停止循环）
  - 调整成功应用后，闭环调用 `safetyGate.recordApplied(gateDecision)` 重置 cooldown 计数器
  - 等效 wall-clock 冷却 = `cooldownDecisionIntervals × samplingIntervalMs`
- **最大迭代约束**（maxIterations）：
  - 如果 `LoopConfig.maxIterations > 0`，达到后自动调用 `stop()`
  - 如果 `maxIterations == 0`，无限运行（直到手动 stop 或 emergency stop）
- **振荡紧急停止**：
  - `OscillationDetector` 连续检测到 `emergencyStopThreshold` 次振荡 → `emergencyStop()`
  - 紧急停止原因写入 `LoopSession.summary`
  - 紧急停止后需要手动 `reset()` 才能重新 `start()`
- **SafetyGate 前置**：
  - 每次调整前必须通过 `RuntimeAdjustmentSafetyGate.evaluate(command, executorState, loopReadiness)`
  - `ExecutorStateSnapshot` 通过 `adapter.currentState()` 获取
  - `loopReadiness` 是在 `start()` 中构造的运行时 `ReadinessAssessment`（status=READY, configLabel="runtime-loop", inputRunIds=[sessionId]）
  - gateDecision.outcome() == REJECTED → 记录拒绝（含 failureCode），continue
  - gateDecision.outcome() == NO_OP → continue
  - gateDecision.outcome() == ALLOW → 继续执行调整
  - 调整成功后调用 `safetyGate.recordApplied(gateDecision)`
- **边界硬限制**：
  - 候选策略中的 maxPoolSize/minPoolSize 定义绝对边界
  - `ScaleAdjustmentCommand.create()` 已有的验证（targetPoolSize >= 0, currentPoolSize != targetPoolSize 等）不可绕过
- 这些约束集成在 `AdjustmentLoop` 主循环中（见 IR-v0.14-002 步骤 2、7、9）

优先级：P0。

## 6. 风险和延期项

| 风险 | 当前判断 | 后续触发条件 |
|---|---|---|
| 闭环主循环线程模型选择（`while+sleep` vs `ScheduledExecutorService`） | P2 风险 | `00-objectives-and-scope.md` D1 选择单线程轮询，但 IR 评估是否直接使用 `ScheduledExecutorService`。两者在功能上等价，区别在于 pause/resume 的实现方式。SR 阶段确定最终选择 |
| 振荡检测的假阳性/假阴性 | P2 风险 | 当前检测基于简单的数值序列模式匹配。乒乓振荡检测对 poolSize 计算敏感（如果连续调整指向同一目标但被 SafetyGate capping 修改可能产生误导）。SR 应设计边界情况测试 |
| `AdjustmentDecision.toCommand()` 需要 runId | P2 风险 | `ScaleAdjustmentCommand.create()` 需要 runId。闭环的 runId 是 sessionId 还是独立的值？SR 阶段明确 |
| `PolicyEvaluationInput` 构造需要瞬时值 | P1 风险 | `PolicyEvaluator.evaluate(PolicyEvaluationInput, ThresholdPolicyConfig)` 需要当前的 activeThreads 和 queueSize（瞬时值）。分类器的 `PressureClassification.metrics` 是聚合值（平均值）。`DecisionOrchestrator.decide()` 需要从 snapshots 列表取最后一个快照的瞬时值。SR 必须确认 `PolicyEvaluationInput` 的构造器签名和数据来源 |
| `LivePressureSampler` 的快照获取接口和并发安全 | P1 风险 | 当前 `LivePressureSampler` 通过 `EvidenceRecorder` 存储快照，但没有直接的 `recentSnapshots(int count)` 查询方法。闭环通过 `EvidenceRecorder.snapshots(runId)` 获取快照。关键问题：`InMemoryEvidenceRecorder` 内部使用 `ArrayList`（非线程安全），`LivePressureSampler` 的 `ScheduledExecutorService` 线程写入、`AdjustmentLoop` 的循环线程读取 — 存在 `ConcurrentModificationException` 风险。SR 必须设计线程安全的数据交换：使用 `CopyOnWriteArrayList`、显式读写锁、或通过 `LivePressureSampler` 提供线程安全的 `recentSnapshots(int count)` 方法 |
| `LoopConfig.candidatePolicies` 的类型和空列表处理 | P2 风险 | 如果候选策略列表为空，闭环无法选择策略。构造时应拒绝空列表。如果运行时某策略被移除，闭环应能在下一周期使用剩余策略 |
| `FeedbackCalibrator` 在小样本下的可靠性 | P3 风险 | 10 次调整的样本量小，统计意义有限。"高分组的成功率 - 低分组的成功率"是一种简单近似。IR 已确定不在此版本使用复杂统计方法。如果全部 success 或全部 failure，相关性为 0，权重不变 |
| 闭环与 `LivePressureSampler` 生命周期耦合 | P2 风险 | `AdjustmentLoop` 依赖 `LivePressureSampler` 提供快照数据。如果 sampler 未启动或已停止，闭环无法获取快照。SR 需设计启动顺序依赖和错误处理 |

## 9. 当前结论

v0.14.0 IR 草案已定义 adaptive closed-loop adjustment 的需求方向：10 条 IR 覆盖 LoopState + LoopConfig（闭环生命周期和配置）、AdjustmentLoop（自主闭环控制器）、DecisionOrchestrator + AdjustmentDecision（决策编排）、PressureStateMachine（状态转换模型 — 承接 v0.13.0 DFR-02）、OscillationDetector（振荡检测）、AdjustmentHistory（调整历史）、FeedbackCalibrator（权重校准 — 承接 v0.13.0 DFR-01）、LoopSession + LoopEvidenceRecorder（会话和证据记录）、闭环安全约束（冷却期/最大迭代/紧急停止/SafetyGate 前置）、端到端验证（≥ 5 周期闭环运行 + 振荡触发紧急停止）。核心设计原则：闭环控制器是既有组件的编排层，不引入新的 executor mutation，不引入外部依赖。本文不授权实现或 OpenSpec change；下一步是 IR review。
