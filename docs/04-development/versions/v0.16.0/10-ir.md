- Status: `CLOSED`

## 1. 需求来源

### 1.1 项目现状

v0.15.0 交付了多执行器协调和闭环交叉验证。三个动态配置维度（线程数、队列容量、拒绝策略）全部完成。系统可以动态调整执行器，通过优先级解决预算冲突，并通过 3 模式比较（baseline vs static vs closed-loop）提供经验证据。

但验证仅在简单工作负载（STEADY、RAMP、BURST）下进行。生产环境条件 — 突发到达、长尾延迟、混合 CPU/IO、下游阻塞 — 暴露了稳定性验证和故障恢复的关键缺口。

### 1.2 结构性缺口

六个具体缺口：

1. **无复杂工作负载场景** — `ScenarioProfile` 枚举只有 3 个值（STEADY、RAMP、BURST）。缺少：LONG_TAIL（偶发尖峰的长尾分布）、MIXED_CPU_IO（CPU/IO 交替模式）、DOWNSTREAM_BLOCKED（下游背压模拟）。`ScenarioDefinition.seed()` 字段装饰性存在，planner 未实际使用。

2. **无回滚机制** — `ExecutorAdjustmentAdapter.apply()` 是单向操作：成功或失败，无法撤销。如果调整从 core=4 到 core=8 导致队列深度从 10 飙升到 100，系统没有恢复到 core=4 的路径。

3. **冷却基于计数器** — `DefaultRuntimeAdjustmentSafetyGate` 使用整数 `cooldownRemaining` 计数器。不可注入时钟意味着测试依赖 `Thread.sleep()` 或无法精确验证冷却行为。生产环境中冷却时长与 wall-clock time 的关系不透明。

4. **反振荡仅建议性** — `OscillationDetector.wouldOscillate()` 返回 boolean，但 `AdjustmentLoop` 中的振荡检查结果仅用于记录，不阻断。`CrossExecutorOscillationDetector` 是建议性的 — 标记但不阻断。持续 ping-pong（core=4→8→4→8→...）可以无限继续。

5. **验证报告覆盖不全** — `ValidationComparisonReport` 关注 3 模式比较，不报告：每场景的回滚计数和成功率、恢复时间、p95/p99 延迟（来自真实观测）、队列深度和吞吐量变化、每决策观察窗口（前后快照）。

6. **v0.15 遗留风险** — 4 个已知问题：
   - 统计显著性使用合成代理数组（`mean + Math.random() * noise`）
   - `GroupLoopOrchestrator.startAll()` 传 `null` 给 `ExecutorRegistry` 构造器
   - `EvidenceRecorder` 和 `LoopEvidenceRecorder` 接口无线程安全文档
   - `CoordinatedAdjustmentAdapter` 和 `GroupLoopOrchestrator` 无独立行为测试

### 1.3 为什么是现在

- v0.14.0 证明了单执行器闭环可行，v0.15.0 证明了多执行器协调可行
- 没有回滚能力，自主闭环系统是不完整的 — 没有撤销就没有真正的自主控制
- 复杂工作负载是生产化的前提 — 简单负载验证不足以建立可信度
- v0.15 遗留风险阻塞了统计可信度（合成代理数组）和代码质量（null 安全问题）

## 2. 范围

### 2.1 范围内

**R1 复杂工作负载场景**: `ScenarioProfile` 新增 `LONG_TAIL`、`MIXED_CPU_IO`、`DOWNSTREAM_BLOCKED`。`DeterministicScenarioPlanner` 使用种子（`seed` 字段）为每种新 profile 提供确定性公式。

**R2 回滚感知调整**: `RollbackAwareAdjustmentAdapter` 装饰器捕获调整前 `ExecutorStateSnapshot`，委托给包装的适配器，采样调整后快照，与 `DegradationConfig` 阈值比较，如检测到退化则通过安全门发出回滚命令。回滚限制为每决策 1 次。

**R3 基于时间的冷却**: `TimeBasedCooldownSafetyGate` 实现 `RuntimeAdjustmentSafetyGate`，接受 `Supplier<Instant>` 时钟。冷却检查使用 `Duration.between(lastApplied, clock.get())`。紧急回滚绕过冷却。

**R4 反振荡门**: `AntiOscillationGuard` 咨询 `OscillationDetector` 历史，计数连续振荡，当超过配置的 `blockThreshold` 时激活，阻断非紧急调整。紧急回滚绕过。稳定（无振荡）成功后重置。

**R5 复杂场景验证报告**: `ComplexScenarioReport` record 包含：scenarioId、seed、scenarioConfig、adjustment/blocked/rollback 计数、rollback 成功率、恢复时间、p95/p99 延迟、拒绝计数、队列深度/吞吐量变化、`ObservationWindow` 列表。`ComplexScenarioReportGenerator` 从 `EvidenceRecorder`、`LoopEvidenceRecorder`、`AdjustmentHistory` 读取。

**R6 v0.15 风险修复**:
- 在 `computeSignificance()` 中用真实快照数组替换合成代理
- 修复 `startAll()` 传 `null` 给 `ExecutorRegistry`
- 为 `EvidenceRecorder` 和 `LoopEvidenceRecorder` 添加线程安全 Javadoc
- 添加 `InMemoryEvidenceRecorder` 和 `FileBackedEvidenceRecorder` 的并发争用测试
- 添加 `CoordinatedAdjustmentAdapter` 和 `GroupLoopOrchestrator` 的行为测试

### 2.2 范围外

- 跨 JVM 或分布式协调
- 新的外部依赖（Java 21、Maven/JUnit5 不变）
- 前端、数据库、消息队列、认证或监控集成
- 多维度同时调整
- 策略自动生成
- `pom.xml` 依赖或 Java 版本变更
- `provided-api/`、`src/**/api/**`、`src/**/contract/**` 路径变更

### 2.3 术语

| 术语 | 定义 |
|------|------|
| RollbackAwareAdjustmentAdapter | 装饰器，实现 ExecutorAdjustmentAdapter，捕获调整前状态，检测退化，通过安全门发出回滚 |
| TimeBasedCooldownSafetyGate | 实现 RuntimeAdjustmentSafetyGate，使用 Supplier&lt;Instant&gt; 替代计数器冷却 |
| AntiOscillationGuard | 独立守卫，咨询 OscillationDetector，当持续振荡超过可配置阈值时阻断非紧急调整 |
| ComplexScenarioReport | 不可变 record，包含复杂场景运行的所有验证指标 |
| ObservationWindow | 不可变 record，携带单一决策的前后快照 |
| DegradationConfig | 不可变 record，指定回滚的退化阈值（队列深度、吞吐量、延迟） |
| emergencyRollback | 标志 ScaleAdjustmentCommand 为紧急回滚 — 绕过冷却和反振荡 |
| LONG_TAIL | 场景 profile：偶发尖峰（seed % 3 == 0 时 workUnits × 5），基于种子的确定性 |
| MIXED_CPU_IO | 场景 profile：CPU 密集（偶数索引）和 IO 密集（奇数索引）交替 |
| DOWNSTREAM_BLOCKED | 场景 profile：恒定工作单元 + 高延迟模拟下游背压 |

## 3. IR 条目

### IR-01: LONG_TAIL 场景 profile

**需求**: `ScenarioProfile.LONG_TAIL` 存在，`DeterministicScenarioPlanner` 使用种子产生确定性计划，其中 `seed % 3 == 0` 产生基础 5 倍的尖峰。

**验收**: 种子=6 产生 workUnits=600 的步骤（baseWorkUnits=100）；种子=7 产生 workUnits=100 的步骤。计划跨调用确定。

**实现文件**: `ScenarioProfile.java`、`DeterministicScenarioPlanner.java`

**优先级**: P0 — 新增场景是其他能力的前置依赖。

### IR-02: MIXED_CPU_IO 场景 profile

**需求**: `ScenarioProfile.MIXED_CPU_IO` 存在，计划在偶数索引（CPU: workUnits × 3）和奇数索引（IO: workUnits = base，延迟 = base × 2）之间交替。

**验收**: baseWorkUnits=50 → step 0 {workUnits=150, delay=0}, step 1 {workUnits=50, delay=100}, 交替。

**实现文件**: `ScenarioProfile.java`、`DeterministicScenarioPlanner.java`

**优先级**: P0。

### IR-03: DOWNSTREAM_BLOCKED 场景 profile

**需求**: `ScenarioProfile.DOWNSTREAM_BLOCKED` 存在，计划为所有步骤产生恒定 workUnits + 高延迟（delay = base × 10）。

**验收**: baseWorkUnits=200 → 所有步骤 workUnits=200, delay=2000。计划确定性。

**实现文件**: `ScenarioProfile.java`、`DeterministicScenarioPlanner.java`

**优先级**: P0。

### IR-04: 回滚感知适配器 — 退化检测

**需求**: `RollbackAwareAdjustmentAdapter.apply()` 在委托前捕获调整前快照，在委托后采样调整后快照，当指标恶化超过 `DegradationConfig` 阈值时触发回滚。

**验收**: 队列深度增加 > 阈值触发回滚。无退化不触发回滚。可配置阈值控制行为。

**实现文件**: `RollbackAwareAdjustmentAdapter.java`、`DegradationConfig.java`

**优先级**: P0。

### IR-05: 回滚感知适配器 — 安全门集成

**需求**: 回滚命令通过注入的 `RuntimeAdjustmentSafetyGate` 评估后再应用。如安全门拒绝回滚，返回原始结果。回滚动作（成功、失败、拒绝）通过 `BiConsumer` 回调记录。

**验收**: 安全门 ALLOW → 应用回滚。安全门 REJECTED → 返回原始结果。监听器收到回滚事件。

**实现文件**: `RollbackAwareAdjustmentAdapter.java`

**优先级**: P1。

### IR-06: 回滚感知适配器 — 有界（最多 1 次/决策）

**需求**: 如果回滚本身导致退化，适配器不进入无限回滚循环。返回回滚结果。

**验收**: 初始 apply 退化 → 回滚 → 回滚退化 → 返回回滚结果（无第二次回滚）。

**实现文件**: `RollbackAwareAdjustmentAdapter.java`

**优先级**: P1。

### IR-07: 基于时间的冷却门 — 可注入时钟

**需求**: `TimeBasedCooldownSafetyGate` 接受 `Supplier<Instant>` 时钟。冷却窗口 = `Duration.between(lastApplied, clock.get()) < cooldownDuration`。维护 per-executor 的 `lastAppliedInstant` map。

**验收**: 可注入时钟。拒绝冷却窗口内的命令。冷却过期后允许命令。使用 `AtomicReference<Instant>` 在不 sleep 的情况下测试。

**实现文件**: `TimeBasedCooldownSafetyGate.java`

**优先级**: P0。

### IR-08: 基于时间的冷却门 — 紧急回滚绕过

**需求**: 带有 `emergencyRollback` 标志的紧急回滚命令绕过冷却。非紧急命令即使在冷却窗口内携带 emergency 标志也不绕过。

**验收**: 冷却激活时，emergencyRollback → ALLOW。冷却激活时，scale-up with emergency flag → REJECTED。

**实现文件**: `TimeBasedCooldownSafetyGate.java`、`ScaleAdjustmentCommand.java`

**优先级**: P1。

### IR-09: 基于时间的冷却门 — 保留所有其他安全检查

**需求**: 其他冷却门检查（就绪、每运行限制、相反方向、无操作）保留。只替换冷却机制。

**验收**: NOT_READY → REJECTED。RUN_LIMIT_EXCEEDED → REJECTED。NO_OP 检测仍然有效。

**实现文件**: `TimeBasedCooldownSafetyGate.java`

**优先级**: P0。

### IR-10: 反振荡门 — 持续振荡阻断

**需求**: `AntiOscillationGuard` 咨询 `OscillationDetector.wouldOscillate()`。当连续振荡计数 >= `blockThreshold` 时激活。激活后阻断非紧急调整返回 `ANTI_OSCILLATION_ACTIVE`。

**验收**: blockThreshold=3，2 次连续振荡 → 未激活。3 次 → 激活并阻断。可配置 threshold。

**实现文件**: `AntiOscillationGuard.java`、`AdjustmentFailureCode.java`

**优先级**: P0。

### IR-11: 反振荡门 — 紧急回滚绕过 + 重置

**需求**: 紧急回滚绕过已激活的守卫。守卫激活期间的非紧急调整被阻断。稳定（无振荡）成功后重置连续计数器。

**验收**: 守卫激活时 emergencyRollback → ALLOW。稳定成功后 counter → 0。

**实现文件**: `AntiOscillationGuard.java`

**优先级**: P1。

### IR-12: 反振荡门 — 调整循环集成

**需求**: `AntiOscillationGuard` 在振荡检测之后、冷却门评估之前评估。作为构造器参数注入（可空以保持向后兼容）。被阻断的调整通过 `LoopEvidenceRecorder` 记录。

**验收**: 守卫在 `oscillationDetector.wouldOscillate()` 之后、`safetyGate.evaluate()` 之前调用。无守卫（null）时循环正常工作。

**实现文件**: `AdjustmentLoop.java`

**优先级**: P0。

### IR-13: 复杂场景验证报告 — record 类型

**需求**: `ComplexScenarioReport` record 包含 scenarioId、seed、scenarioConfig、adjustment/blocked/rollback 计数、rollbackSuccessRate、recoveryTimeMs、p95LatencyMs、p99LatencyMs、rejectionCount、queueDepthDelta、throughputDelta、decisionWindows、generatedAt。

**验收**: record 使用所有字段构造，访问器正确返回。

**实现文件**: `ComplexScenarioReport.java`、`ObservationWindow.java`

**优先级**: P1。

### IR-14: 复杂场景报告生成器 — 真实证据源

**需求**: `ComplexScenarioReportGenerator` 从 `EvidenceRecorder`、`LoopEvidenceRecorder`、`AdjustmentHistory` 读取。所有指标从真实观测数据计算。拒绝 null 源。无合成代理。

**验收**: 报告反映真实记录的数据。百分位延迟来自真实快照。增量反映开始到结束的变化。

**实现文件**: `ComplexScenarioReportGenerator.java`

**优先级**: P1。

### IR-15: v0.15 修复 — 统计显著性

**需求**: `ClosedLoopValidationRunner.computeSignificance()` 使用来自 `InMemoryEvidenceRecorder.snapshots(runId)` 的真实快照数组，而非 `mean + Math.random() * noise`。

**验收**: 无代理数组生成。无 `Math.random()` 合成。`StatisticalSignificanceCalculator.compare()` API 不变。

**实现文件**: `ClosedLoopValidationRunner.java`

**优先级**: P0。

### IR-16: v0.15 修复 — GroupLoopOrchestrator null

**需求**: `startAll()` 不传 `null` 给 `ExecutorRegistry`。构造有效的 `ExecutorRegistry` 实例或接受非 null 参数。

**验收**: `startAll()` 使用非 null `ExecutorRegistry`。有效组件成功。

**实现文件**: `GroupLoopOrchestrator.java`

**优先级**: P1。

### IR-17: v0.15 修复 — 线程安全文档 + 测试

**需求**: `EvidenceRecorder` 和 `LoopEvidenceRecorder` Javadoc 记录并发安全。`InMemoryEvidenceRecorder` 和 `FileBackedEvidenceRecorder` 的并发争用测试。

**验收**: Javadoc 存在。CyclicBarrier 测试：4 线程 × 50 写入 = 200 快照无数据丢失。

**实现文件**: `EvidenceRecorder.java`、`LoopEvidenceRecorder.java`、`InMemoryEvidenceRecorderConcurrencyTest.java`、`FileBackedEvidenceRecorderConcurrencyTest.java`

**优先级**: P2。

### IR-18: v0.15 修复 — 行为测试

**需求**: `CoordinatedAdjustmentAdapter` 的独立测试（拒绝/封顶/批准/委托）。`GroupLoopOrchestrator` 的独立测试（startAll/emergencyStopAll/getGroupHealth）。

**验收**: 行为测试存在并通过。

**实现文件**: `CoordinatedAdjustmentAdapterTest.java`、`GroupLoopOrchestratorTest.java`

**优先级**: P2。

## 4. 风险与延期项

| 风险 | 严重级别 | 处置 |
|------|---------|------|
| 回滚循环（回滚本身退化） | P1 | 限制为 1 次回滚/决策；返回回滚结果 |
| 冷却绕过滥用（emergency 标志） | P1 | Emergency 绕过仅适用于回滚（target == 之前安全状态），不适用于任意 scale-up |
| 反振荡误判 | P2 | 为复杂场景使用更大的 blockThreshold 窗口 |
| 真实数据显著性结果不同 | P2 | 可接受 — v0.15 方法是错误的 |
| AdjustmentLoop 集成复杂性 | P2 | 组合 — 循环以黑盒方式调用守卫/门 |
| 集成测试耗时 | P3 | 单元测试使用最小步骤数；较长运行保留给带标签的集成测试 |

## 5. 用户确认项

- 复杂场景 profile 必须是确定性的且基于种子可重复
- 回滚必须通过安全门（无后门）
- 紧急回滚必须绕过冷却和反振荡 — 但不能被滥用
- 所有报告指标必须来自真实观测数据 — 无合成代理
- v0.15 风险修复必须在不破坏已有测试的情况下完成
