## 核心技术差异：无需 Executor Rebuild

v0.9.0 的核心挑战是 `ThreadPoolExecutor` 不支持 work queue 替换，需要 ExecutorRebuildStrategy（decommission → commission）。**v0.10.0 不面临这个约束** — `ThreadPoolExecutor.setRejectedExecutionHandler()` 是公开的、线程安全的 mutator（`RejectedExecutionHandler` 字段为 `volatile`），无需 executor 重建。

这使 v0.10.0 的设计比 v0.9.0 显著简化：
- Adapter 无需管理 rebuild 生命周期
- 无需 drain-and-replay 逻辑
- 无需 decommission → commission 周期
- `RejectionPolicyAdjustmentAdapter.apply()` 的核心逻辑仅 3 步：lookup executor → safety gate evaluate → `executor.setRejectionPolicy(target)`

**经验**: 在设计新的动态配置维度前，先检查 JDK/TPE 是否已原生支持该操作。v0.9.0 的 queue resize 和 v0.10.0 的 policy replacement 在技术难度上差距悬殊，根本原因是前者需要绕过 JDK 限制而后者不需要。

## 发生的问题

### P1: rejectionPolicy 字段方案历经三阶段演进

`00-objectives-and-scope` §7.2 原始设计：`private final` → `private volatile`，保留字段但允许修改。

```
阶段 1 (scope): private volatile RejectedExecutionHandler rejectionPolicy;
阶段 2 (IR):   IR F07 质疑 volatile vs 直接委托 TPE，推荐方案 B（删除字段，直接委托）
阶段 3 (SR):   SR 采纳方案 B — 删除 rejectionPolicy 字段，getRejectionPolicy() 直接委托 executor.getRejectedExecutionHandler()
```

**根因**: v0.9.0 的 `queueCapacity` 字段有保留的理由（`workQueue.remainingCapacity() + workQueue.size()` 初始化缓存，rank 等扩展字段可能无法从 TPE 直接获取）。但 `RejectedExecutionHandler` 从 TPE 直接可读（`getRejectedExecutionHandler()`），缓存字段是多余的。

**处置**: SR §4.2 明确选择方案 B。这是 IR→SR 管道正确运作的例证 — IR 提出问题，SR 做最终设计决策，实现阶段直接执行。`ManagedExecutor` 变更量极小（+2 行 getter/setter，-1 字段，-1 构造器赋值行）。

### P2: RejectionPolicySafetyGate 三参数签名 vs QueueResizeSafetyGate 两参数

SR §4.3 设计 `RejectionPolicySafetyGate.evaluate(RejectionPolicyCommand, ManagedExecutor, String executorId)` 三参数，而 `QueueResizeSafetyGate.evaluate(QueueResizeCommand, ManagedExecutor)` 是两参数。

额外 `executorId` 参数仅用于并发 resize 保护（`isResizeInProgress.test(executorId)`）。`ManagedExecutor` 不携带 registry ID（ID 是 registry 的 key），因此 executorId 必须作为独立参数传入。

SR review F02 提出此问题，SR disposition 接受并在 §4.3 补充了签名差异的设计选择记录。

**根因**: 两个 safety gate 服务于不同的安全检查需求。Queue resize safety gate 的幂等保护在 adapter 层（`ConcurrentHashMap resizeInProgress`），而 policy safety gate 需要检查 resize 是否在进行中（通过外部 `Predicate<String>`），因此需要 executorId。

**处置**: 接受差异。两个 safety gate 签名不一致是有意的。v0.9.0 复盘已确认 `ControlGate<T>` 接口不适合非"快照 + readiness"模式的 safety gate，`RejectionPolicySafetyGate` 延续了 `QueueResizeSafetyGate` 的独立接口模式。

### P3: Adapter 无幂等保护 — 与 QueueResizeAdjustmentAdapter 的设计差异

`QueueResizeAdjustmentAdapter` 使用 `ConcurrentHashMap<String, Boolean> resizeInProgress` 防止并发 rebuild（两个 resize 同时操作同一 executor 会导致状态混乱）。`RejectionPolicyAdjustmentAdapter` 没有类似保护。

**根因**: `TPE.setRejectedExecutionHandler()` 是原子 volatile 写，两个线程同时调用不会产生中间状态。并发 policy 替换是 last-write-wins 语义，IR F03 明确确认。

**处置**: SR §4.4 补充了幂等保护差异对比说明。这是两个 adapter 的正确设计分化 — 不是所有 adapter 都需要幂等保护。

### P4: Policy set failure 场景不可直接测试

SR spec 要求 adapter 捕获 `setRejectionPolicy()` 抛出的 `RuntimeException` 并返回 `POLICY_SET_FAILED` 结果。但 `TPE.setRejectedExecutionHandler()` 对 JDK 内置 handler 从不抛异常，该 catch 块是 dead code（defense-in-depth）。

Mockito 模拟 `ManagedExecutor.setRejectionPolicy()` 抛出异常可测试此路径，但项目的工程基线对 Mockito 使用有限制。

**处置**: 接受不可直接测试的残余风险。`ManagedExecutor.setRejectionPolicy()` 的非 null 验证已测试（`setRejectionPolicyNullThrows`），TPE 层面对合法 handler 从不抛异常。catch 块作为 defense-in-depth 存在。

### P5: fromCurrent() class 比较对匿名自定义 handler 可能误判

`RejectionPolicyCommand.fromCurrent()` 使用 `target.getClass() == current.getClass()` 做 no-op 检测。对于 JDK 内置四种策略（每个都是独立具名类），class 比较正确。但对于 `new RejectedExecutionHandler() { ... }` 匿名实现，两个语义不同的匿名 handler 共享同一 class 对象，`fromCurrent()` 可能返回空。

**根因**: 自定义 `RejectedExecutionHandler` 实现 out of scope（decision-log DFR-04）。IR F05 明确了 class 比较策略 — 对 JDK 内置策略正确且高效。

**处置**: 接受 class 比较的已知限制。IR/SR 均已记录此 deferred 项。如果未来需要支持自定义 handler 的语义区分，可扩展 `fromCurrent()` 为 `Objects.equals()` 比较。

## 风险和残余

| 风险 | 严重级别 | 处置 |
|---|---|---|
| Policy set failure catch 块不可达 | 低 | JDK 内置 handler 不抛异常；defense-in-depth 保留 |
| fromCurrent() class 比较对匿名 handler 误判 | 低 | 自定义 handler out of scope；IR/SR deferred |

## 关联修复：ExecutorRebuildStrategy 策略保留

v0.10.0 附带修复了 v0.9.0 的遗留缺陷 — `ExecutorRebuildStrategy.rebuild()` 第 75 行硬编码 `new ThreadPoolExecutor.AbortPolicy()`，导致 queue resize rebuild 后丢失原始拒绝策略。

## 流程改进

### v0.9.0 复盘改进落地确认

v0.9.0 复盘提出三项流程改进，v0.10.0 全部落地：

1. **SR 伪代码必须与目标 API 实际签名对齐**: SR 抽样校验 3/3 通过（`isShutdown`/`isTerminated`、`PolicyReplacementResult` 工厂方法模式、`oldTpe.getRejectedExecutionHandler()`）。SR review §3 记录了完整的 API 签名抽样校验过程。

2. **独立 result 类型模式**: `PolicyReplacementResult` 不复用 `AdjustmentResult` 或 `QueueResizeResult`。每个 adapter 返回自己专用的 result 类型 — 此模式现已稳定：`ScaleAdjustmentCommand → AdjustmentResult`, `QueueResizeCommand → QueueResizeResult`, `RejectionPolicyCommand → PolicyReplacementResult`。

3. **ControlGate 接口的适用边界**: `RejectionPolicySafetyGate` 是独立类，不实现 `ControlGate<T>`。`ControlGate<T>` 适合"快照 + readiness"评估模式，不适合"实时 executor 方法调用"或"外部 Predicate 检查"模式。两个 safety gate（QueueResize 和 RejectionPolicy）均使用独立接口。

### 需要固化到规则的新改进

1. **"JDK 原生支持"优先检查**: 在设计新的动态配置维度前，先确认 `ThreadPoolExecutor` 是否已提供公开 mutator。v0.9.0 queue resize 需要 rebuild 因为 `setQueue()` 不存在；v0.10.0 policy replacement 不需要 rebuild 因为 `setRejectedExecutionHandler()` 存在。这个差异决定了设计的复杂度。→ 在 version design template 或 `00-objectives-and-scope` 的 "与前一版本的关键差异" 节中，增加"JDK API 可用性评估"作为必填项。

2. **field vs delegate 决策模式**: `rejectionPolicy` 字段的三阶段演进（volatile → 直接委托 → 字段删除）揭示了一个通用模式：当 TPE 已提供属性的 getter 时，`ManagedExecutor` 不应缓存该属性。缓存引入一致性问题（setter 后需同步更新缓存），且不提供额外价值。→ 未来的 `ManagedExecutor` 扩展属性应遵循：TPE 有 getter → 删除缓存字段，直接委托；TPE 无 getter（如 queueCapacity）→ 保留缓存字段。

### 后续 agent 必须遵守的行为

- `ManagedExecutor.getRejectionPolicy()` 直接委托 `executor.getRejectedExecutionHandler()` — 无缓存字段
- `RejectionPolicyAdjustmentAdapter` 无幂等保护 — 并发 policy 替换是 last-write-wins
- `RejectionPolicySafetyGate` 通过 `Predicate<String>` 检查 resize-in-progress — 不要在 adapter 外部绕过此检查
- `RejectionPolicyCommand.fromCurrent()` 使用 class 比较 — 对 JDK 内置四种策略正确，对匿名自定义 handler 可能误判
- `ExecutorRebuildStrategy.rebuild()` 使用 `oldTpe.getRejectedExecutionHandler()` — 不再硬编码 AbortPolicy
- 所有 policy e2e 测试的 `@AfterEach` 必须：countDown 所有 latch → shutdown executor → awaitTermination → registry.remove

## 结论

v0.10.0 完成了 `DynamicThreadPollerManager` 三个动态配置维度的最后一个 — 运行时拒绝策略替换。与 v0.9.0 queue resize 不同，此维度利用了 `ThreadPoolExecutor.setRejectedExecutionHandler()` 这一 JDK 公开 API，无需 executor 重建，设计复杂度显著降低。

附带修复了 v0.9.0 的 ExecutorRebuildStrategy 策略丢失缺陷（一行变更）。

2 个 change 按计划交付（无 change 数调整），单 commit。3 个设计偏差均已处置（rejectionPolicy 字段方案演进、safety gate 签名差异、adapter 幂等保护差异），均为有意的设计选择而非功能缺陷。534 测试通过，零回归，现有组件（ManagedExecutorAdjustmentAdapter、QueueResizeAdjustmentAdapter、ManagedExecutorScenarioRunner）未经修改。

`DynamicThreadPollerManager` 的核心承诺全部兑现：

1. **线程数动态调整** — v0.7.0（`setCorePoolSize`/`setMaximumPoolSize`）
2. **队列容量动态调整** — v0.9.0（`ExecutorRebuildStrategy` decommission → commission）
3. **拒绝策略动态调整** — v0.10.0（`setRejectedExecutionHandler`）

三个维度的技术难度从高到低依次为：queue resize > thread adjustment > rejection policy replacement。v0.9.0 证明了 executor 生命周期管理基础设施可以安全处理最复杂的 rebuild 场景；v0.10.0 证明了更简单的 JDK 原生 mutator 可以直接复用同一套 adapter/safety-gate/evidence 架构模式。

版本交付完成。`DynamicThreadPollerManager` 的动态配置能力基线已完整。
