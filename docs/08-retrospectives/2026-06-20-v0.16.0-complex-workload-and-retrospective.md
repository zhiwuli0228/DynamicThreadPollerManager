```
Version Baseline → IR → IR Review → Disposition → IR Closure
    → SR → SR Review → Disposition → SR Closure
    → Change Decomposition → Implementation → Verification → Archive → Retrospective
```

### 实际路径

```
SDD Experiment (sdd_test branch)
    ├── brainstorm.md → proposal.md → design.md
    ├── 6 spec files (superspec autonomous pipeline)
    ├── tasks.md → plan.md → apply × N (autonomous runner)
    └── Result: working code, 112 tests pass, .sdd/ + .claude/ + .codex/ infrastructure
            ↓
Extract business code → claude_master (35 Java files, excluding AI framework)
            ↓
Design doc retrofit (claude_master, 2026-06-20)
    ├── Read SDD artifacts (brainstorm/proposal/design/specs)

    ├── IR phase: 10-ir → 11-ir-review → 12-disposition → 13-closure (4 docs)
    ├── SR phase: 20-sr → 21-sr-review → 22-disposition → 23-closure (4 docs)
    └── Update current-state.md
            ↓
Implementation-source consistency verification (18 IR / 24 SR / 4 deviations → 100%)
            ↓
Commit + Push
```

### 偏差分析

| 维度 | 标准流程预期 | SDD 实际 | 偏差性质 |
|---|---|---|---|
| 需求分析 | IR 文档 (人工撰写+评审) | brainstorm.md (SDD runner 产出) | SDD 产出质量高，可直接复用为 IR 素材 |
| 提案 | 版本设计文档 | proposal.md (SDD runner 产出) | 覆盖了目标和范围，但缺少术语表/风险表的标准格式 |
| 功能设计 | SR 文档 (人工撰写+评审) | design.md + 6 spec (SDD runner 产出) | 技术设计质量高，6 个决策点清晰；但缺少 API 签名验证、失败语义表、并发声明 |
| 设计评审 | IR Review + SR Review (独立评审) | **无** — SDD 流程无独立评审环节 | 最大缺口。事后补齐的 SR review 发现了 2 个 P1（cooldown key、AntiOscillationGuard null command）— 如果实现前评审，这些可在编码前修正 |
| 实现 | 基于 SR 的 OpenSpec change | Autonomous SDD runner apply | 代码可工作（139 tests pass），但缺少与设计文档的双向追溯 |
| 验证 | 对照 SR 验证 | 对照 spec 自验证 | SDD runner 有自验证机制（apply 循环），但仅限于 spec 内部一致性 |
| 文档归档 | IR/SR/RETROSPECTIVE 目录 | `.sdd/` 目录 + 无标准设计文档 | 事后补齐 12 个文档，约 5500 行 markdown |

**核心偏差**: SDD 流程跳过了 IR/SR 的独立评审环节。评审环节在 v0.15.0 中消除了 28 个 findings（3 P0 + 8 P1），v0.16.0 的 2 个 P1 均是在事后 SR review 中发现的。如果这些在编码前发现，修复成本接近于零。

## 发生的问题

### P0: AI 框架被 SDD runner 删除

**问题**: SDD runner 在 `sdd_test` 分支的 commit `47c7e4f` 删除了 `.claude/commands/opsx/`、`.claude/skills/`、`.codex/skills/` — 项目的 AI 辅助研发架构。

**影响**: 如果直接 merge sdd_test 到 claude_master，AI 框架将丢失。需要仔细分离：保留 AI 框架删除的 commit，仅提取业务代码。

**处置**: 使用 `git checkout sdd_test -- src/main/java/ src/test/java/` 精确提取 35 个业务文件，不触碰 `.claude/`、`.codex/`、`.sdd/` 目录。

**教训**: 自主 AI runner 在生产项目中运行时，必须限制其文件系统写权限范围。至少应排除 `.claude/`、`.codex/` 等基础设施目录。应在 CLAUDE.md 或项目规则中明确"AI runner 不得修改的路径清单"。

### P1: cooldown key 使用 runId 而非 executor name

**问题**: `TimeBasedCooldownSafetyGate.lastAppliedInstant` map 的 key 是 `command.runId()`（源码 line 73, 122），而非 executor name。多执行器组场景中，所有执行器共享同一个 runId，导致冷却粒度过粗。

**影响**: 执行器 A 的调整会阻止执行器 B 的合理调整。IR-07 声明 "维护 per-executor 的 lastAppliedInstant map"，但代码实现的是 per-runId。

**发现时机**: SR review（事后）——编码前未发现。如果实现前有 SR review，此问题可在设计阶段修正。

**处置**: SR §9 记录为已知 P1 偏差，含修复方案（key 改为 `runId + ":" + executorName`）和触发条件。当前单执行器场景不受影响。

**教训**: 接口语义中的 key 选择（runId vs executor name vs runId+executor）应在设计阶段明确并评审。IR-07 的需求声明 "per-executor" 未被代码验证步骤捕捉——说明需求→代码的自动化验证链路存在断层。

### P2: AntiOscillationGuard 返回 null command

**问题**: `AntiOscillationGuard.evaluate()` 在紧急回滚绕过和无振荡路径返回 `SafetyGateDecision.allow(0, null)`（源码 line 55, 74）。`SafetyGateDecision` 的 `appliedCommand()` 会返回 null。

**影响**: 当前 `AdjustmentLoop` 仅检查 `isAllowed()`，不调用 `appliedCommand()`——因此安全。但任何未来消费者（报告生成器、测试工具）假设 ALLOW 决策始终携带非 null command 会触发 NPE。

**发现时机**: SR review（事后）。SR 文档中未标注此行为。

**处置**: SR 设计层面修正为 `SafetyGateDecision.noOp(...)`。代码未修改（标记为未来修复）。风险低——当前消费者不触发。

**教训**: 公开 API 的返回值约定应在设计文档中明确——特别是 null 参数的语义。`SafetyGateDecision.allow(int, ScaleAdjustmentCommand)` 的 javadoc 应说明 command 是否可为 null。

### P3: SDD 实验与标准流程双轨导致重复工作

**问题**: SDD runner 产出了 brainstorm/proposal/design/spec（~3000 行），设计文档补齐又产出了 IR/SR/README/decision-log（~3500 行）。两者内容高度重叠，但格式不同。

**影响**: 设计文档补齐耗时约 4 小时（12 个文档），大部分是格式转换和补充标准要素（术语表、风险矩阵、API 签名验证、失败语义表）。

**处置**: 接受此次重复——SDD 实验价值在于验证自主 runner 可行性，设计文档补齐是治理合规的必要成本。

**教训**: 如果未来继续使用 SDD，应建立 SDD 产出→标准文档的自动映射。例如：
- `brainstorm.md` §Scope → `10-ir.md` §2
- `design.md` §Decisions → `decision-log.md`
- `specs/*.md` → `20-sr.md` §4 组件设计
- 标准要素（术语表、失败语义、并发声明）作为补充模板

## 已采纳的改进

### 设计文档补齐流程

为"代码先行、文档后补"的场景建立了可重复的流程：
1. 阅读 SDD 产出（brainstorm → proposal → design → specs）
2. 按 managed-change-standard 模板写出 00-objectives-and-scope + decision-log
3. IR 阶段：IR → 独立评审（对照代码和 SDD 产出找 finding）→ 处置 → 闭环
4. SR 阶段：SR → 独立评审（对照源码验证所有 API 签名）→ 处置 → 闭环
5. 实现-SR 一致性校验（逐项源码对照）
6. 更新 current-state.md

### IR/SR review 在事后仍有价值

即使代码已实现，SR review 仍然发现了 2 个 P1 问题。这说明评审的价值独立于评审时机——事前评审（预防缺陷）最优，事后评审（发现缺陷）次之，不评审最差。

### 源码级一致性验证方法

建立了设计文档 vs 源码的一致性验证方法：
- IR: 逐条对照 IR 需求与源码文件:行号
- SR: 模块边界、构造器签名、行为声明、偏差描述、测试文件、并发声明 — 6 个维度 × N 个声明
- 偏差: 确认文档记录的偏差与代码行为一致

v0.16.0 达到 100% 一致性（18/18 IR + 24/24 SR + 4/4 deviations）。

## 仍然存在的问题

1. **P1 cooldown key 未修复**: `TimeBasedCooldownSafetyGate.lastAppliedInstant` 仍按 `command.runId()` 建 key。修复需要 `ScaleAdjustmentCommand` 新增 `executorName()` 字段，涉及 API 变更。当前单执行器场景不受影响。SR §9 含修复方案和触发条件。

2. **AntiOscillationGuard null command 未修复**: 代码中仍返回 `allow(0, null)`。SR 设计已修正为 `noOp(...)`，但源码未同步修改。当前消费者安全，风险低。

3. **仍无 OpenSpec change**: v0.16.0 代码未通过标准 OpenSpec change decomposition 流程。如果后续需要重新走标准实现流程或增量修改，缺少 change 级别的任务拆分和 spec delta。

4. **v0.15 遗留风险全部延期**: v0.15.0 复盘的 5 个遗留问题中，v0.16.0 修复了 3 个（统计显著性/null 安全/线程安全文档），新增了 2 个行为测试。但 `GroupLoopOrchestrator` 的并发采样风险（InMemoryEvidenceRecorder 非线程安全 ArrayList）和 E2E 测试时长问题仍然存在。

5. **SDD runner 的可重复性未验证**: 如果重新运行 SDD runner（相同的 brainstorm → proposal → specs 输入），是否会产出相同的代码？确定性未验证。这使得 SDD 实验在合规性上不如标准流程可审计。

6. **12 个设计文档的长期维护**: 这些 "as-built" 文档描述的是 v0.16.0 的当前代码状态，而非设计意图。如果后续代码修改，文档需要跟随更新——但"代码先行、文档后补"的流程不适用于增量修改。

## 后续 agent 行为要求

1. **SDD runner 路径白名单**: 如果再次使用自主 AI runner（SDD 或类似），必须在 CLAUDE.md 或任务定义中明确"允许修改的路径清单"和"禁止修改的路径清单"。至少：`.claude/`、`.codex/`、`docs/00-project/`、`docs/02-harness/`、`.gitignore` 应为只读。

2. **评审不可跳过**: 无论使用何种开发流程，设计评审（IR Review + SR Review）不可跳过。v0.15.0 的 28 个 findings 和 v0.16.0 的 6 个 findings 证明了评审的价值。如果时间不足，至少执行 P0/P1 级别的快速评审。

3. **事后文档补齐的适用边界**: "as-built" 文档模式仅适用于一次性实验（如 v0.16.0 SDD 实验）。对于持续的增量开发，必须使用标准的"设计先行"流程——as-built 文档在代码修改后极易过时。

4. **接口 key 设计评审**: 任何涉及 map key 的设计决策（如 cooldown per-runId vs per-executor），应在设计文档中明确 key 的类型、唯一性语义和数据生命周期。v0.16.0 P1 的根因是 IR-07 说 "per-executor" 但代码实现 "per-runId"——设计意图与实现的语义偏差。

5. **公开 API 的 null 契约**: 任何 `public static` 工厂方法（如 `SafetyGateDecision.allow(int, ScaleAdjustmentCommand)`），应在 javadoc 中明确参数是否可为 null。如果允 null，说明语义；如果不允，使用 `Objects.requireNonNull`。

## 开发方法论反思

v0.16.0 作为一次开发方法论实验，核心问题是：**自主 SDD runner 能否替代标准 IR→SR→Change→Implement 流程？**

**答案：不能完全替代，但可以互补。**

SDD runner 的优势：
- 速度快 — 从 brainstorm 到 working code 约 1 天
- 代码质量可接受 — 139 tests pass，架构约束满足
- 技术设计合理 — 6 个设计决策全部正确

SDD runner 的不足：
- 无独立设计评审 — v0.15.0 标准流程消除了 28 个 findings，SDD 流程消除 0 个
- 设计文档非标准格式 — 无法直接融入项目治理体系
- 不可审计 — 无 IR→SR→Change 追溯链
- 有破坏性 — 删除了 AI 框架文件

**推荐混合模式**: SDD runner 作为需求探索和原型验证工具（替代 brainstorm + proposal 阶段），但 IR→SR→Change→Implement 的标准设计门禁不可省略。具体：SDD 产出作为 IR 的输入素材（替代从零写 IR），人工评审和 SR 设计照常进行。

## 结论

v0.16.0 以非标准 SDD 实验路径交付了 6 个 capability 的业务代码，同时通过事后补齐的 12 个设计文档满足了项目治理合规要求。代码质量良好（139 tests pass，架构约束满足），但发现了 2 个 P1 设计偏差（cooldown key、AntiOscillationGuard null command）— 如果在标准流程中实现前评审，这些可提前消除。

核心教训：**设计评审不可跳过**。SDD 可以加速需求探索和技术设计，但不能替代 IR/SR 评审的缺陷预防功能。未来版本应坚持"标准流程为主，SDD 辅助需求探索"的混合模式。

v0.16.0 是 claude_master 分支上第 6 个完成 IR→SR→交付→复盘的版本。35 个业务文件、139 个新增测试、12 个设计文档、100% 实现-文档一致性。
