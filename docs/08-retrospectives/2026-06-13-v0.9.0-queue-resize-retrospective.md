## 发生的问题

### P1: QueueResizeResult 未复用 AdjustmentResult

SR §4.4 设计 `QueueResizeAdjustmentAdapter.apply()` 返回 `AdjustmentResult<ResizeEvidence>`，复用现有泛型 `AdjustmentResult<T>`。SR review F01 确认了泛型 API 兼容性。

实际实现创建了独立的 `QueueResizeResult` 类，不依赖 `AdjustmentResult`。

**根因**: `AdjustmentResult` 的 `executorId` 字段在 `failed()` 工厂中为 `null`（`new AdjustmentResult<>(null, false, failureCode, failureReason, evidence)`），而 queue resize 的 `EXECUTOR_NOT_FOUND` 失败场景中 executorId 是有意义的参数。`QueueResizeResult` 去掉了 executorId 字段，使 API 更简洁。

**处置**: 接受偏差。`QueueResizeResult` 是更精确的返回类型——它只服务 queue resize 场景，不携带不必要的 executorId。两个 result 类型并存不冲突。

### P2: QueueResizeSafetyGate 未实现 ControlGate 接口

SR §4.3 设计 `QueueResizeSafetyGate implements ControlGate<QueueResizeCommand>`，`evaluate()` 接收 `(QueueResizeCommand, ExecutorStateSnapshot, ReadinessSummary)`。

实际实现使用独立接口：`evaluate(QueueResizeCommand, ManagedExecutor)` → `EvaluationResult(GateResult, reason)`，不依赖 `ControlGate`/`SafetyGateResult`/`ReadinessSummary`。

**根因**: `ControlGate<T>.evaluate()` 的三参数签名（command + state + readiness）是为 scale adjustment 场景设计的。Queue resize 的安全检查不需要 readiness（SR 已确认），且直接接收 `ManagedExecutor` 比接收 `ExecutorStateSnapshot` 更实用（safety gate 需要调用 `executor.getQueueSize()` / `executor.isShutdown()` 等实时方法，而非仅依赖快照）。

**处置**: 接受偏差。两个 safety gate 各自独立，语义清晰。`ControlGate<T>` 接口的抽象层次不足以同时覆盖 thread adjustment 和 queue resize 两种不同性质的操作。

### P3: 计划 Change 数 3→2，且单 commit 交付

原始 00-objectives-and-scope 计划 3 个 change，SR 合并为 2 个，实际在单一 commit 中交付两个 change。

**根因**: 两个 change 的边界虽然在设计文档中清晰，但实现时发现 change 2 的端到端测试（QueueResizeEndToEndTest）与 change 1 的核心组件共享所有测试基础设施（真实 TPE、ManagedExecutor、ExecutorRegistry、CountDownLatch 清理）。拆成两个 commit 意味着 change 1 commit 包含未验证的组件（adapter/rebuild 完整但端到端未跑），change 2 commit 只追加测试——没有独立价值。

v0.8.0 也遇到了类似情况（3→2 change 合并），但 v0.8.0 是 SR closure 后合并的。v0.9.0 在 SR 阶段就完成了合并，流程上更成熟。

**处置**: 单 commit 交付 2 个 change 是合理的——change 2 的独立可验证性完全依赖 change 1，拆开只会导致中间状态不可测试。v0.8.0 复盘的流程改进 #1（"变更数调整应在 SR 阶段完成"）在 v0.9.0 中已落地。

### P4: ManagedExecutor 构造方式与 SR 伪代码不一致

SR §4.2 伪代码使用 `new ManagedExecutor(newTpe)`（直接包装已构造的 TPE）。实际实现使用 `new ManagedExecutor(corePoolSize, maxPoolSize, keepAliveMs, unit, queue, threadFactory, handler)`（传参构造）。

**根因**: `ManagedExecutor` 不存在接受 `ThreadPoolExecutor` 的单参构造器——它接受构造参数并在内部创建 TPE。SR 伪代码未与 `ManagedExecutor` 的实际 API 对齐。

**处置**: 实现适配为实际 API。影响范围小——只是构造方式的差异。

## 风险和残余

| 风险 | 严重级别 | 处置 |
|---|---|---|
| SHRINK resize 时 queue 深度 > 新容量 → safety gate DENY | 低 | Safety gate 正确拦截；测试 `safetyGateDenyShrinkWithQueueDepth` 覆盖 |
| awaitTermination 超时后 shutdownNow 可能丢失在途任务 | 低 | 单线程测试环境下不会触发超时；生产环境调用方通过 evidence 感知 |
| 并发 resize 请求 → 幂等保护 | 低 | `ConcurrentHashMap` resizeInProgress 标记已实现；`resizeAlreadyInProgressFails` 测试覆盖 |
| EXPAND drain-and-replay 中个别任务被新 queue reject | 低 | `RejectedExecutionException` 被捕获并记录 `rejectedTaskCount`；`expandDrainAndReplayPreservesTasks` 测试验证正常 replay 路径 |

## 流程改进

### 需要固化到规则的改进

1. **SR 伪代码必须与目标 API 实际签名对齐**: SR §4.2 的 `new ManagedExecutor(newTpe)` 与 `ManagedExecutor` 的实际构造器（接受 core/max/keepAlive/queue/factory/handler 参数）不一致。→ 修订 `managed-change-standard.md` 或在 SR checklist 中增加"伪代码中的构造器和方法调用须与实际 API 签名一致"检查项。

2. **独立 result 类型模式**: v0.9.0 创建的 `QueueResizeResult` 不再复用 `AdjustmentResult<T>`，建立了"每个 adapter 返回自己专用的 result 类型"的模式。这是一个合理的架构分化——`ScaleAdjustmentCommand → AdjustmentResult` 和 `QueueResizeCommand → QueueResizeResult` 的语义边界清晰。→ 未来的新调整维度（如 rejection policy）应参考此模式。

3. **ControlGate 接口的适用边界**: `ControlGate<T>` 接口不适合 queue resize safety gate 场景（不需要 readiness 参数，需要访问实时 executor 状态而非快照）。→ 记录为 `ControlGate` 接口的已知限制：它适合基于"快照 + readiness"的评估模式，不适合需要"实时 executor 方法调用"的模式。

### 后续 agent 必须遵守的行为

- QueueResizeAdjustmentAdapter 使用 `ConcurrentHashMap` 幂等保护；不要在外部绕过 adapter 直接调用 `ExecutorRebuildStrategy.rebuild()`
- ExecutorRebuildStrategy 的 decommission 顺序是 `shutdown → drainTo → awaitTermination`（先 shutdown 禁止新任务入队，再 drain，最后等待终止）
- SHRINK resize 时 drained 任务不 replay（drain-and-discard），只有 EXPAND 才 replay
- Rebuild 后保持同一 executorId（registry.remove + registry.register 使用相同 id）
- 所有 queue resize 测试的 `@AfterEach` 必须：先 countDown 所有 latch → shutdown executor → awaitTermination → registry.remove

## 结论

v0.9.0 完成了项目历史上最持久的结构性债务——运行时队列容量动态调整。`ThreadPoolExecutor` 不支持 queue 替换的限制通过 ExecutorRebuildStrategy（decommission → commission 周期）安全解决，safety gate + 幂等保护 + evidence 记录形成完整的操作闭环。

计划 3 个 change 在 SR 阶段合并为 2 个（safety-and-evidence → command-and-rebuild），最终单 commit 交付。4 个偏差均已处置（P1/P2 级别，均为 API 适配层面的设计调优而非功能缺陷）。476 测试通过，零回归，现有组件（ManagedExecutor、ExecutorRegistry、ManagedExecutorAdjustmentAdapter）未经修改。

`DynamicThreadPollerManager` 的核心承诺中，"线程数动态调整"（v0.7.0）和"队列容量动态调整"（v0.9.0）已兑现。剩余 `Runtime rejection-policy replacement` 是下一个也是最后一个动态配置维度。

版本交付完成。可进入 v0.10.0 规划。
