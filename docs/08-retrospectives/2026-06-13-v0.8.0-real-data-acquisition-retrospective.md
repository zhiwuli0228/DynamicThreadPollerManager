## 计划路径 vs 实际路径

### 计划路径（00-objectives-and-scope section 8）

```
real-executor-data-acquisition (change 1/3)
    ├── metrics-pipeline-executor-integration (change 2/3)  ← 可并行
    └── acquisition-paths-versioning-and-gates (change 3/3) ← 可并行
```

### 实际路径

计划 3 个 change 合并为 2 个串行 change：

```
real-executor-data-acquisition (change 1/2)
    └── acquisition-paths-and-quality-gates (change 2/2)
```

| Change | 计划范围 | 实际范围 | 偏差 |
|---|---|---|---|
| 1/2 | ManagedExecutorConfig, ManagedExecutorScenarioRunner, RunnerTest | 计划范围 + SnapshotAssembler.fromExecutorState() + ManualPressureSampler.sampleFromExecutorState() + integration tests | 合并了原 change 2/3（metrics pipeline integration） |
| 2/2 | AcquisitionReportPaths.forVersion(), G7-G9 gates, AcquisitionReportBridge, 9-run test | 计划范围 + RuntimeObservation 扩展 (keepAliveTimeSeconds/largestPoolSize/taskCount) + EvidenceIndex 修改 + ExecutorRegistry 修改 | 合并了原 change 3/3 并追加了运行时观察扩展 |

### 合并原因

原计划的 3 个 change（runner / metrics 集成 / 路径和门禁）在实际分解时发现：
- metrics 集成（SnapshotAssembler.fromExecutorState）与 runner 实现强耦合——没有 runner 数据则无法验证转换正确性，且两者共享测试基础设施
- 路径版本化和门禁扩展共享 acquisition package 修改对象（AcquisitionReportPaths + AcquisitionDataQualityValidator），且都依赖 runner 产出的数据验证
- 拆成 3 个 change 会增加不必要的中间归档和 spec 同步开销，且每个 change 的独立可验证性不强

最终 2 个 change 的模式更合理：change 1 交付"能跑、能采样、能组装快照"的核心能力，change 2 交付"版本化输出、质量门禁、端到端验证"的收口能力。

## 发生的问题

v0.8.0 的实现过程相对顺利，未发现 P1/P2 级别的严重问题。以下是记录在案的所有偏差和处置：

### P1: 计划变更数调整（3→2）

计划中的 3 个 OpenSpec change 在 SR 阶段合并为 2 个。

**根因**: 原计划高估了 change 2（metrics 集成）的独立可验证性。`fromExecutorState()` 的验证完全依赖 change 1 的 runner 产出数据，拆开只会导致 change 2 的验证推迟或需要 mock。

**处置**: SR 确认合并为 2 change，每个 change 独立可验证、可归档。

### P2: AcquisitionReportBridge 作为新增协调类

`AcquisitionReportBridge` 不在原始 00-objectives-and-scope 的范围内，但在实现 change 2 时发现需要一个新的协调点来聚合 runner 输出到版本化报告。

**根因**: `AcquisitionReportWriter` 的现有接口接收 `AcquisitionDataSet`，而 runner 产出的是 `ScenarioRunOutcome` + `List<PressureSnapshot>`——两者之间缺少一个转换层。

**处置**: 新增轻量 `AcquisitionReportBridge`，桥接 runner 输出到 report writer。不修改 `AcquisitionReportWriter` 的公共接口。

### P3: RuntimeObservation 扩展超出 scope

`RuntimeObservation` 新增了 `keepAliveTimeSeconds`, `largestPoolSize`, `taskCount` 三个字段，这些字段在原始 scope 中未明确列出，但在实现 G7 门禁（要求 5 个 TPE 扩展字段全部 non-null）时必然需要。

**根因**: G7 门禁需要验证 TPE 扩展字段的存在性，而这些字段在 v0.7.0 的 `RuntimeObservation` 中不存在。

**处置**: 扩展 `RuntimeObservation` record 并更新所有相关构造点。`ManualPressureSampler` 的新重载 `sampleFromExecutorState()` 负责填充这些字段。

## 风险和残余

| 风险 | 严重级别 | 处置 |
|---|---|---|
| `ManualPressureSampler.sampleFromExecutorState()` 的扩展字段依赖 `ManagedExecutor` 的 `getPoolSize()`/`getLargestPoolSize()`/`getTaskCount()`/`getKeepAliveTime()` | 低 | 所有方法都是 `ThreadPoolExecutor` 的标准 API，不受线程调度竞争影响 |
| `AcquisitionReportBridge` 不产出 `ReadinessSummary` | 已记录 | 这是设计决策：acquisition-only 模式下不需要 readiness 判定；未来若需要可扩展 bridge |
| G8 门禁依赖 queueSize snapshot 计数，受线程调度影响 | 低 | BURST 阈值设为 ≥2（而非精确值），RAMP 阈值设为 ≥1，为调度波动留有裕度 |

## 流程改进

### 需要在后续版本固化的改进

1. **变更数调整应在 SR 阶段完成**: v0.8.0 的 3→2 合并发生在 SR closure 后、change decomposition 时。流程上 SR review disposition 应明确批准变更数调整，而非事后记录。

2. **00-objectives-and-scope 的 scope 清单应区分"必须实现"和"可能需要"**: `AcquisitionReportBridge` 和 `RuntimeObservation` 扩展属于"可能需要"类——依赖实现细节时才确定。有助于减少 scope checklist 与实际交付物之间的差异。

3. **数据获取 artifacts 数量应从 5 调整为 4**: 原始 scope 声明"每个 run 产出 5 个标准 JSON artifact"，但 acquisition-only 模式下不包含 ReadinessSummary（4 artifacts）。这是合理的——acquisition 和 readiness 是两个独立关注点——但 scope 描述应更精确。

### 后续 agent 必须遵守的行为

- ManagedExecutorScenarioRunner 的 `@AfterEach` 必须按顺序执行：`countDown()` → `shutdown()` → `awaitTermination()` → `registry.remove()`
- 新增 RuntimeObservation 字段时同步更新 `ManualPressureSampler` 的所有重载
- AcquisitionReportPaths 版本标签不能包含 `../` 或 `/`
