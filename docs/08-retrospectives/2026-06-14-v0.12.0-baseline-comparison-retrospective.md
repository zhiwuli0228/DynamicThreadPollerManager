## 核心技术差异：纯协调层，无新 JDK 突破

v0.12.0 与 v0.9.0/v0.10.0 的本质区别：本版本不涉及任何新的 `ThreadPoolExecutor` 属性变更。所有新增组件均为"协调层"——BaselineExecutorCatalog 管理配置，ComparableScenarioRunner 编排已有 runner，NormalizedComparisonMetrics 从已有快照计算聚合值。

这使得 v0.12.0 的技术复杂性集中在设计和测试层面，而非 JDK 底层突破：
- 唯一涉及 TPE 的变更是 ManagedExecutor 拒绝计数（`AtomicLong` + handler 包装器）——约 15 行
- `ExecutorRebuildStrategy` 只需 1 行修改（`oldTpe.getRejectedExecutionHandler()` → `oldExecutor.getRejectionPolicy()`）

**经验**: 不是每个版本都需要突破 JDK 限制。comparison/measurement 层可以在不触碰 executor 内部机制的情况下提供显著价值。这验证了 roadmap 的 "evidence-first" 策略：先建立比较基线，再考虑是否需要更多 runtime knobs。

## 发生的问题

### P1: ManagedExecutor handler 包装破坏 getRejectionPolicy() 契约

**问题**: Change 1 为 ManagedExecutor 添加拒绝计数时，使用 handler 包装器（lambda）传递给 TPE。`getRejectionPolicy()` 原本委托 `platformExecutor.getRejectedExecutionHandler()`，现在返回包装器 lambda 而非原始 `AbortPolicy` 实例。

**影响范围**: 5 个现有测试失败（ManagedExecutorTest ×2、RejectionPolicyEndToEndTest ×1、ExecutorRebuildStrategyTest ×2），以及 `ExecutorRebuildStrategy` 运行时行为——`oldTpe.getRejectedExecutionHandler()` 获取包装器后传给新 executor 构造器，导致双重包装。

**根因**: SR §4.10 设计正确（"getRejectionPolicy() 返回原始 handler"），但实现时遗漏了：传递给 TPE 的 handler ≠ 存储在字段中的 handler。`setRejectionPolicy()` 同样需要维护两个版本（原始 + 包装器）。

**处置**: 
1. 添加 `platformRejectionPolicy` / `virtualRejectionPolicyOriginal` 字段存储原始 handler
2. `getRejectionPolicy()` 返回存储的原始 handler
3. `setRejectionPolicy()` 同步更新原始字段和 TPE 包装器
4. `ExecutorRebuildStrategy.rebuild()` 改用 `oldExecutor.getRejectionPolicy()` 读取原始 handler

**教训**: 涉及 handler/wrapper/代理模式的修改，必须逐方法验证"谁持有原始引用、谁持有包装引用"。在 compact 构造器中添加 `final` 字段时，检查所有访问该值的路径。

### P2: ComparisonResult/ComparisonReportArtifact fromMap() 与 compact constructor null 校验冲突

**问题**: `ComparisonResult` 和 `ComparisonReportArtifact` 的 compact constructor 对所有字段执行 `requireNonNull`，但 `fromMap()` 无法从 JSON 重建 `ScenarioRunOutcome`（需 coordinator + executor 上下文）和 `ManagedExecutorConfig`（需 `TimeUnit` 实例）。

**影响**: Change 2 的 `ComparisonJsonWriterTest` 和 `ComparisonEndToEndTest` 全部 10 个测试的 `readComparisonReport()` 路径均抛出 NPE。

**根因**: SR 设计时未明确区分"构造时校验"和"反序列化时容忍"。compact constructor 的 `requireNonNull` 适用于所有构造路径，但 `fromMap()` 的语义是"从持久化表示重建"而非"创建新对象"——反序列化时可接受部分字段为 null。

**处置**: 移除 `baselineOutcome`、`managedOutcome`、`managedConfig` 三个字段的 `requireNonNull`。核心数据（metrics、deltas、preset info）仍保持非空校验——这些可以从 JSON 完全重建。

**教训**: record 的 compact constructor 校验需要考虑两种构造路径：正常代码路径（全量数据）和反序列化路径（可能缺失上下文相关字段）。方案：要么 (a) 区分两类字段的 null 容忍度，要么 (b) 为反序列化提供单独的工厂方法而非依赖 compact constructor。

### P3: SR review 发现 2 P0 阻断项——parse() vs render() 调用错误 + 命名约定不一致

**问题**: SR §4.8 `parseArtifact()` 伪代码中错误调用 `AcquisitionJsonWriter.render(json)` 而非 `AcquisitionJsonWriter.parse(json)`；`comparisonReportFileName()` 使用 `comparison-{id}.json` 而非现有约定 `{id}-comparison.json`。

**影响**: F01 如未被 SR review 发现，实现 agent 可能直接复制错误的 API 调用导致 serialization 往返失败；F02 破坏 `AcquisitionReportPaths` 的命名模式一致性。

**根因**: SR 伪代码中 render/parse 方向混淆——这是手写序列化代码的常见错误。命名约定未与现有 `AcquisitionReportPaths` 源码交叉验证。

**处置**: SR disposition 阶段 FIX。SR review 的 API 签名强制验证规则在本次生效——随机抽取 3 个 API 调用点验证签名匹配。

**教训**: SR 伪代码强制验证规则（v0.9.0 复盘驱动）继续有效。额外建议：序列化/反序列化的方向性（write→read vs render→parse）应作为 SR review 的专项检查项。

### P4: CommonExecutorPreset.toBaselinePreset() 的 corePoolSize=0 边界

**问题**: `BaselineExecutorPreset` 构造器要求 `corePoolSize > 0`，但 `cached` 预设的 `corePoolSize=0`（CachedThreadPool 的标准语义）。`toBaselinePreset()` 直接传递 0 导致 `IllegalArgumentException`。

**影响**: `CommonExecutorPresetTest.toBaselinePresetShouldMapSynchronousQueue` 抛出异常。

**根因**: SR 设计时假设所有预设的 corePoolSize >= 1，但 JDK CachedThreadPool 的标准配置是 core=0, max=Integer.MAX_VALUE。

**处置**: `toBaselinePreset()` 中添加 `mappedCore = corePoolSize == 0 ? 1 : corePoolSize`。

**教训**: 跨类型转换（CommonExecutorPreset → BaselineExecutorPreset）需要处理语义不兼容的边界值。JDK 不同 executor 类型的合法参数范围不完全重叠。

### P5: 预存 flaky 测试

两次独立出现的预存 flaky 测试：
- `ManagedExecutorTest.readOnlyStateShouldReflectThreadPoolExecutor` — TPE 线程状态时序依赖
- `SafetyGateConcurrencyTest` — 并发 timing

**处置**: 非本次变更引入，不做修改。记录为已知残余风险。

## 改进要点

### 已固化的改进

1. **SR 伪代码 API 签名验证规则再次验证有效**: v0.9.0 复盘引入的规则（随机抽取伪代码中 3 个 API 调用点验证实际源码签名）在本次 SR review 中成功发现潜在问题。建议保持。

2. **toMap/fromMap 模式延续**: v0.11.0 建立的序列化架构（record 携带 toMap/fromMap，JSON writer 只做 render/parse 委托）在 v0.12.0 延续——SR review F03 纠正了初始的 StringBuilder 直接序列化方案。

3. **handler wrapper 模式需双份引用**: 当对现有对象添加包装层时，"get原始"和"get包装"必须分别维护。`getRejectionPolicy()` → 原始，`TPE内部` → 包装。

### 仍需解决的问题

1. `AcquisitionReportPaths` 版本化路径硬编码（v0.11.0 evidence/session，v0.12.0 comparison）——每个版本新增路径方法但旧路径仍硬编码。未来可考虑统一 `forVersion()` 模式管理。

2. `openspec/changes/` 中残留 v0.9.0 的 queue-resize 目录（未归档）——历史遗留，非本次范围。

3. 预存 flaky 测试未修复——`readOnlyStateShouldReflectThreadPoolExecutor` 和 `SafetyGateConcurrencyTest` 偶发失败。

### 后续 agent 行为要求

1. **修改 ManagedExecutor 时**: handler 相关字段有 3 个变体——原始 policy（对外 API）、包装后 handler（给 TPE）、拒绝计数器。新增 getter/setter 时必须保持三者一致。

2. **新建 record 的 fromMap()**: 检查 compact constructor 的 `requireNonNull` 是否兼容反序列化路径。如果 fromMap() 无法重建某些字段（如 ScenarioRunOutcome），必须移除这些字段的非空校验或在 fromMap() 中提供 dummy 值。

3. **SR 伪代码中的序列化方向**: render/parse、write/read、toMap/fromMap 三对操作方向必须交叉验证。SR review 应将此作为必查项。

4. **跨类型转换**: 当两个类型的合法值域不完全重叠时（如 corePoolSize: >=1 vs >=0），转换方法必须处理边界值。

5. **命名约定一致性**: 新增 `AcquisitionReportPaths` 方法前，先读现有源码确认命名模式（`{id}-{descriptor}.{ext}`）。
